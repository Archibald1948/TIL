# 개발 환경 구성 - 로컬 스택, 핫 리로드, 초기 데이터

## 들어가며

새 팀원이 들어왔을 때 보통 이런 문서를 줍니다.

```
1. Node 24 설치 (nvm 쓰세요)
2. PostgreSQL 18 설치하고 로컬에 DB 만들기
3. Redis 설치 (brew install redis, 근데 M1은...)
4. .env 파일은 노션에서 복사
5. 마이그레이션 실행
6. 안 되면 옆자리에 물어보세요
```

Compose를 쓰면 이 문서가 두 줄이 됩니다.

```bash
cp .env.example .env
docker compose up -d --wait
```

호스트에는 Docker만 있으면 되고, Node 버전도 DB 버전도 팀 전체가 동일합니다. 이 문서는 **실제로 매일 쓸 만한 개발 스택**을 만드는 방법을 다룹니다.

# 1. 개발용 스택 만들기

앱 + DB + 캐시로 구성한 기본형입니다.

```yaml
name: myapp

services:
  api:
    build:
      context: .
      target: dev              # 멀티스테이지의 개발용 스테이지
    ports:
      - "3000:3000"
    environment:
      NODE_ENV: development
      DATABASE_URL: postgres://app:devpass@db:5432/appdb
      REDIS_URL: redis://cache:6379
    volumes:
      - ./src:/app/src         # 소스만 연결
      - /app/node_modules      # 컨테이너 것 보호 (아래 설명)
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
    restart: unless-stopped

  db:
    image: postgres:18-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: devpass
      POSTGRES_DB: appdb
    volumes:
      - db-data:/var/lib/postgresql        # ⚠️ 18부터 경로가 바뀜 (2절 참고)
      - ./initdb:/docker-entrypoint-initdb.d:ro
    ports:
      - "5432:5432"            # 로컬 DB 툴로 붙기 위해 노출
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d appdb"]
      interval: 3s
      timeout: 3s
      retries: 10

  cache:
    image: redis:alpine
    command: ["redis-server", "--save", "", "--appendonly", "no"]  # 개발용이라 영속화 끔
    ports:
      - "6379:6379"

volumes:
  db-data:
```

앱에서 DB에 붙을 때 호스트명은 `localhost`가 아니라 **서비스 이름**(`db`, `cache`)입니다. 컨테이너 안의 `localhost`는 그 컨테이너 자기 자신입니다.

```
호스트(내 맥북) → localhost:5432   ← ports로 노출했기 때문에 가능
api 컨테이너   → db:5432          ← 같은 네트워크의 서비스 이름
```

## 개발용 Dockerfile 스테이지

```dockerfile
FROM node:24-alpine AS base
WORKDIR /app
COPY package*.json ./

FROM base AS dev
RUN npm ci                      # devDependencies 포함
COPY . .
CMD ["npm", "run", "dev"]       # 핫 리로드 (nodemon, vite 등)

FROM base AS build
RUN npm ci
COPY . .
RUN npm run build

FROM node:24-alpine AS prod
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
CMD ["node", "dist/main.js"]
```

개발은 `target: dev`, 운영은 `target: prod`로 같은 Dockerfile을 씁니다.

# 2. DB 이미지의 함정 (실제로 겪은 것)

인터넷의 거의 모든 예제가 이렇게 되어 있습니다.

```yaml
volumes:
  - db-data:/var/lib/postgresql/data    # Postgres 17까지의 방식
```

**Postgres 18 이미지**에 이걸 그대로 쓰면 컨테이너가 시작하자마자 죽습니다.

```
Counter to that, there appears to be PostgreSQL data in:
  /var/lib/postgresql/data (unused mount/volume)

The suggested container configuration for 18+ is to place a single mount
at /var/lib/postgresql which will then place PostgreSQL data in a
subdirectory, allowing usage of "pg_upgrade --link" without mount point
boundary issues.
```

18부터는 **한 단계 위 경로**에 마운트합니다.

```yaml
volumes:
  - db-data:/var/lib/postgresql         # ✅ Postgres 18+
```

이미지의 메이저 버전을 올릴 때는 Docker Hub의 해당 이미지 문서를 한 번 훑어보는 게 안전합니다. MySQL, MongoDB도 버전마다 데이터 경로나 기본 인증 방식이 바뀐 적이 있습니다.

# 3. 소스 코드 반영: 세 가지 방법

## 방법 1: 바인드 마운트 (가장 흔함)

```yaml
volumes:
  - ./src:/app/src
  - /app/node_modules     # 익명 볼륨
```

두 번째 줄이 중요합니다. `./:/app`처럼 프로젝트 전체를 마운트하면 **호스트에 없는(또는 OS가 다른) `node_modules`가 컨테이너의 것을 덮어버립니다.** 그 경로에 익명 볼륨을 걸어두면 컨테이너 안에서 설치한 모듈이 살아남습니다.

```
호스트                     컨테이너
./src        ────────→    /app/src          (실시간 반영)
(없음)       ✗덮임 X       /app/node_modules  (익명 볼륨이 보호)
```

## 방법 2: compose watch (권장)

바인드 마운트는 파일 시스템을 공유하기 때문에 macOS/Windows에서 느리고, `node_modules` 같은 예외 처리가 번거롭습니다. Compose의 `watch`는 **변경된 파일만 컨테이너로 복사**하는 방식이라 더 깔끔합니다.

```yaml
services:
  web:
    build: .
    develop:
      watch:
        - action: sync              # 파일만 복사 (재시작 없음)
          path: ./site
          target: /usr/share/nginx/html
          ignore:
            - node_modules/

        - action: sync+restart      # 복사 후 컨테이너 재시작 (설정 파일용)
          path: ./nginx.conf
          target: /etc/nginx/nginx.conf

        - action: sync+exec         # 복사 후 명령 실행 (의존성 설치 등)
          path: ./package.json
          target: /app/package.json
          exec:
            command: ["npm", "install"]

        - action: rebuild           # 이미지 재빌드 (Dockerfile 변경 등)
          path: ./Dockerfile
```

| action | 하는 일 | 쓰는 곳 |
|---|---|---|
| `sync` | 변경 파일 복사만 | 핫 리로드가 되는 소스 |
| `sync+restart` | 복사 후 컨테이너 재시작 | 설정 파일, 리로드 없는 서버 |
| `sync+exec` | 복사 후 지정 명령 실행 | 의존성 파일 변경 시 install |
| `rebuild` | 이미지 새로 빌드 | Dockerfile, 락 파일 |

실행은 두 가지 방법이 있습니다.

```bash
docker compose watch            # 빌드·기동까지 하고 감시
docker compose up --watch       # 띄우면서 감시 (-w 축약)
docker compose watch --no-up    # 이미 떠 있는 스택을 감시만
```

실제 동작 로그입니다.

```
Watch enabled
Syncing service "web" after 1 changes were detected
```

파일을 고치면 컨테이너 안 내용이 재빌드 없이 바뀌는 걸 바로 확인할 수 있습니다.

## 방법 3: 그냥 다시 빌드

컴파일 언어(Go, Rust)나 변경이 드문 서비스는 굳이 복잡하게 갈 필요 없습니다.

```bash
docker compose up -d --build api
```

# 4. 초기 데이터와 마이그레이션

## 이미지가 제공하는 초기화 훅

Postgres, MySQL, MongoDB 이미지는 **데이터 디렉터리가 비어 있을 때만** 특정 폴더의 스크립트를 실행합니다.

```yaml
volumes:
  - ./initdb:/docker-entrypoint-initdb.d:ro
```

```sql
-- initdb/01-schema.sql
CREATE TABLE todos (
  id SERIAL PRIMARY KEY,
  title TEXT NOT NULL
);
INSERT INTO todos (title) VALUES ('도커 배우기'), ('컴포즈 배우기');
```

```bash
docker compose up -d --wait
docker compose exec db psql -U app -d appdb -c 'SELECT * FROM todos;'
#  id |     title
# ----+---------------
#   1 | 도커 배우기
#   2 | 컴포즈 배우기
# (2 rows)
```

파일 이름 앞에 숫자를 붙이면 그 순서대로 실행됩니다(`01-`, `02-`). `.sql`뿐 아니라 `.sh`도 됩니다.

**주의**: 이미 볼륨에 데이터가 있으면 스크립트는 실행되지 않습니다. 스키마를 바꿨는데 반영이 안 된다면 볼륨을 지워야 합니다.

```bash
docker compose down -v && docker compose up -d --wait   # 개발 DB 초기화
```

## 마이그레이션은 별도 서비스로

앱 시작 전에 마이그레이션을 돌려야 한다면 "한 번 실행하고 끝나는 서비스"를 만들고 `service_completed_successfully`로 묶습니다.

```yaml
services:
  migrate:
    build: .
    command: ["npm", "run", "migrate"]
    environment:
      DATABASE_URL: postgres://app:devpass@db:5432/appdb
    depends_on:
      db:
        condition: service_healthy
    restart: "no"          # 끝나면 그대로 종료

  api:
    build: .
    depends_on:
      migrate:
        condition: service_completed_successfully   # 마이그레이션 성공 후 시작
      db:
        condition: service_healthy
```

# 5. 개발 편의 장치

## 관리 도구는 프로필로

```yaml
  adminer:
    image: adminer:latest
    ports:
      - "8081:8080"
    profiles: ["tools"]      # 평소엔 안 뜸

  redis-ui:
    image: redis/redisinsight:latest
    ports:
      - "5540:5540"
    profiles: ["tools"]
```

```bash
docker compose up -d                    # 앱만
docker compose --profile tools up -d    # 관리 도구까지
```

## 일회성 작업

```bash
docker compose run --rm api npm test          # 테스트
docker compose run --rm api npx prisma studio # 스키마 탐색
docker compose exec db psql -U app -d appdb   # DB 콘솔
docker compose exec cache redis-cli           # 캐시 콘솔
```

## 포트 충돌 피하기

로컬에 이미 Postgres가 떠 있다면 호스트 포트를 바꿔줍니다.

```yaml
ports:
  - "${DB_PORT:-5432}:5432"    # .env에서 DB_PORT=15432 로 조정 가능
```

## macOS에서 느릴 때

바인드 마운트가 많은 프로젝트는 macOS에서 파일 I/O가 눈에 띄게 느립니다. 선택지는 이렇습니다.

```
1. compose watch 로 전환 (바인드 마운트 제거)
2. node_modules, .git, dist 등을 마운트에서 제외
3. Docker Desktop 설정에서 VirtioFS 사용 (기본값)
4. OrbStack, Colima 같은 대체 런타임 사용
```

# 6. Dev Container 한 걸음

Compose는 "앱을 실행하는 환경"을 컨테이너로 옮겼습니다. **Dev Container**는 한 걸음 더 나아가 **편집기와 도구 체인까지** 컨테이너 안에 둡니다. VS Code로 컨테이너 안에 접속해서 그 안의 Node·확장·린터를 쓰는 방식입니다.

```json
// .devcontainer/devcontainer.json
{
  "name": "myapp",
  "dockerComposeFile": "../compose.yaml",
  "service": "api",
  "workspaceFolder": "/app",
  "customizations": {
    "vscode": {
      "extensions": ["dbaeumer.vscode-eslint", "esbenp.prettier-vscode"]
    }
  },
  "forwardPorts": [3000]
}
```

```
Compose        앱 실행 환경만 컨테이너      편집기는 호스트
Dev Container  편집기·도구까지 컨테이너      "clone 후 바로 개발" 목표
```

팀원 온보딩을 극단적으로 줄이고 싶을 때, 또는 언어/도구 버전 충돌이 잦은 프로젝트에 효과가 좋습니다. 명세는 Microsoft가 만들었지만 지금은 공개 스펙(containers.dev)이라 다른 편집기도 지원합니다.

# 7. 명령어를 스크립트로 감싸기

`docker compose ...`를 매번 길게 치는 대신 Makefile 하나로 팀 표준을 만듭니다.

```makefile
.PHONY: up down logs sh test migrate reset

up:            ## 개발 스택 시작
	docker compose up -d --wait

down:          ## 중지
	docker compose down

logs:          ## 로그 따라가기
	docker compose logs -f --tail 100

sh:            ## api 컨테이너 셸
	docker compose exec api sh

test:          ## 테스트 실행
	docker compose run --rm api npm test

migrate:       ## 마이그레이션
	docker compose run --rm api npm run migrate

reset:         ## DB까지 완전 초기화
	docker compose down -v && docker compose up -d --wait
```

```bash
make up
make logs
make reset
```

`package.json`의 scripts에 넣어도 되고, `just`나 셸 스크립트도 좋습니다. 핵심은 **"새로 온 사람이 명령어를 외우지 않아도 되게"** 만드는 것입니다.

# 8. 자주 하는 실수

```
❌ 프로젝트 전체를 바인드 마운트하고 node_modules 보호를 안 함
   → 컨테이너 안 모듈이 호스트(비어 있거나 OS가 다른) 것으로 덮임

❌ DB 포트를 0.0.0.0으로 열어둠
   → 카페 와이파이에서 내 개발 DB가 노출. "127.0.0.1:5432:5432" 로

❌ 개발 비밀번호를 compose.yaml에 하드코딩하고 운영에서도 사용
   → 개발용은 괜찮지만 운영 값은 절대 파일에 넣지 않음

❌ 스키마를 바꿨는데 initdb 스크립트가 안 돌아서 헤맴
   → 볼륨이 비어 있을 때만 실행. down -v 필요

❌ 컨테이너 안에서 localhost로 DB 접속
   → 서비스 이름(db)이 호스트명

❌ .env를 커밋
   → .env.example만 커밋하고 .env는 .gitignore
```

## 정리

- 개발 스택은 `build.target: dev` + DB/캐시 서비스 + healthcheck 조합이 기본형
- Postgres 18부터 볼륨 경로가 `/var/lib/postgresql`로 바뀜. 이미지 메이저 버전 올릴 땐 문서 확인
- 소스 반영은 바인드 마운트, `compose watch`(sync/sync+restart/sync+exec/rebuild), 재빌드 중 선택
- 바인드 마운트를 쓸 땐 `node_modules` 같은 경로를 익명 볼륨으로 보호
- 초기 데이터는 `/docker-entrypoint-initdb.d` (볼륨이 빌 때만 실행), 마이그레이션은 `service_completed_successfully`로 순서 보장
- 관리 도구는 `profiles`로 분리, 반복 명령은 Makefile로 감싸기
- 편집기·도구까지 컨테이너로 옮기고 싶으면 Dev Container
