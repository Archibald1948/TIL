# 리소스와 성능 - 제한, OOM, 디스크 관리

## 들어가며

컨테이너는 기본적으로 **호스트 자원을 제한 없이** 씁니다. 메모리 누수가 있는 컨테이너 하나가 서버 전체 메모리를 먹어치우면, 같은 서버의 다른 컨테이너들도 같이 죽습니다.

```
제한 없음                      제한 있음
┌──────────────────────┐      ┌──────────────────────┐
│ api (메모리 누수) 3.5GB│      │ api  512MB (제한)     │
│ db   ← 메모리 부족 💀  │      │ db    1GB            │
│ web  ← 메모리 부족 💀  │      │ web   256MB          │
└──────────────────────┘      └──────────────────────┘
호스트 4GB                     문제 있는 컨테이너만 죽음
```

이 문서는 자원 제한을 거는 법, 컨테이너가 죽었을 때 원인을 판별하는 법, 그리고 디스크를 잡아먹는 이미지·캐시를 관리하는 법을 다룹니다.

# 1. 메모리 제한

```bash
docker run -d --memory 512m --memory-swap 512m myapp
```

| 옵션 | 의미 |
|---|---|
| `--memory`, `-m` | 메모리 상한 (이 값을 넘으면 OOM Kill) |
| `--memory-swap` | 메모리 + 스왑 합계. `--memory`와 같은 값이면 스왑 사용 안 함 |
| `--memory-reservation` | 소프트 제한. 호스트에 여유가 없을 때만 이 값까지 줄이도록 압박 |
| `--oom-kill-disable` | OOM 킬 비활성화 (권장하지 않음, 호스트가 멈출 수 있음) |

Compose에서는 `deploy.resources`를 씁니다. 옛날에는 이게 Swarm 전용이라 무시됐지만, **지금의 Compose는 일반 실행에서도 적용합니다.**

```yaml
services:
  web:
    image: nginx:alpine
    deploy:
      resources:
        limits:
          cpus: "0.50"
          memory: 256M
        reservations:
          cpus: "0.25"
          memory: 128M
```

정말 적용됐는지는 `inspect`로 확인합니다.

```bash
docker inspect tilcheck-web-1 --format '{{.HostConfig.Memory}} {{.HostConfig.NanoCpus}}'
# 268435456 500000000
#  ↑ 256MB     ↑ CPU 0.5개 (1e9 = 1코어)
```

`docker stats`의 분모에서도 확인됩니다.

```
tilcheck-web-1     9.73MiB / 256MiB      3.80%    ← 제한 있음
tilcheck-cache-1   11.28MiB / 3.827GiB   0.29%    ← 제한 없음 (호스트 전체)
```

# 2. OOM Kill: 종료 코드 137

메모리 제한을 넘으면 커널이 프로세스를 강제 종료합니다. 직접 재현해 보면 이렇습니다.

```bash
docker run --rm -m 20m alpine:latest sh -c 'tail /dev/zero'
echo $?
# 137
```

`137 = 128 + 9`, 즉 **SIGKILL로 죽었다**는 뜻입니다.

```
종료 코드 해석
0    정상 종료
1    앱 에러 (예외, 잘못된 설정)
125  docker run 자체의 오류
126  실행 권한 없음
127  명령을 찾을 수 없음 (경로 오타)
137  SIGKILL (대부분 OOM Kill) ← 메모리 제한 확인
139  SIGSEGV (세그멘테이션 폴트)
143  SIGTERM (정상적인 중지 요청)
```

OOM인지 확정하려면:

```bash
docker inspect <컨테이너> --format '{{.State.OOMKilled}} {{.State.ExitCode}}'
# true 137

docker events --filter 'event=oom' --since 1h
```

## JVM·Node의 힙 설정

컨테이너 메모리 제한을 걸었는데도 런타임이 호스트 메모리 기준으로 힙을 잡으면 소용이 없습니다. 요즘 런타임은 대부분 cgroup 값을 인식하지만, 명시하는 편이 안전합니다.

```yaml
services:
  api:
    environment:
      NODE_OPTIONS: "--max-old-space-size=384"   # 컨테이너 제한 512M보다 작게
    deploy:
      resources:
        limits:
          memory: 512M
```

```dockerfile
# JVM: 컨테이너 제한의 비율로 힙 설정
ENV JAVA_OPTS="-XX:MaxRAMPercentage=75.0"
```

# 3. CPU 제한

```bash
docker run --cpus 1.5 myapp           # 코어 1.5개만큼
docker run --cpuset-cpus 0,1 myapp    # 0번, 1번 코어에 고정
docker run --cpu-shares 512 myapp     # 상대적 가중치 (경합 시에만 의미)
```

`--cpus`는 "절대량", `--cpu-shares`는 "경합할 때의 비율"입니다. 보통은 `--cpus`(Compose의 `limits.cpus`)면 충분합니다.

```
--cpus 0.5    → 100ms마다 50ms만 실행 (호스트 코어 수와 무관)
--cpu-shares  → 다른 컨테이너와 CPU를 두고 다툴 때의 우선순위
```

CPU 제한은 메모리와 달리 **초과해도 죽지 않고 느려집니다.** 응답 지연이 원인 모르게 생긴다면 CPU 스로틀링을 의심해 볼 수 있습니다.

## 그 밖의 제한

```yaml
services:
  api:
    pids_limit: 200          # 프로세스/스레드 개수 (fork 폭탄 방지)
    ulimits:
      nofile:
        soft: 65535
        hard: 65535          # 열 수 있는 파일 개수
    shm_size: "256mb"        # /dev/shm 크기 (Chrome, Postgres 등에서 필요)
```

# 4. 재시작 정책

컨테이너가 죽었을 때 자동으로 되살릴지 결정합니다.

| 정책 | 동작 |
|---|---|
| `no` | 재시작하지 않음 (기본값) |
| `on-failure[:횟수]` | 0이 아닌 종료 코드일 때만, 횟수 제한 가능 |
| `always` | 항상 재시작. 데몬이 시작될 때도 같이 시작 |
| `unless-stopped` | 항상 재시작하되, 사용자가 명시적으로 stop 했으면 그대로 둠 |

```yaml
services:
  api:
    restart: unless-stopped     # 서버 재부팅 후에도 자동 기동, 내가 멈춘 건 유지
  migrate:
    restart: "no"               # 한 번 돌고 끝나는 작업
```

`always`와 `unless-stopped`의 차이는 재부팅 시 드러납니다. 내가 일부러 멈춰둔 컨테이너를 재부팅 후에도 멈춘 상태로 두고 싶다면 `unless-stopped`입니다.

**주의**: 재시작 정책은 앱 버그를 가려줍니다. 계속 죽고 되살아나는 컨테이너는 `docker events --filter event=restart`나 `docker compose ps`의 재시작 횟수로 확인해야 합니다.

# 5. Apple Silicon에서의 아키텍처와 성능

M1 이후 맥은 arm64입니다. amd64용 이미지를 실행하면 **QEMU 에뮬레이션**이 돌고, 그만큼 느려집니다. 같은 셸 루프를 두 아키텍처로 돌려본 결과입니다.

```bash
time docker run --rm --platform linux/arm64 alpine sh -c 'for i in $(seq 1 200000); do :; done'
# 0.299 total     ← 네이티브

time docker run --rm --platform linux/amd64 alpine sh -c 'for i in $(seq 1 200000); do :; done'
# 4.333 total     ← 에뮬레이션, 약 14배 느림
```

CPU를 많이 쓰는 작업(빌드, 테스트, 압축)에서는 체감이 훨씬 큽니다.

```
증상: 로컬에서 도커만 쓰면 이상하게 느리다
확인: docker inspect <이미지> --format '{{.Architecture}}'
      docker image ls --tree
해결: arm64 지원 이미지 태그 사용, 또는 직접 멀티 아키텍처 빌드
```

이 환경처럼 containerd 이미지 저장소를 쓰면 하나의 태그에 여러 아키텍처를 담은 이미지를 그대로 다룰 수 있습니다.

```bash
docker image ls --tree tilmulti:test
# IMAGE            ID             DISK USAGE   CONTENT SIZE
# tilmulti:test    07940f632099        130MB         57.8MB
# ├─ linux/amd64   00391d396d7d       28.8MB        28.8MB
# └─ linux/arm64   6afd7d6e4ba0        102MB           29MB
```

```bash
docker info --format '{{json .DriverStatus}}'
# [["driver-type","io.containerd.snapshotter.v1"]]    ← containerd 저장소 사용 중
```

# 6. 빌드·실행 속도 올리기

## 빌드

```
1. 레이어 순서: 잘 안 바뀌는 것(의존성 설치)을 위로, 자주 바뀌는 것(소스 복사)을 아래로
2. .dockerignore: node_modules, .git, dist 제외 → 컨텍스트 전송량 감소
3. 캐시 마운트: RUN --mount=type=cache 로 패키지 매니저 캐시 재사용
4. 멀티스테이지: 빌드 도구는 최종 이미지에 넣지 않기
5. CI에서는 레지스트리/GHA 캐시 사용 (6번 문서)
```

```dockerfile
# 패키지 매니저 캐시를 레이어 밖에 두기
RUN --mount=type=cache,target=/root/.npm \
    npm ci
```

## 실행

```
- 바인드 마운트 줄이기 (macOS/Windows에서 파일 I/O가 느림)
- 로그를 과도하게 찍지 않기 (json-file 쓰기 비용)
- 개발용 DB는 영속화 끄기: redis --save "" / postgres fsync=off (개발 전용!)
- Docker Desktop 리소스 설정 조정 (Settings → Resources)
```

현재 VM에 할당된 자원은 이렇게 확인합니다.

```bash
docker info --format 'CPU={{.NCPU}} MEM={{.MemTotal}}'
# CPU=8 MEM=4109152256      ← 약 3.83GiB
```

빌드가 자주 터지거나 느리면 이 값을 올리는 것만으로 해결되는 경우가 많습니다.

# 7. 디스크 관리

Docker는 조용히 디스크를 먹습니다. 이미지, 정지된 컨테이너, 볼륨, **빌드 캐시**가 쌓입니다.

```bash
docker system df
# TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
# Images          8         5         4.136GB   3.768GB (91%)
# Containers      7         6         270.3kB   4.096kB (1%)
# Local Volumes   5         1         213.7MB   213.7MB (100%)
# Build Cache     43        0         3.745GB   3.368GB
```

빌드 캐시가 3.7GB인 걸 보세요. 이미지보다 캐시가 더 큰 경우도 흔합니다.

```bash
docker system df -v      # 어떤 이미지/볼륨이 얼마나 쓰는지 상세히
```

## 정리 명령

```bash
# 안전한 것부터
docker container prune              # 정지된 컨테이너 삭제
docker image prune                  # 태그 없는(dangling) 이미지 삭제
docker builder prune                # 빌드 캐시 삭제
docker builder prune --filter until=168h   # 7일보다 오래된 캐시만

# 위험한 것
docker image prune -a               # 사용 중이 아닌 모든 이미지 삭제 (다시 받아야 함)
docker volume prune                 # 컨테이너가 참조하지 않는 볼륨 삭제 (데이터 손실 가능)
docker system prune                 # 컨테이너+네트워크+dangling 이미지+캐시
docker system prune -a --volumes    # 거의 전부 삭제. 정말 필요할 때만
```

```
⚠️ docker volume prune / system prune --volumes
   → 잠깐 내려둔 스택의 DB 볼륨도 "사용 안 함"으로 판단될 수 있습니다.
     실행 전에 docker volume ls 로 무엇이 지워질지 확인하세요.
```

## 애초에 덜 쌓이게 하기

```
- 로그 로테이션 설정 (3번 문서)
- 이미지 태그를 latest로 덮어쓰지 말고 버전 태그 → 옛날 것만 골라 삭제 가능
- CI 러너에서는 주기적으로 builder prune
- 멀티스테이지로 최종 이미지 크기 줄이기
```

# 8. 성능 문제 진단 순서

```
느리다 / 죽는다
  1. docker stats                  → CPU·메모리가 제한에 붙어 있나?
  2. docker inspect .State         → OOMKilled, ExitCode 확인
  3. docker compose logs           → 앱 레벨 에러
  4. docker events --since 1h      → oom / die / restart 이벤트
  5. docker image inspect --format '{{.Architecture}}'  → 에뮬레이션 여부
  6. docker system df              → 디스크 압박
```

## 정리

- 컨테이너는 기본적으로 자원 제한이 없음. 운영에서는 `deploy.resources.limits`로 메모리·CPU 상한을 반드시 지정
- 메모리 초과는 **즉시 죽음(137)**, CPU 초과는 **느려짐**. 증상이 다름
- 종료 코드 137 + `State.OOMKilled: true` → 메모리 제한 문제
- 런타임 힙 설정(`NODE_OPTIONS`, `MaxRAMPercentage`)을 컨테이너 제한보다 작게 맞추기
- 재시작 정책은 `unless-stopped`가 무난, 일회성 작업은 `"no"`
- Apple Silicon에서 amd64 이미지는 QEMU 에뮬레이션으로 수 배~십수 배 느림. `docker image ls --tree`로 아키텍처 확인
- 디스크는 **빌드 캐시**가 가장 많이 차지. `docker system df`로 주기적으로 확인하고 `builder prune`
- `system prune -a --volumes`는 데이터까지 지울 수 있으니 무엇이 지워지는지 확인 후 실행
