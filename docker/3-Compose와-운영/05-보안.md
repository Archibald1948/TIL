# 보안 - 최소 권한으로 컨테이너 돌리기

## 들어가며

"컨테이너는 격리되어 있으니 안전하다"는 말은 절반만 맞습니다. 컨테이너는 VM이 아니라 **같은 커널을 공유하는 프로세스**입니다. 기본 설정 그대로 쓰면 이런 상태입니다.

```
기본값으로 실행한 컨테이너
- root(uid 0)로 프로세스 실행
- 파일 시스템 전체 쓰기 가능
- 14개의 리눅스 capability 보유
- 자원 제한 없음
- 컨테이너 안에서 커널 취약점을 건드리면 호스트까지 영향
```

이 문서는 "공격당해도 피해를 줄이는" 설정들을 다룹니다. 하나하나는 어렵지 않고, 대부분 compose.yaml에 몇 줄 추가하는 수준입니다.

# 1. root로 실행하지 않기

가장 효과가 큰 조치입니다. 컨테이너 안 root는 대부분 호스트 root와 같은 uid 0이고, 볼륨을 통해 호스트 파일에 영향을 줄 수 있습니다.

## Dockerfile에서

```dockerfile
FROM node:24-alpine

WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .

# 전용 사용자 생성 후 전환
RUN addgroup -S app && adduser -S -G app app
USER app

CMD ["node", "server.js"]
```

`node`, `nginx` 등 공식 이미지에는 비root 계정이 이미 있는 경우가 많습니다(예: node 이미지의 `node` 사용자).

```dockerfile
USER node
```

## Compose에서

```yaml
services:
  app:
    image: myapp:1.0
    user: "1000:1000"     # uid:gid 직접 지정
```

```bash
docker compose exec app id
# uid=1000 gid=1000 groups=1000
```

## 자주 막히는 지점

```
문제: 비root로 바꿨더니 파일 쓰기 권한 에러
해결:
  1. 앱이 쓰는 디렉터리를 COPY --chown=app:app 으로 넘기기
  2. 로그·임시 파일은 tmpfs 또는 볼륨으로
  3. 1024 미만 포트는 바인딩 불가 → 컨테이너 안에서는 8080 쓰고 -p 80:8080 으로 매핑
```

```dockerfile
COPY --chown=app:app . .
```

# 2. 파일 시스템 읽기 전용으로

앱이 자기 파일을 고칠 이유가 없다면 루트 파일 시스템을 잠급니다. 침입자가 웹셸을 심는 것을 어렵게 만듭니다.

```yaml
services:
  app:
    image: alpine:latest
    read_only: true
    tmpfs:
      - /tmp           # 쓰기가 필요한 곳만 메모리 파일 시스템으로
      - /run
```

실제 동작 확인:

```bash
docker compose exec app sh -c 'touch /rootfile'
# touch: /rootfile: Read-only file system

docker compose exec app sh -c 'touch /tmp/ok && echo "tmpfs 쓰기 OK"'
# tmpfs 쓰기 OK
```

`tmpfs`는 메모리에 올라가므로 컨테이너가 사라지면 같이 사라집니다. 캐시나 임시 파일에 적합합니다.

# 3. Capability 줄이기

리눅스는 root 권한을 잘게 쪼갠 **capability**로 관리합니다. 컨테이너는 기본적으로 14개를 갖고 시작합니다.

```bash
docker run --rm alpine sh -c 'apk add -q libcap; capsh --print | head -1'
# Current: cap_chown,cap_dac_override,cap_fowner,cap_fsetid,cap_kill,cap_setgid,
#          cap_setuid,cap_setpcap,cap_net_bind_service,cap_net_raw,cap_sys_chroot,
#          cap_mknod,cap_audit_write,cap_setfcap=ep
```

대부분의 앱은 이 중 아무것도 필요 없습니다. 전부 버리고 필요한 것만 되돌려 줍니다.

```yaml
services:
  app:
    cap_drop:
      - ALL
    cap_add:
      - NET_BIND_SERVICE    # 1024 미만 포트가 꼭 필요할 때만
```

효과 확인:

```bash
docker run --rm alpine sh -c 'touch /tmp/f && chown nobody /tmp/f && echo 성공'
# 성공

docker run --rm --cap-drop ALL alpine sh -c 'touch /tmp/f && chown nobody /tmp/f'
# chown: /tmp/f: Operation not permitted     ← CAP_CHOWN 이 없어짐
```

## 권한 상승 차단

```yaml
security_opt:
  - no-new-privileges:true    # setuid 바이너리로 권한을 올리지 못하게
```

## 절대 하지 말아야 할 것

```yaml
privileged: true       # ❌ 거의 모든 격리를 해제. 사실상 호스트 root
```

Docker in Docker나 일부 하드웨어 접근에 쓰이지만, 대안(소켓 프록시, 특정 device만 전달)을 먼저 찾아야 합니다.

```yaml
# 필요한 장치만 전달하는 편이 훨씬 안전
devices:
  - "/dev/ttyUSB0:/dev/ttyUSB0"
```

# 4. 시크릿 관리

## 환경변수는 생각보다 잘 샙니다

```bash
docker run -d --name envleak -e DB_PASSWORD=supersecret alpine sleep 60
docker inspect envleak --format '{{json .Config.Env}}'
# ["DB_PASSWORD=supersecret","PATH=/usr/local/sbin:..."]
```

컨테이너를 inspect할 수 있는 사람이면 누구나 값을 봅니다. 게다가 환경변수는

```
- docker inspect 로 노출
- 자식 프로세스에 그대로 상속
- 앱이 크래시 리포트를 보낼 때 함께 전송되는 사고가 잦음
- compose.yaml 에 적으면 git 에 그대로 커밋됨
```

## Compose secrets

파일을 컨테이너의 `/run/secrets/`에 마운트하는 방식입니다. 이미지 레이어에도, `docker inspect`의 환경변수에도 남지 않습니다.

```yaml
name: myapp

services:
  app:
    image: myapp:1.0
    secrets:
      - db_password
    environment:
      DB_PASSWORD_FILE: /run/secrets/db_password   # 경로만 넘김

secrets:
  db_password:
    file: ./db_password.txt      # 이 파일은 .gitignore 필수
```

```bash
docker compose exec app cat /run/secrets/db_password
# supersecret
```

앱은 환경변수 대신 **파일에서 읽도록** 만듭니다. 많은 공식 이미지가 이 패턴을 지원합니다(`POSTGRES_PASSWORD_FILE`, `MYSQL_ROOT_PASSWORD_FILE` 등).

```js
const password = process.env.DB_PASSWORD
  ?? fs.readFileSync(process.env.DB_PASSWORD_FILE, "utf8").trim();
```

## 빌드 시점 비밀값

`ARG`로 넘긴 토큰은 **이미지 히스토리에 남습니다.** 빌드 시크릿을 써야 합니다.

```dockerfile
# ❌ 히스토리에 남음
ARG NPM_TOKEN
RUN npm ci

# ✅ 레이어에 남지 않음
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci
```

```bash
docker build --secret id=npmrc,src=$HOME/.npmrc .
```

## 정리하면

```
개발 로컬        .env (gitignore) + compose secrets
CI              CI 플랫폼의 시크릿 저장소 (GitHub Actions secrets 등)
운영            클라우드 시크릿 매니저 (AWS Secrets Manager, GCP Secret Manager,
                Vault, Kubernetes Secret + 외부 연동)
절대 금지        이미지 안에 넣기, git 커밋, 환경변수로 로그에 찍기
```

# 5. 이미지 자체의 보안

## 신뢰할 수 있는 이미지 쓰기

```
✅ Docker Official Image (nginx, postgres, node ...)
✅ Verified Publisher / 벤더 공식 계정
✅ 조직 내부 레지스트리에 검증 후 미러링
⚠️ 개인 계정의 star 몇 개짜리 이미지 → Dockerfile 을 직접 확인
```

## 태그 고정과 다이제스트 고정

```dockerfile
FROM node:24-alpine              # ⚠️ 같은 태그도 내용이 바뀜
FROM node:24.8.0-alpine          # ✅ 버전 고정
FROM node@sha256:abc123...       # ✅✅ 다이제스트 고정 (완전 재현 가능)
```

운영 이미지는 다이제스트 고정을 권장하지만, 그만큼 보안 패치를 직접 챙겨야 합니다. Renovate·Dependabot 같은 도구로 자동 갱신 PR을 받는 조합이 현실적입니다.

## 취약점 스캔

```bash
# Docker 내장 (Docker Hub 로그인 필요)
docker scout quickview nginx:alpine
docker scout cves myapp:1.0

# Trivy (오픈소스, 로그인 불필요)
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasecurity/trivy image myapp:1.0

# Dockerfile 린트
docker run --rm -i hadolint/hadolint < Dockerfile
```

`docker scout`는 Docker 계정 로그인이 필요합니다. 로그인하지 않으면 이런 안내가 나옵니다.

```
Log in with your Docker ID or email address to use docker scout.
```

CI에 붙일 때는 Trivy가 설정이 간단한 편입니다. "취약점 0개"는 현실적으로 불가능하니, **CRITICAL/HIGH만 실패 처리**하는 식으로 시작합니다.

```yaml
# GitHub Actions 예시
- name: Trivy 스캔
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: myapp:${{ github.sha }}
    severity: CRITICAL,HIGH
    exit-code: "1"
```

## 이미지를 작게

공격 표면 자체를 줄이는 방법입니다.

```
node:24         (약 1.1GB)  셸, 패키지 매니저, 컴파일러 전부 포함
node:24-alpine  (약 130MB)  최소 구성
distroless      (약 70MB)   셸조차 없음 → 침입해도 할 수 있는 게 거의 없음
scratch         (0B)        정적 바이너리(Go, Rust)만 넣기
```

```dockerfile
FROM gcr.io/distroless/nodejs24-debian12
COPY --from=build /app /app
CMD ["/app/server.js"]
```

셸이 없으면 `docker exec`로 들어가 디버깅하기 어렵다는 단점이 있습니다. 개발은 alpine, 운영은 distroless처럼 나누는 방법도 있습니다.

# 6. docker.sock을 마운트하지 말 것

편의상 이런 설정을 종종 봅니다.

```yaml
volumes:
  - /var/run/docker.sock:/var/run/docker.sock   # ⚠️ 위험
```

이게 얼마나 위험한지 직접 확인해 보면 이렇습니다.

```bash
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock docker:cli docker ps --format '{{.Names}}'
# tildev-db-1
# tilwatch-web-1
# tilsec-app-1
# tilcheck-tools-1
# ...
```

컨테이너 하나가 **호스트의 모든 컨테이너를 보고 조작**할 수 있습니다. 여기서 한 걸음 더 나가면 호스트 파일 시스템을 마운트한 특권 컨테이너를 띄울 수 있고, 그건 곧 호스트 장악입니다.

```
소켓을 컨테이너에 주는 것 = 그 컨테이너에 호스트 root 권한을 주는 것
```

꼭 필요하다면(예: Traefik, Watchtower, CI 러너):

```
1. 읽기 전용으로 마운트 (:ro) — 완화일 뿐 근본 해결은 아님
2. docker-socket-proxy 를 앞에 두고 필요한 API만 허용
3. 소켓 대신 Docker API를 TLS로 제한 노출
4. rootless 모드에서 운영
```

# 7. rootless 모드 (리눅스)

Docker 데몬 자체를 일반 사용자 권한으로 돌리는 방식입니다. 데몬이 탈취돼도 호스트 root를 얻지 못합니다.

```bash
# 설치 (리눅스)
dockerd-rootless-setuptool.sh install

# 이후 이 사용자의 docker 명령은 rootless 데몬을 사용
docker context use rootless
docker info --format '{{.SecurityOptions}}'   # rootless 항목 확인
```

제약도 있습니다.

```
- 1024 미만 포트 바인딩 제한 (설정으로 완화 가능)
- 일부 스토리지 드라이버·네트워크 기능 제약
- 성능이 조금 떨어질 수 있음
```

macOS·Windows의 Docker Desktop은 리눅스 VM 안에서 돌기 때문에 호스트와 이미 분리되어 있고, rootless 설정은 리눅스 서버에서 의미가 큽니다.

# 8. 네트워크 최소 노출

```yaml
services:
  web:
    ports:
      - "80:80"            # 외부 공개가 필요한 것만

  db:
    # ports 없음! 같은 네트워크의 서비스만 접근 가능
    networks: [backend]

  api:
    networks: [frontend, backend]   # 중간 계층만 양쪽에 연결

networks:
  frontend:
  backend:
    internal: true         # 외부 인터넷으로 나가지도 못하게
```

개발 중 DB에 툴로 붙어야 한다면 로컬로만 여는 습관을 들입니다.

```yaml
ports:
  - "127.0.0.1:5432:5432"    # ✅ 내 컴퓨터에서만
  - "5432:5432"              # ❌ 같은 네트워크의 누구나
```

# 9. 체크리스트

```
이미지
  □ 공식/검증된 베이스 이미지
  □ 버전 또는 다이제스트 고정
  □ 멀티스테이지로 빌드 도구 제외
  □ .dockerignore 에 .env, .git, 키 파일
  □ CI에서 취약점 스캔 (CRITICAL/HIGH 차단)

실행
  □ USER 지정 (비root)
  □ read_only: true + 필요한 곳만 tmpfs
  □ cap_drop: ALL (+ 꼭 필요한 것만 cap_add)
  □ security_opt: no-new-privileges:true
  □ privileged: true 사용하지 않음
  □ 메모리·CPU 제한 (4번 문서)

비밀값
  □ 이미지·git에 비밀값 없음
  □ compose secrets 또는 외부 시크릿 매니저
  □ 빌드 시크릿은 --mount=type=secret

네트워크
  □ 꼭 필요한 포트만 공개, DB는 미공개
  □ 개발용 노출은 127.0.0.1 바인딩
  □ docker.sock 마운트 없음
```

## 정리

- 컨테이너는 커널을 공유하는 프로세스. 기본값은 편의를 위한 설정이지 안전한 설정이 아님
- `USER`로 비root 실행하는 것이 가장 효과가 큼
- `read_only` + `tmpfs`, `cap_drop: ALL`, `no-new-privileges`는 몇 줄로 얻는 큰 이득
- 환경변수 비밀값은 `docker inspect`로 그대로 노출됨 → compose `secrets`나 외부 시크릿 매니저 사용
- 빌드 시 비밀값은 `ARG` 대신 `RUN --mount=type=secret`
- 이미지는 공식·고정 태그·작게, 스캔은 `docker scout`(로그인 필요) 또는 Trivy
- `docker.sock` 마운트는 사실상 호스트 root 위임. 프록시나 대안을 먼저 검토
- 리눅스 서버라면 rootless 모드 고려, 포트는 필요한 것만 노출
