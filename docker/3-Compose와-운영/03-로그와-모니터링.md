# 로그와 모니터링 - 컨테이너가 무슨 일을 하는지 보기

## 들어가며

서버에 SSH로 들어가서 `tail -f /var/log/app.log`를 하던 시절과 달리, 컨테이너에서는 로그를 파일에 쓰지 않습니다.

```
전통적인 방식              컨테이너 방식
앱 → /var/log/app.log      앱 → stdout/stderr → Docker가 수집
로그 로테이션은 앱이 담당    로테이션은 로깅 드라이버가 담당
```

컨테이너는 언제든 삭제되고 다시 만들어지므로, 컨테이너 안 파일에 로그를 쌓으면 **컨테이너가 사라질 때 로그도 사라집니다.** 그래서 "로그는 표준 출력으로 내보내고, 수집은 플랫폼이 한다"가 원칙입니다. 이 문서는 그 수집·조회·모니터링 방법을 다룹니다.

# 1. 로그의 기본: stdout / stderr

컨테이너 안 프로세스가 표준 출력에 찍은 내용을 Docker가 받아 로깅 드라이버로 넘깁니다.

```bash
docker logs <컨테이너>
docker compose logs <서비스>
```

앱 코드에서도 파일이 아니라 콘솔로 출력해야 합니다.

```js
// ✅ 컨테이너에 맞는 방식
console.log(JSON.stringify({ level: "info", msg: "서버 시작", port: 3000 }));

// ❌ 컨테이너 안 파일에 기록
fs.appendFileSync("/var/log/app.log", "서버 시작\n");
```

nginx 이미지 같은 공식 이미지는 이미 그렇게 되어 있습니다. 이미지 안에서 로그 파일을 `/dev/stdout`으로 심볼릭 링크해 둡니다.

## 구조화 로그를 권장하는 이유

```js
// 사람이 읽기 좋은 로그
console.log("user 42 login failed from 1.2.3.4");

// 기계가 읽기 좋은 로그 (검색·집계 가능)
console.log(JSON.stringify({
  level: "warn", event: "login_failed", userId: 42, ip: "1.2.3.4"
}));
```

로그를 나중에 Loki, Elasticsearch, CloudWatch 같은 곳으로 보낼 계획이라면 처음부터 JSON으로 찍는 편이 훨씬 편합니다.

# 2. 로그 조회하기

```bash
# 기본
docker compose logs                    # 전체 서비스
docker compose logs web                # 특정 서비스
docker compose logs -f web             # 실시간 따라가기
docker compose logs --tail 100 web     # 마지막 100줄
docker compose logs -t web             # 타임스탬프 표시
docker compose logs --since 10m        # 최근 10분
docker compose logs --since 2026-09-16T04:00:00 --until 2026-09-16T05:00:00
docker compose logs --no-log-prefix web   # "web-1 | " 접두사 제거 (파이프 처리용)
```

실제 출력입니다.

```bash
docker compose logs -t --since 2m --tail 2 web
# web-1  | 2026-09-16T04:10:26.201182091Z ::1 - - [16/Sep/2026:04:10:26 +0000] "GET / HTTP/1.1" 200 13 "-" "Wget" "-"
# web-1  | 2026-09-16T04:10:31.297555552Z ::1 - - [16/Sep/2026:04:10:31 +0000] "GET / HTTP/1.1" 200 13 "-" "Wget" "-"
```

## 검색과 가공

```bash
# 에러만
docker compose logs --no-log-prefix api | grep -i error

# JSON 로그에서 특정 필드만 (jq 필요)
docker compose logs --no-log-prefix api | jq -r 'select(.level=="error") | .msg'

# 파일로 저장
docker compose logs --no-log-prefix --since 1h api > api-$(date +%F).log
```

`docker logs`는 **stdout과 stderr를 모두** 보여줍니다. 나누고 싶으면 리다이렉션을 씁니다.

```bash
docker logs api 2> errors.log 1> output.log
```

# 3. 로깅 드라이버

컨테이너 로그를 어디에 어떻게 저장할지 결정하는 것이 로깅 드라이버입니다. 현재 엔진에서 쓸 수 있는 것들입니다.

```bash
docker info --format '{{json .Plugins.Log}}'
# ["awslogs","fluentd","gcplogs","gelf","journald","json-file","local","splunk","syslog"]
```

| 드라이버 | 설명 | `docker logs` 지원 |
|---|---|---|
| `json-file` | 기본값. 호스트에 JSON 파일로 저장 | ✅ |
| `local` | Docker 전용 포맷. json-file보다 효율적, 기본 로테이션 있음 | ✅ |
| `journald` | systemd 저널로 전송 | ✅ |
| `syslog` | syslog 서버로 전송 | ❌ |
| `fluentd` | Fluentd로 전송 (로그 수집 파이프라인) | ❌ |
| `awslogs` / `gcplogs` / `splunk` | 각 클라우드·SaaS로 직접 전송 | ❌ |
| `none` | 로그를 버림 | ❌ |

## json-file의 함정: 로테이션

기본 드라이버 `json-file`은 **아무 설정을 안 하면 무한정 커집니다.** 디스크가 가득 차는 사고의 단골 원인입니다.

```bash
# 로그 파일 위치 확인 (리눅스 기준, Docker Desktop은 VM 안 경로)
docker inspect tilcheck-web-1 --format '{{.LogPath}}'
# /var/lib/docker/containers/b5c7efe...b5c7efe-json.log
```

반드시 로테이션을 걸어둡니다.

```yaml
services:
  web:
    image: nginx:alpine
    logging:
      driver: json-file
      options:
        max-size: "10m"    # 파일 하나가 10MB 넘으면 새 파일
        max-file: "3"      # 최대 3개 보관 (총 30MB)
```

적용 결과 확인:

```bash
docker inspect tilcheck-web-1 --format '{{json .HostConfig.LogConfig}}'
# {"Config":{"max-file":"3","max-size":"10m"},"Type":"json-file"}
```

## 데몬 기본값으로 설정하기

서비스마다 쓰는 게 번거로우면 데몬 설정에 기본값을 둡니다. 리눅스는 `/etc/docker/daemon.json`, Docker Desktop은 Settings → Docker Engine에서 편집합니다.

```json
{
  "log-driver": "local",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

```bash
sudo systemctl restart docker    # 리눅스, 적용하려면 재시작 필요
```

이후 **새로 만들어지는** 컨테이너에만 적용됩니다. 기존 컨테이너는 다시 만들어야 합니다.

# 4. 실시간 상태 보기

## docker stats

```bash
docker stats --no-stream --format '{{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}\t{{.MemPerc}}'
# tilcheck-web-1     0.00%   9.73MiB / 256MiB     3.80%
# tilcheck-cache-1   0.26%   11.28MiB / 3.827GiB  0.29%
```

`--no-stream`이 없으면 top처럼 계속 갱신됩니다. Compose 프로젝트만 보려면:

```bash
docker compose stats
```

메모리 뒤의 분모에 주목하세요. 위 출력에서 `web`은 `256MiB`(제한을 걸어둔 값), `cache`는 `3.827GiB`(호스트 전체)입니다. **제한이 없으면 호스트 메모리를 다 쓸 수 있다는 뜻**입니다.

## docker events

컨테이너에 무슨 일이 일어났는지(시작, 종료, OOM, 헬스체크) 시간순으로 보여줍니다. 장애 원인 추적에 유용합니다.

```bash
docker events --since 5m --until 0s --filter 'type=container' \
  --format '{{.Time}} {{.Action}} {{.Actor.Attributes.name}}'
# 1789531831 exec_create: wget -qO- http://localhost/ tilcheck-web-1
# 1789531831 exec_start: wget -qO- http://localhost/ tilcheck-web-1
# 1789531831 exec_die tilcheck-web-1
```

자주 쓰는 필터입니다.

```bash
docker events --filter 'event=die'        # 종료된 컨테이너
docker events --filter 'event=oom'        # 메모리 초과로 죽은 것
docker events --filter 'event=health_status'
docker events --filter 'container=api'
```

## 헬스체크 상태

```bash
# 현재 상태
docker inspect tilcheck-web-1 --format '{{.State.Health.Status}}'
# healthy

# 최근 검사 이력 (실패 원인 파악)
docker inspect tilcheck-web-1 --format '{{range .State.Health.Log}}{{.Start}} exit={{.ExitCode}} {{.Output}}{{"\n"}}{{end}}'
# 2026-09-16 04:10:26.122666716 +0000 UTC exit=0
# 2026-09-16 04:10:31.205779011 +0000 UTC exit=0
```

`unhealthy`인데 이유를 모르겠다면 `.Output`에 헬스체크 명령의 실제 출력이 들어 있습니다.

## 프로세스와 파일 변경

```bash
docker compose top             # 컨테이너 안에서 돌고 있는 프로세스
docker diff <컨테이너>          # 이미지 대비 변경된 파일 (A 추가 / C 변경 / D 삭제)
docker port <컨테이너>          # 포트 매핑 확인
```

# 5. 메트릭 수집: cAdvisor + Prometheus + Grafana

`docker stats`는 지금 이 순간만 보여줍니다. **시간에 따른 변화**를 보려면 메트릭을 저장해야 합니다. 표준 조합은 이렇습니다.

```
컨테이너들
   │  (컨테이너별 CPU/메모리/네트워크)
   ▼
cAdvisor  ──메트릭 노출(/metrics)──▶  Prometheus  ──쿼리──▶  Grafana
                                      (시계열 저장)         (대시보드)
```

```yaml
name: monitoring

services:
  cadvisor:
    image: ghcr.io/google/cadvisor:v0.60.5
    ports:
      - "8080:8080"
    volumes:
      - /:/rootfs:ro
      - /var/run:/var/run:ro
      - /sys:/sys:ro
      - /var/lib/docker/:/var/lib/docker:ro
    privileged: true          # 호스트 지표를 읽기 위해 필요

  prometheus:
    image: prom/prometheus:latest
    ports:
      - "9090:9090"
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml:ro
      - prom-data:/prometheus

  grafana:
    image: grafana/grafana:latest
    ports:
      - "3001:3000"
    environment:
      GF_SECURITY_ADMIN_PASSWORD: ${GRAFANA_PASSWORD:?관리자 비밀번호 필요}
    volumes:
      - grafana-data:/var/lib/grafana
    depends_on:
      - prometheus

volumes:
  prom-data:
  grafana-data:
```

```yaml
# prometheus.yml
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: cadvisor
    static_configs:
      - targets: ["cadvisor:8080"]
```

cAdvisor 이미지는 최근 릴리스가 `ghcr.io/google/cadvisor`에 올라옵니다. 오래된 자료에 나오는 `gcr.io/cadvisor/cadvisor`는 예전 경로라 최신 태그가 없을 수 있습니다.

## Docker 데몬 자체 메트릭

데몬의 상태(빌드 수, API 호출 등)도 Prometheus 형식으로 노출할 수 있습니다.

```json
// daemon.json
{
  "metrics-addr": "127.0.0.1:9323"
}
```

```yaml
  - job_name: docker
    static_configs:
      - targets: ["host.docker.internal:9323"]
```

# 6. 로그 수집 파이프라인 (한 단계 위)

컨테이너가 여러 서버에 흩어지면 `docker logs`로는 감당이 안 됩니다. 이때 쓰는 구성입니다.

```
컨테이너 stdout
   │
   ▼
수집기 (Fluent Bit / Promtail / Vector)
   │
   ▼
저장소 (Loki / Elasticsearch / CloudWatch)
   │
   ▼
조회 (Grafana / Kibana)
```

가벼운 조합은 **Promtail + Loki + Grafana**입니다. Grafana에서 메트릭과 로그를 한 화면에서 볼 수 있습니다.

```yaml
  loki:
    image: grafana/loki:latest
    ports:
      - "3100:3100"

  promtail:
    image: grafana/promtail:latest
    volumes:
      - /var/lib/docker/containers:/var/lib/docker/containers:ro
      - ./promtail.yml:/etc/promtail/config.yml:ro
    command: -config.file=/etc/promtail/config.yml
```

개인 프로젝트라면 여기까지 갈 필요는 없습니다. `json-file` + 로테이션 + `docker compose logs`면 충분하고, 서비스가 커지면 그때 도입해도 늦지 않습니다.

# 7. 문제 상황별 확인 순서

```
컨테이너가 자꾸 죽는다
  1. docker compose ps -a          → 상태와 종료 코드
  2. docker compose logs --tail 50 → 마지막 로그
  3. docker events --filter event=die
  4. 종료 코드 137이면 메모리 부족(OOM), 1이면 앱 에러

unhealthy 상태다
  1. docker inspect --format '{{json .State.Health}}'
  2. .Log[].Output 에서 헬스체크 명령의 실제 출력 확인
  3. docker compose exec 로 들어가서 직접 같은 명령 실행

로그가 안 보인다
  1. 앱이 파일에 쓰고 있지 않은지 확인 (stdout으로 바꾸기)
  2. 로깅 드라이버가 syslog/fluentd면 docker logs로는 안 보임
  3. 출력 버퍼링 문제일 수 있음 (Python은 PYTHONUNBUFFERED=1)

디스크가 가득 찼다
  1. docker system df
  2. 로그 로테이션 설정 여부 확인
  3. 4번 문서의 정리 명령 참고
```

Python 앱의 출력 버퍼링은 자주 겪는 문제입니다.

```dockerfile
ENV PYTHONUNBUFFERED=1    # 이게 없으면 로그가 한참 뒤에 몰아서 나옴
```

## 정리

- 컨테이너 로그는 파일이 아니라 **stdout/stderr**로 내보내고, 나중을 위해 JSON 구조화 로그를 권장
- `docker compose logs`의 `-f`, `--tail`, `-t`, `--since`, `--no-log-prefix`를 손에 익히기
- 기본 드라이버 `json-file`은 **로테이션을 설정하지 않으면 무한정 커짐** → `max-size`, `max-file` 필수
- 드라이버 기본값은 `daemon.json`에 두고, 새 컨테이너부터 적용됨
- `docker stats`로 현재 사용량, `docker events`로 사건 추적, `docker inspect`의 `State.Health.Log`로 헬스체크 실패 원인 확인
- 시계열 메트릭이 필요하면 cAdvisor + Prometheus + Grafana, 로그 집중화는 Promtail + Loki
- 종료 코드 137은 OOM 신호. 메모리 제한과 함께 보기
