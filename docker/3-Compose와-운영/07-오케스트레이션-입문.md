# 오케스트레이션 입문 - Compose 다음에 오는 것

## 들어가며

Compose로 서버 한 대는 잘 굴러갑니다. 그런데 서비스가 커지면 이런 요구가 생깁니다.

```
"트래픽이 몰리니 api 컨테이너를 10개로 늘려줘"        → 서버 한 대로 부족
"서버 한 대가 죽어도 서비스는 살아 있어야 해"          → 여러 대에 분산 필요
"배포할 때 다운타임 없이 하나씩 교체해줘"              → 롤링 업데이트
"컨테이너가 죽으면 다른 서버에서 다시 띄워줘"          → 스케줄링
"어느 서버에 뭐가 떠 있는지 한눈에 보고 싶어"          → 클러스터 관리
```

이걸 해주는 것이 **컨테이너 오케스트레이션**입니다. 이 문서는 "Compose로 어디까지 되고, 그 다음엔 무엇이 있는지"를 정리합니다. 쿠버네티스를 깊게 다루지는 않고, 넘어갈 때 알아야 할 개념 대응만 잡습니다.

# 1. Compose의 한계

Compose가 못 하는 것을 명확히 알아야 언제 넘어갈지 판단할 수 있습니다.

| 필요한 것 | Compose | 오케스트레이터 |
|---|---|---|
| 여러 컨테이너 정의·실행 | ✅ | ✅ |
| 한 대 안에서 복제본 늘리기 | `--scale`로 가능 | ✅ |
| **여러 서버에 분산 배치** | ❌ | ✅ |
| **노드 장애 시 자동 재배치** | ❌ | ✅ |
| **무중단 롤링 업데이트·자동 롤백** | ❌ (수동 구성) | ✅ |
| 부하 기반 자동 스케일링 | ❌ | ✅ |
| 선언적 상태 유지(원하는 상태로 수렴) | ❌ | ✅ |
| 시크릿·설정 관리 체계 | 기본 수준 | ✅ |

Compose에도 `--scale`은 있습니다. 다만 **한 호스트 안에서만** 복제합니다.

```bash
docker compose up -d --scale api=3
docker compose ps
# myapp-api-1, myapp-api-2, myapp-api-3    ← 전부 같은 서버 안
```

이때 `ports`로 호스트 포트를 고정해 뒀다면 충돌이 납니다. 앞단에 프록시를 두고 서비스 이름으로 접근하게 해야 합니다(같은 네트워크 안에서는 DNS 라운드로빈이 동작합니다).

```
정리하면
서버 1대 + 서비스 몇 개 + 가끔 배포     → Compose로 충분
서버 여러 대 + 무중단 + 자동 복구       → 오케스트레이터 필요
```

현실적인 조언을 하나 덧붙이면, **필요해지기 전에 쿠버네티스로 가면 대부분 후회합니다.** 운영·학습 비용이 상당하고, 작은 서비스는 VPS 한 대 + Compose가 훨씬 효율적입니다.

# 2. 선택지 비교

## Docker Swarm

Docker에 내장된 오케스트레이터입니다. Compose 파일과 문법이 거의 같아서 진입 장벽이 낮습니다.

```bash
docker swarm init                          # 매니저 노드 초기화
docker swarm join --token <토큰> <주소>     # 워커 노드 추가
docker stack deploy -c compose.yaml myapp  # 스택 배포
docker service ls
docker service scale myapp_api=5
docker service update --image myapp:2.0 myapp_api   # 롤링 업데이트
```

```yaml
services:
  api:
    image: myapp:1.0
    deploy:
      replicas: 3
      update_config:
        parallelism: 1        # 한 번에 1개씩 교체
        delay: 10s
        order: start-first    # 새 것 먼저 띄우고 옛 것 제거
      restart_policy:
        condition: on-failure
```

```
장점  배우기 쉬움, Compose 지식 재사용, 추가 설치 없음
단점  생태계·기능이 쿠버네티스에 비해 제한적, 신규 채택 사례가 적음
```

작은 팀이 서버 2~3대를 묶는 정도라면 여전히 합리적인 선택입니다.

## Kubernetes

사실상 업계 표준입니다. 클라우드 3사 모두 관리형 서비스(EKS, GKE, AKS)를 제공합니다.

```
장점  압도적인 생태계, 자동 스케일링, 무중단 배포, 어디서나 같은 방식
단점  개념이 많고 러닝 커브가 가파름, 작은 규모엔 과함, 운영 인력 필요
```

가벼운 배포판도 있습니다.

| 이름 | 용도 |
|---|---|
| **k3s** | 경량 배포판. 라즈베리파이·엣지·소규모 서버에 적합 |
| **kind** | Docker 컨테이너 안에 클러스터 생성. CI·학습용 |
| **minikube** | 로컬 단일 노드 클러스터. 학습용의 고전 |
| **Docker Desktop 내장 k8s** | 설정에서 체크 한 번으로 켜짐. 가장 간편 |

# 3. Compose 개념을 쿠버네티스로 옮기면

용어만 갈아끼우면 절반은 이해됩니다.

| Compose | Kubernetes | 설명 |
|---|---|---|
| service | **Deployment** (+ Pod) | 실행 단위. k8s는 Pod(컨테이너 묶음)를 Deployment가 관리 |
| `deploy.replicas` | `spec.replicas` | 복제본 수 |
| `ports` | **Service** | 네트워크 노출. 외부 공개는 추가로 Ingress |
| `environment` | `env` / **ConfigMap** | 설정 값 |
| `secrets` | **Secret** | 비밀 값 |
| `volumes` | **PersistentVolumeClaim** | 영속 저장소 |
| `networks` | (기본적으로 전부 통신 가능) | 제한하려면 NetworkPolicy |
| `healthcheck` | `livenessProbe` / `readinessProbe` | 살아있나 / 요청 받을 준비됐나 |
| `deploy.resources` | `resources.requests/limits` | 자원 요청과 상한 |
| `restart: unless-stopped` | (기본 동작) | k8s는 항상 원하는 상태로 되돌림 |
| `docker compose up` | `kubectl apply -f` | 선언 적용 |
| `docker compose logs` | `kubectl logs` | 로그 |
| `docker compose exec` | `kubectl exec -it` | 컨테이너 접속 |
| `docker compose ps` | `kubectl get pods` | 상태 확인 |

특히 헷갈리는 두 가지를 짚어둡니다.

```
Pod        컨테이너 1개 이상을 묶은 최소 배포 단위. 같은 Pod 안 컨테이너는
           네트워크·볼륨을 공유 (Compose에는 대응 개념이 없음)

Service    "이 라벨을 가진 Pod들에게 트래픽을 보내는 안정적인 이름/IP"
           Compose에서 서비스 이름으로 접근하던 것과 같은 역할
```

## healthcheck는 둘로 나뉩니다

```yaml
# Compose
healthcheck:
  test: ["CMD", "wget", "-qO-", "http://localhost/health"]
```

```yaml
# Kubernetes
livenessProbe:      # 실패하면 컨테이너를 재시작
  httpGet: { path: /health, port: 3000 }
  periodSeconds: 10
readinessProbe:     # 실패하면 트래픽만 끊음 (재시작 안 함)
  httpGet: { path: /ready, port: 3000 }
  periodSeconds: 5
startupProbe:       # 기동이 느린 앱의 유예 기간
  httpGet: { path: /health, port: 3000 }
  failureThreshold: 30
```

# 4. compose 파일을 쿠버네티스 매니페스트로 변환해 보기

Docker CLI에는 compose 파일을 k8s 매니페스트로 바꿔주는 기능이 들어 있습니다. 개념 대응을 눈으로 보기에 좋습니다.

```bash
docker compose bridge convert -o k8s-out
# Kubernetes resource web-deployment.yaml created
# Kubernetes resource web-service.yaml created
# Kubernetes resource 0-tilwatch-namespace.yaml created
# Kubernetes resource default-network-policy.yaml created
# Kubernetes resource kustomization.yaml created
```

```bash
find k8s-out -type f
# k8s-out/base/0-tilwatch-namespace.yaml
# k8s-out/base/default-network-policy.yaml
# k8s-out/base/kustomization.yaml
# k8s-out/base/web-deployment.yaml
# k8s-out/base/web-expose.yaml
# k8s-out/base/web-service.yaml
# k8s-out/overlays/desktop/kustomization.yaml
# k8s-out/overlays/desktop/web-service.yaml
```

`web` 서비스 하나가 Deployment로 변환된 결과입니다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
    name: web
    namespace: tilwatch
    labels:
        com.docker.compose.project: tilwatch
        com.docker.compose.service: web
spec:
    replicas: 1
    selector:
        matchLabels:
            com.docker.compose.project: tilwatch
            com.docker.compose.service: web
    template:
        metadata:
            labels:
                com.docker.compose.project: tilwatch
                com.docker.compose.service: web
        spec:
            containers:
                - name: web
                  image: tilwatch-web
                  imagePullPolicy: IfNotPresent
                  ports:
                    - name: web-80
                      containerPort: 80
```

`ports: "19081:80"` 는 Service로 분리됩니다.

```yaml
apiVersion: v1
kind: Service
metadata:
    name: web-published
    namespace: tilwatch
spec:
    selector:
        com.docker.compose.project: tilwatch
        com.docker.compose.service: web
    ports:
        - name: web-19081
          port: 19081
          protocol: TCP
          targetPort: web-80
```

```
compose의 service     → Deployment (어떤 Pod을 몇 개 띄울지)
compose의 ports       → Service (어떤 Pod으로 트래픽을 보낼지)
compose의 project     → Namespace + 라벨
```

변환 결과를 그대로 운영에 쓰기보다는 **개념을 익히는 출발점**으로 보는 게 맞습니다. 실제로는 Ingress, 리소스 요청, 프로브, 스토리지 클래스 등을 직접 다듬어야 합니다.

# 5. 로컬에서 쿠버네티스 맛보기

## Docker Desktop (가장 쉬움)

Settings → Kubernetes → Enable Kubernetes 체크. 단일 노드 클러스터가 뜨고 `kubectl` 컨텍스트도 자동으로 잡힙니다.

```bash
kubectl config use-context docker-desktop
kubectl get nodes
```

## kind (Docker 안에 클러스터)

```bash
brew install kind                       # macOS
kind create cluster --name til          # Docker 컨테이너로 노드 생성
kubectl get nodes
kind delete cluster --name til
```

노드 자체가 Docker 컨테이너라 생성·삭제가 빠릅니다. CI에서 쿠버네티스 테스트를 돌릴 때 많이 씁니다.

## minikube

```bash
brew install minikube
minikube start
minikube dashboard      # 웹 대시보드
minikube stop
```

## 첫 배포 흐름

```bash
kubectl create deployment web --image=nginx:alpine
kubectl scale deployment web --replicas=3
kubectl expose deployment web --port=80 --type=NodePort
kubectl get pods,svc
kubectl logs -l app=web --tail 20
kubectl port-forward deployment/web 8080:80
kubectl delete deployment web
```

명령형으로 익힌 다음, 실제로는 YAML 매니페스트를 `kubectl apply -f`로 적용하는 선언형으로 옮겨 갑니다.

# 6. 그 다음에 만나게 될 것들

쿠버네티스에 발을 들이면 이런 도구들이 따라옵니다. 이름만이라도 알아두면 길을 잃지 않습니다.

| 분류 | 도구 | 역할 |
|---|---|---|
| 패키징 | **Helm** | 매니페스트를 템플릿화한 "패키지 매니저" |
| 설정 관리 | **Kustomize** | 환경별 오버레이 (kubectl 내장) |
| 배포 자동화 | **Argo CD**, Flux | git 저장소 상태를 클러스터에 동기화 (GitOps) |
| 인그레스 | ingress-nginx, **Traefik** | 외부 트래픽 라우팅 |
| 인증서 | cert-manager | TLS 인증서 자동 발급·갱신 |
| 관측 | Prometheus, Grafana, Loki | 메트릭·로그 |
| 로컬 개발 | Skaffold, Tilt | 코드 변경 → 클러스터 반영 루프 |

# 7. 언제 넘어가야 할까

```
Compose로 충분한 신호
  - 서버 1대로 트래픽을 감당함
  - 배포가 하루 몇 번 수준이고 짧은 다운타임이 허용됨
  - 운영 인력이 1~2명

오케스트레이터가 필요한 신호
  - 서버를 여러 대 쓰기 시작했고 수동 배치가 힘들어짐
  - 다운타임이 곧 매출 손실
  - 트래픽 변동이 커서 자동 스케일링이 필요
  - 여러 팀이 같은 인프라를 공유
  - 이미 클라우드 관리형 k8s를 쓰는 조직에 합류
```

중간 단계도 있습니다.

```
Compose → (관리형 컨테이너 서비스: Cloud Run, ECS Fargate) → Kubernetes
```

서버 관리 부담만 덜고 싶다면 관리형 컨테이너 서비스가 쿠버네티스보다 훨씬 간단합니다. 이 경로를 먼저 검토해 보는 것을 권합니다.

## 정리

- Compose는 **한 호스트** 기준. 여러 서버 분산, 자동 복구, 롤링 업데이트는 오케스트레이터의 영역
- `docker compose up --scale`은 같은 서버 안에서만 복제본을 늘림
- Swarm은 Compose 문법을 거의 그대로 쓰는 내장 오케스트레이터, Kubernetes는 사실상 표준
- 개념 대응: service→Deployment, ports→Service, environment→ConfigMap, secrets→Secret, volumes→PVC, healthcheck→liveness/readiness probe
- `docker compose bridge convert`로 compose 파일을 k8s 매니페스트로 변환해 보면 대응 관계가 눈에 들어옴
- 로컬 실습은 Docker Desktop 내장 k8s, kind, minikube 중 아무거나
- **필요해지기 전에 넘어가지 말 것.** 중간 단계로 Cloud Run·ECS 같은 관리형 서비스도 있음
