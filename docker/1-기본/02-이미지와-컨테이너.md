# 이미지와 컨테이너 - 레이어로 이해하는 도커

## 들어가며

Docker를 쓰다 보면 이런 의문이 생깁니다.

```
- 이미지 3개를 받았는데 왜 디스크는 그만큼 안 늘어나지?
- 같은 Dockerfile을 두 번 빌드했는데 왜 두 번째는 1초만에 끝나지?
- docker images에서 지웠는데 왜 용량이 그대로지?
- latest 태그는 뭐가 "최신"이라는 거지?
```

전부 **레이어(layer)** 구조를 이해하면 풀립니다. 이 문서는 이미지 내부 구조와 컨테이너의 생애주기를 다룹니다.

# 1. 이미지는 레이어의 쌓임이다

## 레이어 구조

이미지는 하나의 큰 파일이 아니라, **읽기 전용 레이어를 차곡차곡 쌓은 것**입니다.

```
Dockerfile                          만들어지는 레이어
─────────────────────────────────   ──────────────────────────
FROM node:22-alpine              →  (베이스 이미지 레이어들)
WORKDIR /app                     →  (메타데이터만, 크기 0)
COPY package.json ./             →  레이어 A: package.json 추가
RUN npm install                  →  레이어 B: node_modules 추가
COPY . .                         →  레이어 C: 소스 코드 추가
CMD ["node", "server.js"]        →  (메타데이터만, 크기 0)
```

실제로 레이어 개수를 볼 수 있습니다.

```bash
docker image inspect alpine:3.22 --format '{{len .RootFS.Layers}} layers'
# 1 layers

docker image inspect nginx:1.29-alpine --format '{{len .RootFS.Layers}} layers'
# 8 layers
```

## 유니온 파일시스템

여러 레이어를 겹쳐서 하나의 파일시스템처럼 보이게 하는 기술이 **유니온 파일시스템**입니다. 요즘 Docker의 기본 드라이버는 `overlayfs`입니다.

```bash
docker info --format '{{.Driver}}'
# overlayfs
```

```
컨테이너가 보는 파일시스템
┌──────────────────────────────────┐
│ 쓰기 가능 레이어 (컨테이너 레이어) │ ← 컨테이너마다 하나씩, 삭제 시 사라짐
├──────────────────────────────────┤
│ 레이어 C: 소스 코드               │ ┐
├──────────────────────────────────┤ │
│ 레이어 B: node_modules           │ │ 읽기 전용
├──────────────────────────────────┤ │ (여러 컨테이너가 공유)
│ 레이어 A: package.json           │ │
├──────────────────────────────────┤ │
│ 베이스: node:22-alpine           │ ┘
└──────────────────────────────────┘
```

**Copy-on-Write(CoW)**: 컨테이너가 아래 레이어의 파일을 수정하면, 그 파일을 쓰기 가능 레이어로 복사한 뒤 수정합니다. 원본 레이어는 그대로입니다. 그래서 같은 이미지로 컨테이너를 10개 띄워도 디스크는 거의 늘지 않습니다.

## 레이어는 공유된다

`docker system df -v`로 공유 크기를 직접 볼 수 있습니다.

```bash
docker system df -v
```

```
REPOSITORY     TAG      IMAGE ID       SIZE      SHARED SIZE   UNIQUE SIZE
tilchk-ign2    latest   38bbf9d3b4ef   13.4MB    9.208MB       4.145MB
tilchk-ign1    latest   9b152b4ac699   97.3MB    9.208MB       88.04MB
```

두 이미지 모두 `SIZE`는 각각 13.4MB, 97.3MB지만 그중 9.2MB는 **공유 레이어**라서 디스크에는 한 번만 저장됩니다. `docker images`의 SIZE를 단순히 더하면 실제 사용량보다 훨씬 크게 나옵니다.

# 2. 태그는 이미지의 별명이다

```bash
docker tag alpine:3.22 myalpine:v1
docker tag alpine:3.22 myalpine:latest

docker images --format '{{.Repository}}:{{.Tag}} {{.ID}}'
```

```
alpine:3.22             14358309a308
myalpine:latest         14358309a308
myalpine:v1             14358309a308
```

IMAGE ID가 전부 같습니다. **태그는 이미지를 가리키는 포인터**일 뿐이고, 새 이미지가 복제된 게 아닙니다. git의 브랜치나 태그와 같은 개념입니다.

## latest의 함정

```
latest = "가장 최신"이라는 뜻이 아니다
       = 태그를 생략했을 때 붙는 기본 이름일 뿐

nginx:latest 를 오늘 pull 한 것과 한 달 뒤 pull 한 것은 다른 이미지일 수 있음
→ 프로덕션에서는 반드시 명시적 태그(nginx:1.29-alpine)나 다이제스트 사용
```

## 다이제스트로 완전히 고정하기

```bash
docker pull alpine:3.22
# Digest: sha256:14358309a308569c32bdc37e2e0e9694be33a9d99e68afb0f5ff33cc1f695dce

# 태그가 바뀌어도 절대 변하지 않는 참조
docker pull alpine@sha256:14358309a308569c32bdc37e2e0e9694be33a9d99e68afb0f5ff33cc1f695dce
```

다이제스트는 이미지 내용의 해시라서, 같은 다이제스트면 바이트 단위로 같은 이미지가 보장됩니다.

# 3. 이미지 살펴보기

## pull - 이미지 받기

```bash
docker pull nginx:1.29-alpine
```

```
1.29-alpine: Pulling from library/nginx
a0bf7fcddd4c: Download complete     ← 레이어별로 병렬 다운로드
6da8c403a7d9: Download complete
Digest: sha256:5616878291a2eed594aee8db4dade5878cf7edcb475e59193904b198d9b830de
Status: Downloaded newer image for nginx:1.29-alpine
```

이미 있는 레이어는 다시 받지 않고 `Already exists`로 표시됩니다.

## history - 어떻게 만들어졌는지 보기

```bash
docker history nginx:1.29-alpine --format 'table {{.CreatedBy}}\t{{.Size}}'
```

```
CREATED BY                                                  SIZE
RUN /bin/sh -c set -x  && apkArch="$(cat /etc/apk/arch)"...  79.1MB
ENV NJS_VERSION=0.9.6                                        0B
CMD ["nginx" "-g" "daemon off;"]                             0B
ENTRYPOINT ["/docker-entrypoint.sh"]                         0B
COPY docker-entrypoint.sh / # buildkit                       1.62kB
LABEL maintainer=NGINX Docker Maintainers                    0B
```

남이 만든 이미지가 무엇을 했는지 역추적할 수 있습니다. `ENV`, `CMD`, `LABEL` 같은 메타데이터 명령은 크기가 0입니다.

> 이미지에 비밀번호나 토큰을 `ENV`로 넣으면 `docker history`로 그대로 노출됩니다. 시크릿은 절대 이미지에 넣지 않습니다.

## inspect - 상세 정보

```bash
docker image inspect nginx:1.29-alpine --format '{{.Config.Cmd}} / {{.Config.ExposedPorts}}'
# [nginx -g daemon off;] / map[80/tcp:{}]

docker image inspect nginx:1.29-alpine --format '{{.Os}}/{{.Architecture}}'
# linux/arm64
```

`--format`에 Go 템플릿을 쓸 수 있고, `docker inspect 이름 | jq`로 전체 JSON을 볼 수도 있습니다.

# 4. 컨테이너의 생애주기

```
            docker create              docker start
  이미지 ───────────────► created ──────────────────► running
                                                       │  │
                            docker stop / 프로세스 종료 │  │ docker pause
                                                       ▼  ▼
                                                   exited  paused
                                                       │
                                            docker start │ (재시작 가능)
                                                       ▼
                                                    running
                                                       │
                                              docker rm │ (정지 상태에서만)
                                                       ▼
                                                     삭제됨
```

`docker run`은 사실 `create` + `start`를 합친 명령입니다.

## 상태 확인

```bash
docker run --name job alpine:3.22 sh -c 'echo 작업완료; exit 3'
# 작업완료

docker ps -a --filter name=job --format '{{.Names}} | {{.Status}}'
# job | Exited (3) Less than a second ago
```

- `docker ps` : 실행 중인 컨테이너만
- `docker ps -a` : 종료된 것까지 전부

종료된 컨테이너는 **사라지지 않고 남아 있습니다**. 로그와 파일시스템이 그대로라서 디버깅에 쓸 수 있고, 대신 정리하지 않으면 계속 쌓입니다.

```bash
docker start job     # 다시 실행 가능
docker rm job        # 완전히 삭제
```

## 재시작 정책

```bash
docker run -d --name crash --restart on-failure:3 alpine:3.22 sh -c 'sleep 1; exit 1'

# 8초 후 확인
docker inspect -f '{{.State.Status}} restarts={{.RestartCount}} exit={{.State.ExitCode}}' crash
# exited restarts=3 exit=1
```

| 정책 | 동작 |
|---|---|
| `no` | 기본값, 재시작 안 함 |
| `on-failure[:횟수]` | 0이 아닌 종료 코드일 때만 재시작 |
| `always` | 항상 재시작, 데몬 재시작 시에도 |
| `unless-stopped` | `always`와 같지만 사용자가 직접 stop한 경우는 제외 |

# 5. 디스크 정리

## 현재 사용량 보기

```bash
docker system df
```

```
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          33        7         6.029GB   4.39GB (72%)
Containers      9         7         356.4kB   8.192kB (2%)
Local Volumes   5         1         213.7MB   213.7MB (100%)
Build Cache     124       0         4.975GB   4.499GB
```

`RECLAIMABLE`이 회수 가능한 용량입니다. 위 예시에서는 빌드 캐시만 4.5GB입니다. Docker를 오래 쓰면 수십 GB가 쌓이는 일이 흔합니다.

## 단계별 정리

```bash
# 1. 중지된 컨테이너만 삭제
docker container prune

# 2. 어떤 컨테이너도 안 쓰는 이미지 중 태그 없는 것(dangling)만
docker image prune

# 3. 태그가 있어도 안 쓰는 이미지까지 전부 (주의)
docker image prune -a

# 4. 빌드 캐시
docker builder prune

# 5. 볼륨 (데이터가 날아감, 가장 위험)
docker volume prune
```

전체를 한 번에 정리하는 명령도 있습니다.

```bash
docker system prune        # 컨테이너 + 네트워크 + dangling 이미지 + 빌드 캐시
docker system prune -a --volumes   # 볼륨까지 전부 (매우 위험)
```

> `--volumes`를 붙이면 DB 데이터 볼륨도 지워집니다. 로컬 개발 DB가 통째로 날아갈 수 있으니, 정리 전에 `docker volume ls`로 무엇이 지워질지 먼저 확인하세요.

## 개별 삭제

```bash
docker rm 컨테이너이름         # 컨테이너 (중지 상태)
docker rm -f 컨테이너이름      # 강제 (실행 중이어도)
docker rmi 이미지이름          # 이미지
docker volume rm 볼륨이름      # 볼륨
```

이미지가 안 지워질 때는 대부분 그 이미지를 쓰는 컨테이너(종료된 것 포함)가 남아 있어서입니다.

## 정리

- 이미지는 **읽기 전용 레이어의 스택**, 컨테이너는 그 위에 얹힌 **쓰기 가능 레이어 + 프로세스**
- overlayfs가 레이어를 겹쳐 하나의 파일시스템으로 보여주고, 수정은 Copy-on-Write로 처리
- 레이어는 이미지 간에 공유된다 (`docker system df -v`의 SHARED SIZE)
- 태그는 이미지 ID를 가리키는 별명, `latest`는 "최신"이 아니라 기본 태그일 뿐
- 재현성이 중요하면 태그 대신 **다이제스트(sha256:...)** 로 고정
- `docker history`로 이미지 제작 과정이 다 보인다 → 시크릿을 이미지에 넣지 말 것
- 종료된 컨테이너는 자동으로 사라지지 않는다 (`--rm`을 쓰거나 주기적으로 prune)
- `docker system df`로 낭비를 확인하고, prune은 범위를 좁혀서 실행
