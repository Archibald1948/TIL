# 볼륨과 데이터 - 컨테이너가 죽어도 남아야 하는 것들

## 들어가며

컨테이너의 파일시스템은 **휘발성**입니다.

```bash
docker run --rm alpine:3.22 sh -c 'echo hi > /data.txt; cat /data.txt'
# hi

docker run --rm alpine:3.22 cat /data.txt
# cat: can't open '/data.txt': No such file or directory
```

컨테이너를 지우면 그 안에 쓴 데이터도 같이 사라집니다. DB 컨테이너를 지웠더니 데이터가 전부 날아가는 사고가 여기서 나옵니다. 데이터를 컨테이너 **바깥**에 두는 방법이 필요합니다.

# 1. 데이터를 컨테이너 밖에 두는 3가지 방법

```
 호스트                                   컨테이너
┌────────────────────────────────┐      ┌────────────────────┐
│ /var/lib/docker/volumes/...    │◄────►│ /var/lib/postgresql │  ① volume
│ (도커가 관리)                   │      └────────────────────┘
├────────────────────────────────┤
│ /Users/me/project/src          │◄────►│ /app                │  ② bind mount
│ (내가 관리하는 임의 경로)        │      └────────────────────┘
├────────────────────────────────┤
│ (메모리)                        │◄────►│ /cache              │  ③ tmpfs
└────────────────────────────────┘      └────────────────────┘
```

| 방식 | 저장 위치 | 주 용도 |
|---|---|---|
| **volume** | Docker가 관리하는 영역 | DB 데이터 등 영속 데이터 (운영 권장) |
| **bind mount** | 호스트의 특정 경로 | 개발 중 소스 코드 실시간 반영, 설정 파일 주입 |
| **tmpfs** | 호스트 메모리 | 캐시, 임시 파일, 디스크에 남기면 안 되는 값 |

# 2. 볼륨 (named volume)

## 만들고 쓰기

```bash
docker volume create appdata

docker run --rm -v appdata:/data alpine:3.22 sh -c 'echo "저장된 데이터" > /data/note.txt'
docker run --rm -v appdata:/data alpine:3.22 cat /data/note.txt
# 저장된 데이터
```

컨테이너는 두 번 다 새로 만들어졌지만 데이터는 남아 있습니다.

```bash
docker volume inspect appdata --format '{{.Name}} | {{.Driver}} | {{.Mountpoint}}'
# appdata | local | /var/lib/docker/volumes/appdata/_data
```

> `Mountpoint` 경로는 **리눅스 VM 안의 경로**입니다. macOS에서 Finder로 열 수 없습니다. 볼륨 내용을 보려면 컨테이너를 통해 접근해야 합니다.

## 볼륨 안을 들여다보기

```bash
docker run --rm -v appdata:/data alpine:3.22 ls -la /data
```

## 실전 예시 - DB 데이터 보존

```bash
docker run -d --name db \
  -e POSTGRES_PASSWORD=devpass \
  -v pgdata:/var/lib/postgresql/data \
  postgres:17-alpine

docker rm -f db           # 컨테이너를 지워도
docker run -d --name db \ # 같은 볼륨을 붙이면 데이터 그대로
  -e POSTGRES_PASSWORD=devpass \
  -v pgdata:/var/lib/postgresql/data \
  postgres:17-alpine
```

## 볼륨은 빈 디렉터리에 기존 내용을 복사한다

```bash
docker run --rm -v newvol:/usr/share/nginx/html nginx:1.29-alpine ls /usr/share/nginx/html
# 50x.html
# index.html
```

**빈 볼륨**을 마운트하면 이미지에 원래 있던 파일이 볼륨으로 복사됩니다. 반면 bind mount는 그냥 덮어씁니다.

```bash
mkdir empty
docker run --rm -v "$PWD/empty:/usr/share/nginx/html" nginx:1.29-alpine sh -c 'ls -A /usr/share/nginx/html | wc -l'
# 0     ← 이미지의 파일이 가려짐
```

이 차이 때문에 "볼륨 붙였더니 파일이 사라졌다"는 혼란이 자주 생깁니다.

## 익명 볼륨

```bash
docker run -d --name anon -v /data alpine:3.22 sleep 30
docker inspect -f '{{range .Mounts}}{{.Type}} {{.Name}} -> {{.Destination}}{{end}}' anon
# volume bdd26c07dc533b885ab65bfa04cdd4b36ab52486fbd3f8edac2bab6573fed46e -> /data
```

이름을 주지 않으면 해시 이름의 볼륨이 생깁니다. 관리가 어렵고 쓰레기로 남기 쉬우니 가능하면 이름을 붙이세요.

# 3. bind mount

호스트의 특정 디렉터리를 컨테이너에 그대로 연결합니다.

```bash
mkdir -p bindtest && echo "호스트 파일" > bindtest/host.txt

docker run --rm -v "$PWD/bindtest:/app" alpine:3.22 sh -c \
  'cat /app/host.txt; echo "컨테이너가 씀" > /app/from-container.txt'
# 호스트 파일

ls bindtest
# from-container.txt   host.txt
```

양방향으로 즉시 반영됩니다. **개발 환경에서 소스 코드를 마운트하는 게 대표적인 용법**입니다.

```bash
# 코드를 고치면 컨테이너 안에서 즉시 반영 (nodemon 등과 함께)
docker run --rm -it \
  -v "$PWD:/app" \
  -v /app/node_modules \
  -w /app -p 3000:3000 \
  node:22-alpine npm run dev
```

```
-v "$PWD:/app"          호스트 소스 → 컨테이너
-v /app/node_modules    node_modules는 익명 볼륨으로 가려서
                        호스트의 (OS가 다를 수 있는) node_modules가 덮어쓰지 않게 함
```

## 읽기 전용 마운트

```bash
docker run --rm -v "$PWD/bindtest:/app:ro" alpine:3.22 sh -c 'echo x > /app/no.txt'
# sh: can't create /app/no.txt: Read-only file system
```

설정 파일을 주입할 때는 `:ro`를 붙이는 습관이 좋습니다.

```bash
docker run -d -p 8080:80 \
  -v "$PWD/nginx.conf:/etc/nginx/nginx.conf:ro" \
  nginx:1.29-alpine
```

## --mount 문법

`-v`의 긴 버전으로, 의미가 명확해서 스크립트에서는 이쪽이 권장됩니다.

```bash
docker run --rm \
  --mount type=bind,source="$PWD"/bindtest,target=/app,readonly \
  alpine:3.22 ls /app

docker run --rm \
  --mount type=volume,source=appdata,target=/data \
  alpine:3.22 ls /data
```

# 4. 권한 문제 (UID/GID)

컨테이너는 기본적으로 root로 실행되므로, bind mount에 파일을 만들면 **리눅스에서는 root 소유**가 됩니다.

```bash
# 리눅스 호스트에서
docker run --rm -v "$PWD:/app" alpine:3.22 touch /app/created.txt
ls -l created.txt
# -rw-r--r-- 1 root root 0 ... created.txt   ← 내 계정으로 수정/삭제가 안 됨
```

macOS에서는 Docker Desktop이 파일 공유 계층에서 소유자를 호스트 사용자로 매핑해주기 때문에 이 문제가 드러나지 않습니다.

```bash
# macOS에서 실행한 결과
docker run --rm -v "$PWD/bindtest:/app" alpine:3.22 ls -l /app
# -rw-r--r--    1 root     root            20 ... from-container.txt   ← 컨테이너에서는 root

ls -l bindtest/from-container.txt
# -rw-r--r--  1 gimseongsu  wheel  20 ... bindtest/from-container.txt  ← 호스트에서는 내 계정
```

## 해결책: 실행 UID 지정

```bash
docker run --rm --user 1000:1000 -v "$PWD/bindtest:/app" alpine:3.22 sh -c 'id; touch /app/user1000.txt'
# uid=1000 gid=1000 groups=1000

# 리눅스에서는 현재 사용자로 실행
docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/app" -w /app node:22-alpine npm install
```

Dockerfile에서 아예 비root 유저를 지정하는 방법도 있습니다. [2-이미지-빌드/04. 이미지 경량화와 보안](../2-이미지-빌드/04-이미지-경량화와-보안.md)에서 다룹니다.

# 5. tmpfs

디스크가 아니라 **메모리**에 올리는 마운트입니다. 컨테이너가 죽으면 즉시 사라집니다.

```bash
docker run --rm --tmpfs /cache:size=10m alpine:3.22 sh -c 'df -h /cache | tail -1; touch /cache/a; ls /cache'
```

```
tmpfs                    10.0M         0     10.0M   0% /cache
a
```

| 쓰기 좋은 경우 | 이유 |
|---|---|
| 세션/임시 파일 | 빠르고, 디스크에 흔적이 안 남음 |
| 시크릿을 파일로 받아야 할 때 | 디스크에 평문으로 남지 않음 |
| 빌드 산출물 캐시 | I/O가 빠름 |

# 6. 백업과 복원

볼륨은 Docker 내부 경로에 있어서 직접 복사하기 어렵습니다. **임시 컨테이너에 볼륨과 호스트 디렉터리를 동시에 마운트**해서 tar로 옮기는 게 표준 방법입니다.

```bash
# 백업: 볼륨(appdata) → 현재 디렉터리의 tar.gz
docker run --rm \
  -v appdata:/data \
  -v "$PWD:/backup" \
  alpine:3.22 tar czf /backup/vol-backup.tar.gz -C /data .

ls -lh vol-backup.tar.gz
# 155B vol-backup.tar.gz
```

```bash
# 복원: tar.gz → 새 볼륨(appdata-restored)
docker volume create appdata-restored
docker run --rm \
  -v appdata-restored:/data \
  -v "$PWD:/backup" \
  alpine:3.22 tar xzf /backup/vol-backup.tar.gz -C /data

docker run --rm -v appdata-restored:/data alpine:3.22 ls /data
```

DB라면 파일을 통째로 복사하는 것보다 **DB 자체의 덤프 기능**이 안전합니다.

```bash
docker exec db pg_dump -U postgres myapp > dump.sql
cat dump.sql | docker exec -i db psql -U postgres myapp
```

# 7. 볼륨 관리

```bash
docker volume ls
docker volume inspect 볼륨이름
docker volume rm 볼륨이름
docker volume prune          # 어떤 컨테이너도 안 쓰는 볼륨 전부 삭제
```

```bash
# 어떤 컨테이너가 이 볼륨을 쓰는지 찾기
docker ps -a --filter volume=appdata --format '{{.Names}}'
```

> `docker volume prune`과 `docker system prune --volumes`는 **데이터를 실제로 삭제**합니다. 로컬 DB 볼륨이 지워지면 복구할 수 없으니, 실행 전에 `docker volume ls`로 목록을 확인하세요.

## 정리

- 컨테이너 파일시스템은 휘발성 → 남겨야 할 데이터는 반드시 바깥에 저장
- **volume**: Docker가 관리, 운영 데이터(DB)에 적합. 빈 볼륨은 이미지의 기존 파일을 복사해온다
- **bind mount**: 호스트 경로 직결, 개발 중 소스 마운트와 설정 주입에 적합. 이미지의 파일을 가린다
- **tmpfs**: 메모리에만 존재, 임시 파일과 시크릿에 적합
- 설정 파일 주입은 `:ro`로 읽기 전용
- 리눅스에서는 bind mount 파일이 root 소유가 되는 문제가 있다 → `--user $(id -u):$(id -g)`
- 볼륨 백업/복원은 임시 컨테이너 + tar 조합, DB는 덤프 사용
- prune 계열 명령은 데이터를 지운다. 범위를 확인하고 실행할 것
