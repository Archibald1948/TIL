# 자주 쓰는 명령어 - 실무에서 손에 붙는 것들

## 들어가며

Docker 명령어는 수십 개지만, 실제로 매일 쓰는 건 10개 남짓입니다. 이 문서는 그 10개와 **문제가 생겼을 때 원인을 찾아가는 순서**를 다룹니다.

```
컨테이너가 안 뜬다
  → docker ps -a 로 상태 확인
  → docker logs 로 에러 메시지 확인
  → docker inspect 로 설정 확인
  → docker exec 로 안에 들어가서 확인
```

이 흐름만 익혀도 대부분의 문제는 혼자 해결됩니다.

# 1. docker run 옵션

가장 많이 쓰는 명령이고, 옵션 조합이 전부입니다.

```bash
docker run [옵션] 이미지[:태그] [명령] [인자...]
```

| 옵션 | 뜻 | 예시 |
|---|---|---|
| `-d` | 백그라운드 실행 | `-d` |
| `-it` | 대화형 터미널 | `-it ... sh` |
| `--rm` | 종료 시 컨테이너 자동 삭제 | `--rm` |
| `--name` | 이름 지정 | `--name web` |
| `-p` | 포트 매핑 (호스트:컨테이너) | `-p 8080:80` |
| `-v` | 볼륨/바인드 마운트 | `-v data:/var/lib/mysql` |
| `-e` | 환경 변수 | `-e NODE_ENV=production` |
| `--env-file` | 환경 변수 파일 | `--env-file .env` |
| `-w` | 작업 디렉터리 | `-w /app` |
| `-u` | 실행 유저 | `-u 1000:1000` |
| `--restart` | 재시작 정책 | `--restart unless-stopped` |
| `--network` | 네트워크 지정 | `--network mynet` |
| `-m`, `--cpus` | 메모리/CPU 제한 | `-m 512m --cpus 1.5` |

## 조합 예시

```bash
# 일회용 도구 실행 (가장 자주 쓰는 패턴)
docker run --rm -it alpine:3.22 sh

# 백그라운드 웹 서버
docker run -d --name web -p 8080:80 --restart unless-stopped nginx:1.29-alpine

# 환경 변수를 넣은 DB
docker run -d --name db \
  -e POSTGRES_PASSWORD=devpass \
  -e POSTGRES_DB=myapp \
  -p 5432:5432 \
  -v pgdata:/var/lib/postgresql/data \
  postgres:17-alpine

# 현재 디렉터리를 마운트해서 일회성 빌드
docker run --rm -v "$PWD:/app" -w /app node:22-alpine npm run build

# 리소스 제한
docker run -d --name limited -m 512m --cpus 1.5 nginx:1.29-alpine
```

## -d와 --rm

```
-d 없이 실행  → 터미널이 컨테이너에 붙어 있음, Ctrl+C로 종료
-d로 실행     → 바로 프롬프트 복귀, docker logs로 출력 확인

--rm 있음     → 종료되는 순간 컨테이너 삭제 (실습/일회성 작업에 필수)
--rm 없음     → Exited 상태로 남음 (로그를 나중에 볼 수 있음)
```

# 2. 상태 확인: ps

```bash
docker ps                    # 실행 중
docker ps -a                 # 전부 (종료된 것 포함)
docker ps -q                 # ID만
docker ps --filter name=web  # 이름으로 필터
docker ps --filter status=exited
```

기본 출력은 너무 넓어서 터미널에서 줄바꿈됩니다. `--format`으로 필요한 것만 봅니다.

```bash
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'
```

```
NAMES   IMAGE               STATUS                  PORTS
web     nginx:1.29-alpine   Up Less than a second   0.0.0.0:18080->80/tcp, [::]:18080->80/tcp
```

자주 쓴다면 셸 alias로 등록해두면 편합니다.

```bash
alias dps="docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'"
```

# 3. 로그: logs

컨테이너가 죽었을 때 **가장 먼저 볼 것**입니다.

```bash
docker logs web              # 전체 로그
docker logs --tail 50 web    # 마지막 50줄
docker logs -f web           # 실시간 추적 (tail -f)
docker logs -t web           # 타임스탬프 포함
docker logs --since 10m web  # 최근 10분
```

```bash
docker logs --tail 3 web
```

```
2026/09/16 03:40:18 [notice] 1#1: start worker process 36
2026/09/16 03:40:18 [notice] 1#1: start worker process 37
192.168.65.1 - - [16/Sep/2026:03:40:18 +0000] "GET / HTTP/1.1" 200 896 "-" "curl/8.7.1" "-"
```

> `docker logs`는 컨테이너의 **표준 출력/표준 에러**를 보여줍니다. 앱이 파일에만 로그를 쓰면 여기에 안 나옵니다. 컨테이너에서는 파일이 아니라 stdout/stderr로 로그를 내보내는 게 원칙입니다.

# 4. 안에 들어가기: exec

실행 중인 컨테이너에서 추가 명령을 실행합니다.

```bash
# 셸 열기 (디버깅의 핵심)
docker exec -it web sh          # alpine 계열
docker exec -it web bash        # debian/ubuntu 계열

# 단발 명령
docker exec web ls /usr/share/nginx/html
docker exec web cat /etc/nginx/nginx.conf
docker exec web env             # 환경 변수 확인
docker exec -u root web sh      # root로 들어가기 (비root 이미지 디버깅)
```

```bash
docker exec web sh -c 'hostname; whoami'
```

```
3c831053c11a
root
```

호스트명이 컨테이너 ID 앞 12자리입니다.

> `docker attach`는 PID 1 프로세스에 직접 붙는 것이라 Ctrl+C로 컨테이너를 죽일 수 있습니다. 디버깅할 때는 `exec`를 쓰세요.

# 5. 상세 정보: inspect

컨테이너/이미지/네트워크/볼륨의 모든 설정을 JSON으로 보여줍니다.

```bash
docker inspect web                           # 전체 JSON
docker inspect -f '{{.State.Status}}' web    # 특정 필드만
docker inspect -f '{{.State.ExitCode}}' web  # 종료 코드
docker inspect -f '{{json .Mounts}}' web | jq
```

```bash
docker inspect -f '{{.State.Status}} | {{.Config.Image}} | restarts={{.RestartCount}}' web
# running | nginx:1.29-alpine | restarts=0
```

## Docker 29에서 바뀐 점

예전 문서에 흔히 나오는 `{{.NetworkSettings.IPAddress}}`는 Docker 29에서 더 이상 동작하지 않습니다.

```bash
docker inspect -f '{{.NetworkSettings.IPAddress}}' web
# template parsing error: ... map has no entry for key "IPAddress"
```

네트워크별 정보 아래에서 찾아야 합니다.

```bash
docker inspect -f '{{.NetworkSettings.Networks.bridge.IPAddress}}' web
# 172.17.0.2
```

# 6. 리소스 사용량: stats, top

```bash
docker stats                  # 실시간 (top처럼)
docker stats --no-stream      # 1회만 출력
```

```bash
docker stats --no-stream --format 'table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}' web
```

```
NAME   CPU %     MEM USAGE / LIMIT
web    0.00%     7.363MiB / 3.827GiB
```

메모리 LIMIT이 호스트 전체(3.827GiB)로 잡혀 있으면 제한이 없다는 뜻입니다. `-m 512m`으로 띄우면 여기에 512MiB로 표시됩니다.

```bash
docker top web     # 컨테이너 안의 프로세스 목록
```

```
UID     PID    PPID   CMD
root    780    757    nginx: master process nginx -g daemon off;
statd   823    780    nginx: worker process
```

# 7. 파일 복사: cp

```bash
docker cp web:/etc/nginx/nginx.conf ./nginx.conf   # 컨테이너 → 호스트
docker cp ./index.html web:/usr/share/nginx/html/  # 호스트 → 컨테이너
```

설정 파일을 꺼내서 수정한 다음 마운트하는 식으로 자주 씁니다. 다만 `cp`로 컨테이너 안을 고치는 건 일회성입니다. 컨테이너를 지우면 사라지므로, 영구적인 변경은 이미지나 볼륨으로 해야 합니다.

# 8. 생애주기 명령

```bash
docker start web       # 정지된 컨테이너 재시작
docker stop web        # SIGTERM 전송 후, 기본 10초 뒤 SIGKILL
docker stop -t 30 web  # 30초까지 기다림
docker restart web
docker kill web        # 즉시 SIGKILL
docker pause/unpause web
docker rename web web2
```

`stop`이 어떻게 동작하는지는 실제로 확인할 수 있습니다.

```bash
docker run -d --name trap alpine:3.22 \
  sh -c 'trap "echo SIGTERM 받음; exit 0" TERM; echo 시작; while :; do sleep 0.5; done'

docker stop trap
docker logs trap
```

```
시작
SIGTERM 받음
```

```bash
docker inspect -f '{{.State.ExitCode}}' trap
# 0
```

SIGTERM을 잡아서 정상 종료하면 종료 코드가 0입니다. 신호를 무시하면 타임아웃 후 SIGKILL을 받고 **137**(128+9)로 끝납니다. 앱에서 graceful shutdown을 구현해야 하는 이유입니다.

# 9. 디버깅 흐름

컨테이너가 계속 죽을 때의 순서입니다.

```bash
# 1. 상태와 종료 코드 확인
docker ps -a --filter name=myapp --format '{{.Names}} | {{.Status}}'
# myapp | Exited (1) 3 seconds ago

# 2. 로그 확인 (원인의 90%는 여기서 나옴)
docker logs myapp

# 3. 설정이 의도대로 들어갔는지 확인
docker inspect -f '{{.Config.Env}}' myapp
docker inspect -f '{{json .Mounts}}' myapp

# 4. 이미지 자체는 정상인지, 셸로 직접 들어가서 확인
docker run --rm -it --entrypoint sh myapp-image
#   → 안에서 파일 위치, 권한, 명령을 직접 실행해보기

# 5. 네트워크 문제라면 같은 네트워크의 임시 컨테이너로 확인
docker run --rm --network mynet alpine:3.22 wget -qO- http://myapp:3000
```

## 자주 만나는 종료 코드

| 코드 | 의미 |
|---|---|
| 0 | 정상 종료 |
| 1 | 앱 에러 (대부분 로그에 원인이 있음) |
| 125 | docker run 자체 실패 (잘못된 옵션) |
| 126 | 명령을 실행할 수 없음 (권한 없음) |
| 127 | 명령을 찾을 수 없음 (경로 오타, 셸 없는 이미지) |
| 137 | SIGKILL (OOM 또는 stop 타임아웃) |
| 143 | SIGTERM으로 종료 |

특히 **137**은 메모리 부족(OOM)일 때가 많습니다.

```bash
docker inspect -f '{{.State.OOMKilled}}' myapp
# true 면 메모리 부족
```

## 정리

- `docker run`은 옵션 조합이 전부다: `-d --name -p -v -e --rm -it`
- `--format`으로 출력을 다듬으면 `ps`, `inspect`가 훨씬 쓸 만해진다
- 문제가 생기면 **ps -a → logs → inspect → exec** 순서로 좁혀간다
- 로그는 stdout/stderr로 내보내야 `docker logs`로 볼 수 있다
- `docker exec -it 이름 sh`가 디버깅의 기본, `attach`는 피할 것
- Docker 29부터 `.NetworkSettings.IPAddress`는 없어졌고 `.Networks.<네트워크>.IPAddress`를 써야 한다
- 종료 코드 137은 SIGKILL(대부분 OOM), 143은 SIGTERM
