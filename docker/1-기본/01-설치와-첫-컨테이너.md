# 설치와 첫 컨테이너 - "제 컴퓨터에서는 되는데요"의 끝

## 들어가며

팀 프로젝트를 하다 보면 이런 일이 반복됩니다.

```
상황 1: 새 팀원이 합류
- Node 20을 쓰는데 팀원은 Node 18이 깔려 있음
- PostgreSQL 16이 필요한데 로컬엔 14가 있음
- README의 "설치 방법" 12단계를 따라 해도 어딘가에서 막힘
- 환경 세팅에만 하루 소요

상황 2: 배포
- 로컬에서는 잘 되는데 서버에서 죽음
- 서버의 OpenSSL 버전이 다름
- "제 컴퓨터에서는 되는데요..."

상황 3: 여러 프로젝트 동시 작업
- A 프로젝트는 MySQL 5.7, B 프로젝트는 MySQL 8
- 한 컴퓨터에 둘 다 설치하려니 포트와 설정이 충돌
```

**Docker**는 애플리케이션과 그 실행 환경(OS 라이브러리, 런타임, 설정)을 통째로 묶어서 어디서든 똑같이 실행되게 만듭니다. 이 문서에서는 Docker를 설치하고 첫 컨테이너를 띄워봅니다.

# 1. 컨테이너란 무엇인가

## 한 줄 정의

```
컨테이너 = 호스트 커널을 공유하면서, 격리된 파일시스템/네트워크/프로세스 공간에서 실행되는 프로세스
```

중요한 건 **컨테이너는 가상 머신이 아니라 그냥 프로세스**라는 점입니다. 리눅스 커널의 두 기능이 핵심입니다.

| 커널 기능 | 역할 |
|---|---|
| namespace | 격리 - 프로세스 목록, 네트워크, 마운트, 호스트명을 따로 보이게 함 |
| cgroup | 제한 - CPU, 메모리, I/O 사용량을 제한 |

컨테이너 안에서 `ps`를 찍으면 자기 프로세스만 보입니다. 직접 확인해봅시다 (뒤에서 설치 후 실행).

```bash
docker run --rm alpine:3.22 sh -c 'ps -o pid,comm'
```

```
PID   COMMAND
    1 sh
    6 ps
```

호스트에는 수백 개의 프로세스가 떠 있지만, 컨테이너 안에서는 자기 자신이 **PID 1**입니다. 이게 namespace 격리입니다.

# 2. 가상 머신과 뭐가 다른가

```
가상 머신 (VM)                        컨테이너
┌─────────────────────────┐          ┌─────────────────────────┐
│  앱 A   │  앱 B         │          │  앱 A   │  앱 B         │
├─────────┼───────────────┤          ├─────────┼───────────────┤
│ 게스트  │ 게스트        │          │ 라이브러리만 (수십 MB)  │
│ OS      │ OS            │          ├─────────────────────────┤
│ (수 GB) │ (수 GB)       │          │  Docker Engine          │
├─────────┴───────────────┤          ├─────────────────────────┤
│  하이퍼바이저           │          │  호스트 OS (커널 공유)  │
├─────────────────────────┤          ├─────────────────────────┤
│  호스트 OS              │          │  하드웨어               │
├─────────────────────────┤          └─────────────────────────┘
│  하드웨어               │
└─────────────────────────┘
```

| 비교 | 가상 머신 | 컨테이너 |
|---|---|---|
| 격리 수준 | 커널까지 완전 분리 | 커널 공유, 프로세스 수준 격리 |
| 부팅 시간 | 수십 초 ~ 분 | 밀리초 ~ 초 |
| 크기 | 수 GB | 수십 MB ~ 수백 MB |
| 오버헤드 | 게스트 OS 전체가 돌아감 | 프로세스 하나만큼 |
| 보안 경계 | 강함 | VM보다 약함 (커널 공유) |

컨테이너가 가벼운 이유는 **게스트 OS를 통째로 돌리지 않기 때문**입니다. Ubuntu 이미지 안에 들어 있는 건 커널이 아니라 Ubuntu의 파일시스템(라이브러리, 바이너리)뿐이고, 커널은 호스트 것을 그대로 씁니다.

> macOS와 Windows에는 리눅스 커널이 없습니다. 그래서 Docker Desktop은 내부적으로 가벼운 리눅스 VM을 하나 띄우고, 그 안에서 컨테이너를 실행합니다. "Mac에서는 컨테이너가 VM 위에서 돈다"는 말이 이 뜻입니다.

# 3. 설치

## macOS / Windows - Docker Desktop

가장 간단한 방법입니다. GUI 대시보드, Compose, Kubernetes, buildx가 전부 포함되어 있습니다.

```bash
# macOS - Homebrew
brew install --cask docker

# 또는 https://www.docker.com/products/docker-desktop 에서 dmg 다운로드
# Apple Silicon / Intel 빌드가 따로 있으니 확인할 것
```

설치 후 Docker Desktop 앱을 **실행해야** 데몬이 뜹니다. 터미널만 열어서는 동작하지 않습니다.

```bash
docker version
```

```
Client: 29.1.5
Server: 29.1.5
```

`Server`가 안 보이고 `Cannot connect to the Docker daemon` 에러가 나오면 Docker Desktop이 실행 중인지 확인합니다.

> Docker Desktop은 개인/소규모 사용은 무료지만, 일정 규모 이상 기업에서는 유료 구독이 필요합니다. 라이선스 조건은 회사 정책을 확인하세요.

## Linux - Docker Engine

리눅스는 VM이 필요 없어서 Engine만 설치하면 됩니다.

```bash
# Ubuntu - 공식 설치 스크립트 (편의용, 프로덕션은 apt 저장소 권장)
curl -fsSL https://get.docker.com | sh

# sudo 없이 쓰기 (재로그인 필요)
sudo usermod -aG docker $USER

# 데몬 자동 시작
sudo systemctl enable --now docker

docker run --rm hello-world
```

> `docker` 그룹에 사용자를 넣는 것은 사실상 root 권한을 주는 것과 같습니다. 개인 개발 머신에서는 편하지만, 공용 서버라면 rootless 모드를 검토하세요.

## macOS 대안 - Colima

Docker Desktop 라이선스가 걸리거나 더 가벼운 게 필요하면 Colima를 쓸 수 있습니다. CLI만 제공하고 리눅스 VM을 직접 관리합니다.

```bash
brew install colima docker
colima start --cpu 4 --memory 8

docker ps   # colima가 띄운 데몬에 연결됨
```

출력 자체가 동작 원리를 설명합니다.

```
1. docker CLI가 Docker 데몬에 요청 (CLI는 그냥 클라이언트)
2. 데몬이 로컬에 이미지가 없으면 레지스트리(Docker Hub)에서 pull
3. 이미지로 컨테이너를 만들어 실행
4. 컨테이너의 표준 출력을 터미널로 전달
```

## Alpine 리눅스에서 명령 실행하기

```bash
docker run --rm alpine:3.22 echo "안녕 컨테이너"
```

```
안녕 컨테이너
```

방금 13MB짜리 리눅스를 받아서, 그 안에서 `echo`를 실행하고, 컨테이너를 지웠습니다. 걸린 시간은 1초 안팎입니다.

```bash
docker run --rm alpine:3.22 cat /etc/os-release
```

```
NAME="Alpine Linux"
ID=alpine
VERSION_ID=3.22.5
```

호스트가 macOS여도 컨테이너 안은 Alpine 리눅스입니다.

## 대화형으로 들어가보기

```bash
docker run --rm -it alpine:3.22 sh
```

```
/ # ls
bin  dev  etc  home  lib  media  mnt  opt  proc  root  run  sbin  srv  sys  tmp  usr  var
/ # apk add --no-cache curl     # 패키지 설치도 됨
/ # exit                        # 나오면 컨테이너는 삭제됨(--rm)
```

- `-i` : 표준 입력을 열어둠 (interactive)
- `-t` : 가상 터미널 할당 (tty)
- 둘을 붙여서 `-it`로 씁니다

# 5. 이미지와 컨테이너의 관계

가장 중요한 개념입니다.

```
이미지(Image)     = 실행에 필요한 파일시스템 + 메타데이터의 스냅샷 (읽기 전용, 클래스)
컨테이너(Container) = 이미지를 실행한 인스턴스 (쓰기 가능한 레이어가 얹힌 프로세스, 객체)

  이미지 하나 → 컨테이너 여러 개
  nginx 이미지 1개로 컨테이너 10개를 띄워도 이미지는 한 벌만 디스크를 차지
```

코드에 비유하면 이렇습니다.

```js
// 이미지 = 클래스
class NginxImage { ... }

// 컨테이너 = 인스턴스
const c1 = new NginxImage();  // docker run nginx
const c2 = new NginxImage();  // docker run nginx
```

컨테이너 안에서 파일을 만들어도 이미지는 바뀌지 않습니다. 컨테이너를 지우면 그 변경분도 함께 사라집니다.

```bash
docker run --rm alpine:3.22 sh -c 'echo hi > /data.txt; cat /data.txt'
# hi

docker run --rm alpine:3.22 cat /data.txt
# cat: can't open '/data.txt': No such file or directory  ← 새 컨테이너라 없음
```

데이터를 남기려면 볼륨이 필요합니다. [05. 볼륨과 데이터](./05-볼륨과-데이터.md)에서 다룹니다.

# 6. docker run 뜯어보기

```bash
docker run -d --name web -p 8080:80 nginx:1.29-alpine
```

```
docker run              컨테이너 생성 + 시작
  -d                    백그라운드 실행 (detached)
  --name web            컨테이너 이름 지정 (안 주면 랜덤 이름)
  -p 8080:80            호스트 8080 → 컨테이너 80 포트 연결
  nginx:1.29-alpine     이미지 이름:태그
```

실행하고 확인해봅니다.

```bash
docker run -d --name web -p 8080:80 nginx:1.29-alpine
docker ps
```

```
NAMES   IMAGE               STATUS                  PORTS
web     nginx:1.29-alpine   Up Less than a second   0.0.0.0:8080->80/tcp, [::]:8080->80/tcp
```

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080
# 200
```

브라우저로 `http://localhost:8080`에 접속하면 nginx 기본 페이지가 보입니다. 로컬에 nginx를 설치한 적이 없는데도 말입니다.

정리는 이렇게 합니다.

```bash
docker stop web     # 중지
docker rm web       # 삭제
```

```bash
container to be able to reuse that name.
→ docker rm -f web 후 다시 실행

# 포트가 이미 쓰이고 있을 때

driver failed programming external connectivity on endpoint web
(98c106e4f04e...): Bind for 0.0.0.0:8080 failed: port is already allocated
→ 다른 포트를 쓰거나, 점유 중인 컨테이너를 종료
```

## 정리

- 컨테이너는 VM이 아니라 **커널을 공유하는 격리된 프로세스**다 (namespace + cgroup)
- 그래서 VM보다 훨씬 가볍고 빠르지만, 보안 경계는 VM보다 약하다
- macOS/Windows에서는 Docker Desktop이 내부 리눅스 VM 위에서 컨테이너를 돌린다
- **이미지는 읽기 전용 스냅샷, 컨테이너는 그 실행 인스턴스** (클래스와 객체 관계)
- 컨테이너에 쓴 데이터는 컨테이너를 지우면 사라진다
- `docker run -d --name 이름 -p 호스트:컨테이너 이미지:태그`가 기본형
- `-it`는 대화형 셸, `--rm`은 종료 시 자동 삭제
