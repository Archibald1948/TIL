# 레지스트리와 배포 - 만든 이미지를 남에게 전달하기

## 들어가며

로컬에서 만든 이미지는 로컬에만 있습니다. 서버나 팀원, CI가 쓰려면 **레지스트리**에 올려야 합니다.

```
내 노트북                레지스트리                  서버 / CI / 팀원
  docker build  ──push──►  Docker Hub / GHCR  ──pull──►  docker run
```

여기에 더해 요즘은 **Apple Silicon(arm64) 노트북에서 빌드해 x86(amd64) 서버에 배포**하는 조합이 흔해서, 아키텍처 문제를 반드시 알아야 합니다.

# 1. 레지스트리 종류

| 레지스트리 | 주소 | 특징 |
|---|---|---|
| Docker Hub | `docker.io` | 기본값, 공개 이미지의 표준 저장소 |
| GitHub Container Registry | `ghcr.io` | GitHub 저장소/Actions와 통합이 쉬움 |
| AWS ECR | `<id>.dkr.ecr.<region>.amazonaws.com` | AWS 배포 시 |
| Google Artifact Registry | `<region>-docker.pkg.dev` | GCP 배포 시 |
| 자체 호스팅 | Harbor, `registry:3` | 사내 폐쇄망 |

이미지 이름은 사실 주소입니다.

```
ghcr.io/myorg/myapp:1.2.3
└─────┘ └───┘ └───┘ └───┘
레지스트리 계정 저장소  태그

nginx:1.29-alpine
= docker.io/library/nginx:1.29-alpine  (생략된 기본값)
```

# 2. 로그인과 푸시

## Docker Hub

```bash
docker login
# Username: myaccount
# Password: (액세스 토큰 권장)

docker tag myapp:latest myaccount/myapp:1.0.0
docker push myaccount/myapp:1.0.0
```

## GHCR

```bash
# GitHub Personal Access Token (write:packages 권한)
echo $GITHUB_TOKEN | docker login ghcr.io -u myusername --password-stdin

docker tag myapp:latest ghcr.io/myorg/myapp:1.0.0
docker push ghcr.io/myorg/myapp:1.0.0
```

GitHub Actions 안에서는 자동 발급되는 토큰을 씁니다.

```yaml
- uses: docker/login-action@v3
  with:
    registry: ghcr.io
    username: ${{ github.actor }}
    password: ${{ secrets.GITHUB_TOKEN }}
```

> 비밀번호를 `docker login -p`로 직접 넘기면 셸 히스토리에 남습니다. `--password-stdin`을 쓰세요. 계정 비밀번호 대신 **액세스 토큰**을 발급해 쓰는 것이 원칙입니다.

## 로그인 정보는 어디에 저장되나

```bash
cat ~/.docker/config.json
```

기본적으로는 base64 인코딩(암호화 아님)으로 저장됩니다. macOS는 Keychain, Linux는 `pass` 같은 credential helper를 연결할 수 있습니다.

# 3. 태그 전략

## latest만 쓰면 생기는 문제

```
문제 1. 서버에서 무엇이 돌고 있는지 알 수 없다
문제 2. 롤백할 대상이 없다 (이전 latest는 이미 덮어씀)
문제 3. docker pull 했을 때 캐시 때문에 갱신이 안 될 수 있다
```

## 실무에서 쓰는 조합

```bash
GIT_SHA=$(git rev-parse --short HEAD)   # 예: a1b2c3d
VERSION=1.4.2

docker build \
  -t ghcr.io/myorg/myapp:$VERSION \
  -t ghcr.io/myorg/myapp:$GIT_SHA \
  -t ghcr.io/myorg/myapp:latest \
  .

docker push ghcr.io/myorg/myapp:$VERSION
docker push ghcr.io/myorg/myapp:$GIT_SHA
docker push ghcr.io/myorg/myapp:latest
```

| 태그 | 역할 |
|---|---|
| `1.4.2` | 사람이 읽는 릴리스 버전 (semver) |
| `a1b2c3d` (git sha) | **정확히 어떤 커밋인지** 추적, 배포/롤백 기준 |
| `latest` | 편의용. 운영 배포에는 쓰지 않음 |
| `1.4`, `1` | 이동 태그(minor/major 최신) |

배포 매니페스트에는 `latest` 대신 git sha나 다이제스트를 쓰는 게 안전합니다.

```bash
# 다이제스트로 완전히 고정
docker pull ghcr.io/myorg/myapp@sha256:abc123...
```

## 이미지 메타데이터 라벨

```dockerfile
LABEL org.opencontainers.image.source="https://github.com/myorg/myapp"
LABEL org.opencontainers.image.version="1.4.2"
LABEL org.opencontainers.image.revision="a1b2c3d"
```

GHCR은 `image.source` 라벨을 보고 패키지를 저장소에 연결해줍니다.

# 4. 멀티 아키텍처 빌드

## 왜 필요한가

```
Apple Silicon 맥 (arm64)에서 빌드 → 이미지도 arm64
AWS EC2 t3 인스턴스 (amd64)에서 실행 → 실행 불가 또는 에뮬레이션으로 매우 느림
```

아키텍처가 다른 이미지를 실행하면 경고가 뜹니다.

```
WARNING: The requested image's platform (linux/amd64) does not match the
detected host platform (linux/arm64/v8) and no specific platform was requested
```

## buildx로 여러 아키텍처 한 번에

```bash
docker buildx ls
```

```
NAME/NODE        DRIVER/ENDPOINT   STATUS    BUILDKIT   PLATFORMS
desktop-linux*   docker
 \_ desktop-linux \_ desktop-linux running   v0.26.3    linux/amd64, linux/arm64, linux/ppc64le, ...
```

```bash
# 두 아키텍처용 이미지를 만들어 레지스트리에 푸시
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t ghcr.io/myorg/myapp:1.0.0 \
  --push .
```

푸시된 것은 **매니페스트 리스트**입니다. 사용자가 `docker pull` 하면 자기 아키텍처에 맞는 이미지가 자동 선택됩니다.

```bash
docker buildx imagetools inspect ghcr.io/myorg/myapp:1.0.0
```

## 로컬로 불러오기

예전에는 멀티 플랫폼 이미지를 `--load`로 가져올 수 없었지만, containerd 이미지 스토어를 쓰면 가능합니다.

```bash
docker info --format '{{.Driver}}'
# overlayfs  (containerd 스냅샷터)

docker buildx build --platform linux/amd64,linux/arm64 -t myapp:multi --load .
docker images myapp --format '{{.Repository}} {{.Size}}'
# myapp 27.7MB    ← 두 아키텍처가 함께 들어 있음
```

> containerd 이미지 스토어가 꺼져 있는 환경(구버전 Docker Desktop, 일부 Linux 설정)에서는 `--load`가 거부됩니다. 그때는 `--push`로 레지스트리에 올리거나 아키텍처별로 따로 빌드해야 합니다. Docker Desktop 설정의 "Use containerd for pulling and storing images"에서 확인할 수 있습니다.

## 특정 아키텍처만 빌드

```bash
docker buildx build --platform linux/amd64 -t myapp:amd64 --load .
docker image inspect myapp:amd64 --format '{{.Os}}/{{.Architecture}}'
# linux/amd64
```

Apple Silicon에서 amd64 이미지를 빌드하면 QEMU 에뮬레이션이 동작해 느립니다. 네이티브 컴파일이 필요한 언어라면 **크로스 컴파일**이 훨씬 빠릅니다.

```dockerfile
FROM --platform=$BUILDPLATFORM golang:1.25-alpine AS builder
ARG TARGETOS TARGETARCH
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH go build -o /server .

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=builder /server /server
ENTRYPOINT ["/server"]
```

```
$BUILDPLATFORM  빌드를 수행하는 머신의 플랫폼 (arm64 맥)
$TARGETPLATFORM 만들려는 이미지의 플랫폼 (amd64)
→ 빌드는 네이티브로 빠르게, 결과물만 타깃 아키텍처로
```

# 5. 서버로 배포하는 방법들

## 1) 레지스트리 경유 (표준)

```bash
# 로컬 또는 CI
docker buildx build --platform linux/amd64 -t ghcr.io/myorg/myapp:$GIT_SHA --push .

# 서버
docker pull ghcr.io/myorg/myapp:$GIT_SHA
docker stop myapp && docker rm myapp
docker run -d --name myapp -p 80:3000 --restart unless-stopped ghcr.io/myorg/myapp:$GIT_SHA
```

## 2) 레지스트리 없이 전송 (임시용)

```bash
# 이미지를 tar로 저장해서 전송
docker save myapp:1.0.0 | gzip > myapp.tar.gz
scp myapp.tar.gz server:~/
ssh server 'gunzip -c myapp.tar.gz | docker load'
```

네트워크가 막힌 환경에서 쓸 수 있지만, 버전 관리가 안 되므로 상시 운영에는 적합하지 않습니다.

## 3) GitHub Actions 예시

```yaml
name: build-and-push

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - uses: docker/metadata-action@v5
        id: meta
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=sha,format=short
            type=ref,event=branch
            type=semver,pattern={{version}}

      - uses: docker/build-push-action@v6
        with:
          context: .
          platforms: linux/amd64,linux/arm64
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

# 6. 자체 레지스트리

사내망에서 간단히 띄울 수 있습니다.

```bash
docker run -d --name registry -p 5000:5000 \
  -v registry-data:/var/lib/registry \
  registry:3

docker tag myapp:1.0.0 localhost:5000/myapp:1.0.0
docker push localhost:5000/myapp:1.0.0
```

실제 운영에서는 HTTPS와 인증이 필요하고, 웹 UI/스캔/권한 관리가 필요하면 Harbor 같은 솔루션을 씁니다.

## 정리

- 이미지 이름은 곧 레지스트리 주소다 (`ghcr.io/조직/앱:태그`)
- 로그인은 비밀번호 대신 **액세스 토큰 + `--password-stdin`**
- `latest`만 쓰면 추적도 롤백도 안 된다 → **semver + git sha**를 함께 태깅
- 배포 시점 고정이 중요하면 다이제스트(`@sha256:...`)를 사용
- Apple Silicon에서 빌드해 x86 서버에 올리면 아키텍처 불일치가 발생한다
- `docker buildx build --platform linux/amd64,linux/arm64 --push`로 멀티 아치 이미지 생성
- containerd 이미지 스토어를 쓰면 멀티 플랫폼 이미지를 `--load`로 로컬에 둘 수도 있다
- 네이티브 컴파일 언어는 QEMU 에뮬레이션보다 `$BUILDPLATFORM` + 크로스 컴파일이 훨씬 빠르다
