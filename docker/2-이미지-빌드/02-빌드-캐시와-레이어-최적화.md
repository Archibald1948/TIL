# 빌드 캐시와 레이어 최적화 - 3분 빌드를 3초로

## 들어가며

```
개발 중 흔한 풍경

코드 한 줄 수정 → docker build → npm install 처음부터 다시 → 3분 대기
코드 한 줄 수정 → docker build → 또 3분
```

Dockerfile에서 **명령어 순서만 바꿔도** 이 3분이 몇 초로 줄어듭니다. 원리는 레이어 캐시입니다.

# 1. 빌드 캐시의 규칙

빌드는 Dockerfile의 명령을 위에서 아래로 실행하면서 레이어를 쌓습니다. 이때 각 레이어마다 "이전과 같은가"를 확인합니다.

```
규칙 1. 명령어 문자열이 같고, 이전 레이어도 캐시 적중이면 → 캐시 사용
규칙 2. COPY/ADD는 복사하는 파일의 내용(체크섬)까지 비교
규칙 3. 한 레이어에서 캐시가 깨지면, 그 아래 모든 레이어는 다시 실행
```

3번이 핵심입니다. **자주 바뀌는 것을 아래쪽에 두어야 합니다.**

```
변경 빈도가 낮은 것 (위)
  ↓  베이스 이미지
  ↓  시스템 패키지 설치
  ↓  의존성 파일 복사 (package.json)
  ↓  의존성 설치 (npm install)
  ↓  애플리케이션 소스 복사
변경 빈도가 높은 것 (아래)
```

# 2. 나쁜 예 vs 좋은 예

같은 앱을 두 가지 Dockerfile로 빌드해서 비교해봅니다.

```dockerfile
# Dockerfile.bad
FROM node:22-alpine
WORKDIR /app
COPY . .                      # 소스 전체를 먼저 복사
RUN npm install --omit=dev    # → 소스가 바뀌면 여기부터 다시 실행
CMD ["node", "server.js"]
```

```dockerfile
# Dockerfile.good
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./         # 의존성 정의만 먼저
RUN npm install --omit=dev    # → package.json이 그대로면 캐시 적중
COPY . .                      # 소스는 나중에
CMD ["node", "server.js"]
```

`server.js`를 한 줄 고친 뒤 각각 다시 빌드한 결과입니다.

```bash
# bad: 소스가 바뀌었으니 npm install도 다시
docker build -t app-bad -f Dockerfile.bad .
```

```
#7 [3/4] COPY . .
#8 [4/4] RUN npm install --omit=dev      ← 다시 실행됨
소요: 3.2초
```

```bash
# good: npm install은 캐시 재사용
docker build -t app-good -f Dockerfile.good .
```

```
#6 [2/5] WORKDIR /app          CACHED
#7 [3/5] COPY package*.json ./ CACHED
#8 [4/5] RUN npm install       CACHED     ← 재사용
#9 [5/5] COPY . .
소요: 0.4초
```

의존성이 68개뿐인 장난감 앱인데도 8배 차이가 납니다. 의존성이 수백 개인 실제 프로젝트에서는 **분 단위 대 초 단위**로 벌어집니다.

# 3. 빌드 컨텍스트

```bash
docker build -t myapp .
#                     ↑ 이 디렉터리 전체가 빌드 컨텍스트
```

빌드를 시작하면 컨텍스트가 Docker 데몬으로 전송됩니다. 빌드 로그의 이 줄이 그것입니다.

```
#3 [internal] load build context
#3 transferring context: 53B done
```

컨텍스트가 크면 빌드 시작 전부터 느려집니다. `.dockerignore`로 줄입니다.

```
node_modules
.git
dist
coverage
*.log
.env*
```

`node_modules`(40MB)를 제외했을 때의 차이는 이미지 크기로도 드러납니다.

```
.dockerignore 없음 → 97.3MB
node_modules 제외  → 13.4MB
```

> `.git`은 특히 중요합니다. 커밋할 때마다 내용이 바뀌므로, 제외하지 않으면 `COPY . .`의 캐시가 매번 깨집니다.

# 4. RUN 레이어 다루기

## 레이어는 합치되, 캐시는 살린다

```dockerfile
# 레이어 3개, 그리고 apt 캐시가 이미지에 남음
RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*
```

```dockerfile
# 레이어 1개, 정리까지 같은 레이어에서
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl \
 && rm -rf /var/lib/apt/lists/*
```

중요한 이유: **한 레이어에서 지운 파일은 이전 레이어에는 그대로 남아 있습니다.** 아래처럼 하면 이미지 크기가 전혀 줄지 않습니다.

```dockerfile
RUN apt-get install -y build-essential   # 200MB 추가
RUN apt-get remove -y build-essential    # 지워도 이전 레이어에 200MB가 남음
```

## apt-get update와 install은 반드시 같은 RUN에

```dockerfile
# 위험: update는 캐시되고 install만 새로 실행되면
#       오래된 패키지 목록으로 설치하게 됨 (cache busting 문제)
RUN apt-get update
RUN apt-get install -y curl nginx
```

## Alpine의 --no-cache

```dockerfile
RUN apk add --no-cache curl git    # 패키지 인덱스를 남기지 않음
```

# 5. BuildKit 캐시 마운트

BuildKit(현재 기본 빌더)은 `RUN` 명령에 **이미지에 포함되지 않는 캐시 디렉터리**를 붙일 수 있습니다.

```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm install --omit=dev
COPY . .
CMD ["node", "server.js"]
```

`package.json`이 바뀌면 `npm install`은 다시 실행되지만, **다운로드 캐시는 유지**되므로 네트워크 다운로드가 생략됩니다.

```
캐시 없이 재설치        → 2.4초 (전부 다운로드)
캐시 마운트로 재설치     → 1.0초 (로컬 캐시 재사용)
```

언어별로 캐시 경로가 다릅니다.

```dockerfile
# npm
RUN --mount=type=cache,target=/root/.npm npm ci

# pnpm
RUN --mount=type=cache,target=/pnpm/store pnpm install --frozen-lockfile

# pip
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt

# Go
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go build -o /server .

# Rust (cargo)
RUN --mount=type=cache,target=/usr/local/cargo/registry \
    --mount=type=cache,target=/app/target \
    cargo build --release

# apt
RUN --mount=type=cache,target=/var/cache/apt \
    apt-get update && apt-get install -y curl
```

> 캐시 마운트의 내용은 이미지에 포함되지 않습니다. 빌드 머신에만 남습니다. CI에서는 캐시가 러너 사이에 공유되지 않으므로 별도 설정(`--cache-from`, GitHub Actions 캐시 등)이 필요합니다.

# 6. 빌드 시크릿

개인 저장소에서 패키지를 받으려면 빌드 중에 토큰이 필요합니다. `ARG`로 넘기면 `docker history`에 남습니다. `--mount=type=secret`을 쓰면 남지 않습니다.

```dockerfile
FROM alpine:3.22
RUN --mount=type=secret,id=apikey \
    echo "빌드 중 시크릿 길이: $(wc -c < /run/secrets/apikey)" && \
    echo "이미지에는 남지 않음" > /result.txt
```

```bash
echo "sk-비밀키-1234" > secret.txt
docker build --secret id=apikey,src=secret.txt -t secretdemo .
```

이미지에 남았는지 확인해보면,

```bash
docker run --rm secretdemo sh -c 'ls /run/secrets; cat /result.txt'
# ls: /run/secrets: No such file or directory     ← 런타임에는 없음
# 이미지에는 남지 않음

docker history secretdemo --format '{{.CreatedBy}}' | grep -c '비밀키'
# 0                                                ← history에도 없음
```

실전 예시입니다.

```dockerfile
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci --omit=dev
```

```bash
docker build --secret id=npmrc,src=$HOME/.npmrc -t myapp .
```

환경 변수로 넘길 수도 있습니다.

```bash
docker build --secret id=GITHUB_TOKEN,env=GITHUB_TOKEN -t myapp .
```

# 7. 캐시 무효화를 의도적으로 하기

가끔은 캐시를 강제로 무시해야 합니다.

```bash
docker build --no-cache -t myapp .            # 전부 새로
docker build --pull -t myapp .                # 베이스 이미지도 최신으로 다시 받기
```

특정 지점부터만 무효화하고 싶다면 `ARG`를 이용합니다.

```dockerfile
ARG CACHEBUST=1
RUN --mount=type=cache,target=/root/.npm npm install
```

```bash
docker build --build-arg CACHEBUST=$(date +%s) -t myapp .
```

# 8. 빌드 캐시 관리

빌드 캐시는 생각보다 빨리 커집니다.

```bash
docker system df
```

```
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          33        7         6.029GB   4.39GB (72%)
Build Cache     124       0         4.975GB   4.499GB
```

```bash
docker builder prune                 # 안 쓰는 캐시 정리
docker builder prune --filter until=168h   # 7일 이상 된 것만
docker builder prune -a              # 전부 (다음 빌드가 느려짐)
```

## CI에서 캐시 재사용

CI 러너는 매번 새 환경이라 로컬 캐시가 없습니다. 레지스트리를 캐시 저장소로 쓸 수 있습니다.

```bash
docker buildx build \
  --cache-from type=registry,ref=ghcr.io/myorg/myapp:buildcache \
  --cache-to type=registry,ref=ghcr.io/myorg/myapp:buildcache,mode=max \
  -t ghcr.io/myorg/myapp:latest --push .
```

GitHub Actions라면 `type=gha`를 쓰는 방법도 있습니다.

```yaml
- uses: docker/build-push-action@v6
  with:
    push: true
    tags: ghcr.io/myorg/myapp:latest
    cache-from: type=gha
    cache-to: type=gha,mode=max
```

# 9. 체크리스트

```
□ .dockerignore에 node_modules, .git, dist, .env가 들어 있는가
□ 의존성 파일(package.json, go.mod, requirements.txt)을 소스보다 먼저 COPY 하는가
□ 패키지 설치와 캐시 정리가 같은 RUN 안에 있는가
□ apt-get update와 install이 같은 RUN 안에 있는가
□ 자주 바뀌는 명령이 아래쪽에 있는가
□ 반복 다운로드가 많다면 --mount=type=cache를 쓰는가
□ 빌드 시 토큰이 필요하면 ARG가 아니라 --mount=type=secret을 쓰는가
```

## 정리

- 캐시는 **위에서부터 순서대로** 확인되고, 한 번 깨지면 그 아래는 전부 다시 실행된다
- 의존성 설치를 소스 복사보다 **위에** 두는 것만으로 빌드가 극적으로 빨라진다 (실측 3.2초 → 0.4초)
- `.dockerignore`는 컨텍스트 전송량, 이미지 크기, 캐시 적중률에 모두 영향을 준다
- 한 레이어에서 지운 파일은 이전 레이어에 그대로 남는다 → 설치와 정리는 같은 `RUN`에서
- `--mount=type=cache`로 패키지 매니저 캐시를 이미지 밖에 유지할 수 있다
- 빌드 시 시크릿은 `--mount=type=secret` (ARG/ENV는 history에 남는다)
- 빌드 캐시는 계속 쌓이므로 `docker builder prune`으로 주기적으로 정리
- CI에서는 `--cache-from/--cache-to`로 캐시를 레지스트리에 저장해 재사용
