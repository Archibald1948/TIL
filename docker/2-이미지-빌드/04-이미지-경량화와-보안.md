# 이미지 경량화와 보안 - 작을수록 안전하다

## 들어가며

이미지 크기와 보안은 사실 같은 문제입니다.

```
이미지가 크다 = 안에 들어 있는 패키지가 많다
             = 취약점(CVE)을 가진 패키지가 많다
             = 공격자가 쓸 수 있는 도구(셸, curl, 패키지 매니저)가 많다

이미지가 작다 = 배포가 빠르다 + 공격 표면이 작다
```

이 문서는 베이스 이미지 선택, 비root 실행, 취약점 스캔, 시크릿 관리를 다룹니다.

# 1. 베이스 이미지 선택

로컬에서 직접 받아 측정한 크기입니다 (arm64 기준).

| 이미지 | 크기 | 특징 |
|---|---|---|
| `gcr.io/distroless/static-debian12` | 6.18MB | 셸도 패키지 매니저도 없음 |
| `alpine:3.22` | 13.4MB | musl libc, apk, 셸 있음 |
| `python:3.13-alpine` | 83.2MB | |
| `nginx:1.29-alpine` | 92.7MB | |
| `debian:13-slim` | 141MB | glibc, 최소 구성 |
| `python:3.13-slim` | 215MB | |
| `node:22-alpine` | 229MB | |
| `node:22-slim` | 349MB | |

## 계열별 성격

```
full (node:22, python:3.13)
  - 빌드 도구, git, curl 등 다 들어 있음 (수백 MB ~ 1GB 이상)
  - 빌드 스테이지에서는 편하지만 런타임에는 과함

slim (node:22-slim, python:3.13-slim)
  - Debian 기반에서 불필요한 것 제거
  - glibc 사용 → 호환성 문제가 적음
  - 무난한 기본 선택

alpine
  - musl libc 기반, 매우 작음
  - 네이티브 모듈이 musl에서 문제를 일으킬 수 있음
  - Python은 wheel을 못 써서 빌드가 느려지는 경우가 있음

distroless
  - 앱과 런타임만, 셸/패키지 매니저 없음
  - 가장 안전하지만 디버깅이 어려움 (docker exec로 셸 진입 불가)
  - Go/Rust 정적 바이너리, Java, Node에 적합

scratch
  - 완전히 빈 이미지, CA 인증서조차 없음
  - 정적 링크 바이너리 전용
```

## Alpine을 고를 때 주의할 점

```
musl libc ≠ glibc

- 일부 네이티브 모듈(node-gyp로 빌드되는 것들)이 musl에서 동작 차이를 보임
- Python은 wheel(미리 컴파일된 바이너리)을 쓸 수 없어 소스 컴파일 → 빌드 시간 증가
- DNS 처리 방식 차이로 드물게 이슈가 있었음

→ "무조건 alpine"이 아니라, 앱이 정상 동작하는지 확인하고 선택
```

## distroless는 셸이 없다

```bash
docker run --rm gcr.io/distroless/static-debian12 sh -c 'echo hi'
```

```
exec: "sh": executable file not found in $PATH
```

`docker exec`로 들어가서 확인하는 게 불가능합니다. 디버깅이 필요하면 `:debug` 태그(busybox 포함) 이미지를 임시로 쓰거나, `docker debug`(Docker Desktop 기능)를 이용합니다.

# 2. 비root로 실행하기

컨테이너는 기본적으로 **root**로 실행됩니다. 컨테이너 안의 root는 호스트의 root와 (user namespace를 쓰지 않는 한) 같은 UID 0이라, 컨테이너 탈출 취약점과 겹치면 위험합니다.

## 이미지에 준비된 유저 사용

```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
USER node                  # node 이미지에는 uid 1000 node 유저가 있음
EXPOSE 3000
CMD ["node", "server.js"]
```

```bash
docker run --rm myapp id
# uid=1000(node) gid=1000(node) groups=1000(node)

docker run --rm myapp sh -c 'touch /root/x'
# touch: /root/x: Permission denied
```

## 직접 만들기

```dockerfile
# Alpine
RUN addgroup -S app && adduser -S -G app app
USER app

# Debian/Ubuntu
RUN groupadd -r app && useradd -r -g app app
USER app
```

## 주의사항

```
- USER 이후의 RUN은 그 유저 권한으로 실행됨 → 패키지 설치는 USER 앞에
- 앱이 쓰는 디렉터리의 소유권을 미리 넘겨줘야 함
    COPY --chown=app:app . .
- 1024 미만 포트(80, 443)는 비root가 바인딩할 수 없음 → 3000, 8080 등을 쓰고
  포트 매핑으로 해결 (-p 80:8080)
```

## 런타임에서 강제하기

Dockerfile을 못 고치는 이미지라면 실행할 때 지정할 수 있습니다.

```bash
docker run --user 1000:1000 someimage
```

추가로 권한을 조이는 옵션들입니다.

```bash
docker run -d \
  --user 1000:1000 \
  --read-only \                          # 루트 파일시스템 읽기 전용
  --tmpfs /tmp \                         # 쓰기가 필요한 곳만 tmpfs
  --cap-drop ALL \                       # 모든 리눅스 capability 제거
  --security-opt no-new-privileges \     # 권한 상승 차단
  myapp
```

# 3. 취약점 스캔

## docker scout (Docker Desktop 내장)

```bash
docker scout quickview myapp:latest
docker scout cves myapp:latest
docker scout recommendations myapp:latest   # 더 안전한 베이스 이미지 추천
```

```
로그인이 필요합니다.

$ docker scout quickview myapp
Log in with your Docker ID or email address to use docker scout.
→ docker login 후 사용
```

## Trivy (오픈소스)

```bash
brew install trivy

trivy image myapp:latest
trivy image --severity HIGH,CRITICAL myapp:latest
trivy image --exit-code 1 --severity CRITICAL myapp:latest   # CI에서 실패 처리
trivy fs .                                                    # 소스 코드/의존성 스캔
```

Docker로 바로 돌릴 수도 있습니다.

```bash
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy image myapp:latest
```

## CI에 넣기

```yaml
# GitHub Actions 예시
- name: Trivy 스캔
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: ghcr.io/myorg/myapp:${{ github.sha }}
    severity: CRITICAL,HIGH
    exit-code: '1'
```

## 취약점을 줄이는 현실적인 방법

```
1. 베이스 이미지를 주기적으로 업데이트 (docker build --pull)
2. 더 작은 베이스로 교체 (slim → alpine → distroless)
3. 빌드 도구를 런타임 이미지에서 제거 (멀티스테이지)
4. 사용하지 않는 패키지 제거
5. 애플리케이션 의존성도 함께 스캔 (npm audit, pip-audit)
```

# 4. 이미지 들여다보기: dive

레이어별로 무엇이 얼마나 차지하는지 보여주는 도구입니다.

```bash
brew install dive
dive myapp:latest
```

```
좌측: 레이어 목록과 크기
우측: 해당 레이어가 추가/변경한 파일 트리
하단: efficiency 점수와 낭비된 공간
```

도구 없이도 대략은 알 수 있습니다.

```bash
docker history myapp:latest --format 'table {{.Size}}\t{{.CreatedBy}}' | head -10
docker image inspect myapp:latest --format '{{len .RootFS.Layers}} layers'
```

# 5. 시크릿을 이미지에 넣지 않기

## 왜 위험한가

```dockerfile
# 절대 하지 말 것
ENV API_KEY=sk-abcd1234
COPY .env /app/.env
RUN git clone https://토큰@github.com/private/repo.git
```

```bash
docker history myimage --no-trunc        # RUN 명령의 인자가 그대로 보임
docker inspect myimage --format '{{.Config.Env}}'   # ENV가 그대로 보임
```

레이어를 지워도 **이전 레이어에 남아 있어서** 이미지를 받은 사람은 복구할 수 있습니다.

## 올바른 방법

```
빌드 시 필요한 시크릿   → --mount=type=secret
런타임에 필요한 시크릿  → 환경 변수 주입(-e, --env-file), 시크릿 매니저, 볼륨 마운트
```

```dockerfile
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci --omit=dev
```

```bash
docker build --secret id=npmrc,src=$HOME/.npmrc -t myapp .
```

```bash
# 런타임 주입
docker run -d --env-file .env.production myapp
```

`.dockerignore`에 `.env*`를 넣어 실수로 복사되는 것도 막습니다.

```
.env
.env.*
*.pem
*.key
.git
```

# 6. SBOM과 서명

## SBOM (Software Bill of Materials)

이미지에 어떤 패키지가 들어 있는지 목록으로 만든 것입니다. 새 CVE가 발표됐을 때 "우리 이미지에 그 패키지가 있나"를 빠르게 확인할 수 있습니다.

```bash
docker buildx build --sbom=true -t myapp --load .
```

```
#12 [linux/arm64] generating sbom using docker.io/docker/buildkit-syft-scanner:stable-1
#13 naming to docker.io/library/myapp:latest done
```

```bash
docker buildx build --sbom=true --provenance=true -t ghcr.io/myorg/myapp:1.0 --push .
docker buildx imagetools inspect ghcr.io/myorg/myapp:1.0 --format '{{ json .SBOM }}'
```

## 이미지 서명

이미지가 위변조되지 않았음을 증명합니다. 요즘은 Sigstore의 cosign이 널리 쓰입니다.

```bash
cosign sign ghcr.io/myorg/myapp:1.0
cosign verify ghcr.io/myorg/myapp:1.0
```

# 7. 체크리스트

```
크기
□ 런타임 이미지에 컴파일러/빌드 도구가 없는가 (멀티스테이지)
□ 베이스가 full이 아니라 slim/alpine/distroless인가
□ .dockerignore로 불필요한 파일을 제외했는가
□ 패키지 설치 후 캐시를 같은 RUN에서 정리했는가

보안
□ USER로 비root 실행을 지정했는가
□ 이미지에 .env, 키 파일, 토큰이 들어가지 않는가
□ 베이스 이미지 태그가 고정되어 있는가 (latest 금지)
□ CI에서 취약점 스캔을 돌리는가
□ 베이스 이미지를 주기적으로 갱신하는가
□ 운영에서 --read-only, --cap-drop ALL을 검토했는가
```

## 정리

- 이미지 크기와 공격 표면은 같이 움직인다. 작을수록 CVE도, 공격 도구도 줄어든다
- 베이스는 full → slim → alpine → distroless → scratch 순으로 작아지고 디버깅은 어려워진다
- Alpine은 musl libc라서 네이티브 모듈/Python 휠에서 문제가 생길 수 있다
- `USER`로 비root 실행은 가장 비용 대비 효과가 큰 보안 조치
- 운영에서는 `--read-only`, `--cap-drop ALL`, `--security-opt no-new-privileges`도 검토
- `docker scout`(로그인 필요), `trivy`로 취약점을 스캔하고 CI에서 실패 처리
- 시크릿은 절대 이미지에 넣지 않는다. 빌드는 `--mount=type=secret`, 런타임은 환경 변수/시크릿 매니저
- SBOM(`--sbom=true`)과 서명(cosign)으로 공급망 신뢰를 보강할 수 있다
