# 멀티스테이지 빌드 - 빌드 도구를 최종 이미지에서 빼내기

## 들어가며

컴파일이 필요한 언어로 이미지를 만들면 이런 일이 생깁니다.

```
Go 애플리케이션을 빌드했더니
  - 컴파일된 바이너리: 약 8MB
  - 그런데 이미지는: 440MB

이미지에 들어 있는 것
  ✅ 내 바이너리 (8MB)
  ❌ Go 컴파일러 (수백 MB)
  ❌ 소스 코드
  ❌ 빌드 캐시
  → 실행에는 하나도 필요 없는 것들
```

**멀티스테이지 빌드**는 "빌드하는 이미지"와 "실행하는 이미지"를 나눠서, 결과물만 옮겨 담는 방법입니다.

# 1. 기본 구조

```dockerfile
# 1단계: 빌드 (무거워도 상관없음)
FROM golang:1.25-alpine AS builder
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /server .

# 2단계: 실행 (최소한만)
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=builder /server /server
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/server"]
```

```
FROM ... AS builder        스테이지에 이름을 붙임
COPY --from=builder 경로   앞 스테이지에서 파일만 가져옴
최종 이미지 = 마지막 FROM 부터 만들어진 것만
```

빌드 스테이지의 컴파일러, 소스, 중간 산출물은 **최종 이미지에 하나도 포함되지 않습니다.**

# 2. 실측 비교 (Go)

같은 Go 웹 서버를 두 방식으로 빌드했습니다.

```dockerfile
# Dockerfile.single - 단일 스테이지
FROM golang:1.25-alpine
WORKDIR /src
COPY . .
RUN go build -o /app/server .
CMD ["/app/server"]
```

```dockerfile
# Dockerfile.multi - 멀티스테이지
FROM golang:1.25-alpine AS builder
WORKDIR /src
COPY go.mod ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /server .

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=builder /server /server
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/server"]
```

```bash
docker images --format '{{.Repository}}\t{{.Size}}' | grep go
```

```
tilchk-go-single    440MB
tilchk-go-multi     13.6MB     ← 32배 차이
```

동작은 동일합니다.

```bash
docker run -d -p 18081:8080 tilchk-go-multi
curl -s http://localhost:18081
# hello from go
```

빌드 옵션도 크기에 영향을 줍니다.

```
CGO_ENABLED=0        C 라이브러리 의존성 제거 → scratch/distroless에서 실행 가능
-ldflags="-s -w"     디버그 심볼과 DWARF 정보 제거 → 바이너리 20~30% 감소
```

# 3. 언어별 패턴

## Node.js

Node는 인터프리터가 필요해서 Go만큼 극적이지는 않지만, **devDependencies와 빌드 산출물을 분리**하는 효과가 있습니다.

```dockerfile
# 1단계: 프로덕션 의존성만
FROM node:22-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev

# 2단계: 빌드 (devDependencies 포함, TypeScript 컴파일 등)
FROM node:22-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build          # dist/ 생성

# 3단계: 실행
FROM node:22-alpine AS runtime
WORKDIR /app
ENV NODE_ENV=production
COPY --from=deps /app/node_modules ./node_modules
COPY --from=builder /app/dist ./dist
USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]
```

```
단일 스테이지 (devDependencies 포함)  246MB
멀티스테이지                          234MB
```

> 위 수치는 의존성이 68개뿐인 예제 앱 기준이라 차이가 작습니다. TypeScript, webpack, 테스트 라이브러리까지 들어간 실제 프로젝트에서는 devDependencies가 수백 MB인 경우가 많아 차이가 훨씬 커집니다.

프런트엔드 정적 빌드라면 최종 이미지가 nginx가 됩니다. 이 경우는 차이가 큽니다.

```dockerfile
FROM node:22-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build          # dist/ 에 정적 파일 생성

FROM nginx:1.29-alpine
COPY --from=builder /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

```
node:22-alpine 기반 (빌드 환경 포함)   229MB + 소스/의존성
nginx:1.29-alpine + 정적 파일           92.7MB + 정적 파일 몇 MB
```

## Python

```dockerfile
FROM python:3.13-slim AS builder
WORKDIR /app
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --no-cache-dir -r requirements.txt

FROM python:3.13-slim
WORKDIR /app
COPY --from=builder /opt/venv /opt/venv
COPY . .
ENV PATH="/opt/venv/bin:$PATH" \
    PYTHONUNBUFFERED=1
RUN useradd -m appuser && chown -R appuser /app
USER appuser
CMD ["python", "main.py"]
```

가상환경(`/opt/venv`)만 통째로 옮기는 게 요령입니다. 빌드 중 필요한 컴파일러(`gcc`, `build-essential`)가 최종 이미지에 남지 않습니다.

```
python:3.13-slim    215MB
python:3.13-alpine   83.2MB
```

> Python은 Alpine에서 휠(wheel) 바이너리를 못 쓰고 소스 컴파일로 넘어가는 패키지가 있어, 빌드가 느려지고 오히려 이미지가 커질 수 있습니다. 특별한 이유가 없으면 `slim`을 먼저 고려하세요.

## Rust

```dockerfile
FROM rust:1.98-alpine AS builder
RUN apk add --no-cache musl-dev
WORKDIR /src
COPY Cargo.toml Cargo.lock ./
RUN mkdir src && echo "fn main() {}" > src/main.rs
RUN --mount=type=cache,target=/usr/local/cargo/registry \
    cargo build --release && rm -rf src
COPY . .
RUN --mount=type=cache,target=/usr/local/cargo/registry \
    touch src/main.rs && cargo build --release && \
    cp target/release/myapp /myapp

FROM scratch
COPY --from=builder /myapp /myapp
EXPOSE 8080
ENTRYPOINT ["/myapp"]
```

```
빈 main.rs로 먼저 빌드 → 의존성만 컴파일된 상태를 캐시
그 다음 실제 소스를 복사해 빌드 → 의존성 재컴파일 생략
```

Rust/Go처럼 **정적 링크된 단일 바이너리**를 만들 수 있는 언어는 `scratch`(완전히 빈 이미지)까지 갈 수 있습니다. 다만 `scratch`에는 CA 인증서도 없어서 HTTPS 요청이 실패합니다. 그럴 때는 인증서를 복사하거나 distroless를 씁니다.

```dockerfile
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
```

# 4. --target 으로 스테이지 골라 빌드하기

```bash
docker build --target builder -t myapp-builder .
```

특정 스테이지까지만 빌드합니다. 개발용과 운영용을 한 Dockerfile에서 관리할 때 유용합니다.

```dockerfile
FROM node:22-alpine AS base
WORKDIR /app
COPY package*.json ./

FROM base AS dev
RUN npm install
COPY . .
CMD ["npm", "run", "dev"]        # nodemon 등

FROM base AS build
RUN npm ci
COPY . .
RUN npm run build

FROM node:22-alpine AS prod
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
USER node
CMD ["node", "dist/server.js"]
```

```bash
docker build --target dev  -t myapp:dev .     # 개발용
docker build --target prod -t myapp:prod .    # 운영용 (기본값은 마지막 스테이지)
```

Compose에서는 `build.target`으로 지정합니다.

```yaml
services:
  app:
    build:
      context: .
      target: dev
```

# 5. 알아두면 좋은 것들

## 스테이지는 이미지도 될 수 있다

```dockerfile
FROM myregistry.com/base-image:1.0 AS builder
```

외부 이미지를 스테이지처럼 쓸 수도 있고,

```dockerfile
COPY --from=nginx:1.29-alpine /etc/nginx/nginx.conf /tmp/nginx-default.conf
```

빌드하지 않은 이미지에서 파일만 꺼내올 수도 있습니다.

## 필요한 스테이지만 실행된다

BuildKit은 최종 결과에 필요한 스테이지만 빌드합니다. 쓰이지 않는 스테이지는 건너뜁니다. 그래서 테스트 전용 스테이지를 넣어두고 필요할 때만 `--target test`로 돌리는 패턴이 가능합니다.

```dockerfile
FROM builder AS test
RUN npm run test
```

```bash
docker build --target test .     # CI에서 테스트만 실행
```

## 빌드 산출물을 이미지 대신 파일로 꺼내기

```bash
docker build --output type=local,dest=./out --target export .
```

```dockerfile
FROM scratch AS export
COPY --from=builder /app/dist /
```

크로스 컴파일 결과물만 호스트로 뽑아낼 때 유용합니다.

## 정리

- 멀티스테이지는 **빌드 환경과 실행 환경을 분리**해서 최종 이미지에 결과물만 남긴다
- `FROM ... AS 이름` + `COPY --from=이름`이 전부
- Go/Rust처럼 정적 바이너리를 만드는 언어는 효과가 극적이다 (실측 440MB → 13.6MB)
- Node는 devDependencies 분리, 프런트엔드는 nginx로 갈아타는 형태로 효과를 본다
- Python은 venv를 통째로 옮기는 패턴이 깔끔하고, Alpine보다 slim이 무난하다
- `--target`으로 개발/빌드/테스트/운영 스테이지를 한 파일에서 관리할 수 있다
- 쓰이지 않는 스테이지는 빌드되지 않으므로 테스트 스테이지를 넣어둬도 손해가 없다
