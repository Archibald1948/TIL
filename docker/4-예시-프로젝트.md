# 예시 프로젝트 - Docker로 만들면 좋은 것들

## 들어가며

Docker는 문법을 외운다고 늘지 않습니다. **"내 앱을 컨테이너로 옮겨 서버에 띄워봤다"**는 경험 한 번이 문서 열 개보다 낫습니다.

이 문서는 난이도 순서로 연습거리를 정리합니다. 각 항목마다

```
- 왜 Docker가 어울리는지
- 어떻게 구성하는지 (스케치)
- 참고할 실제 오픈소스
```

를 함께 적었습니다. 위에서부터 차례로 해도 좋고, 지금 하고 있는 프로젝트와 가까운 것을 골라도 됩니다.

# 1. 입문: 손에 익히기

## 1-1. 정적 사이트를 nginx로 배포하기

가장 빠르게 "컨테이너로 서비스가 뜬다"를 경험할 수 있는 과제입니다.

```
왜 Docker인가
- 호스트에 nginx를 설치하지 않아도 됨
- 설정 파일과 콘텐츠가 이미지 하나에 담겨 어디서나 동일하게 동작
- 정적 사이트 빌드(Hugo, Vite 등)까지 멀티스테이지로 묶을 수 있음
```

```dockerfile
# 빌드 단계: 정적 사이트 생성
FROM node:24-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# 실행 단계: nginx로 서빙 (최종 이미지에 node 없음)
FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
```

```bash
docker build -t my-site .
docker run -d -p 8080:80 my-site
```

**다음 단계**: SPA라면 라우팅 폴백(`try_files $uri /index.html`) 설정, gzip/brotli 압축, 캐시 헤더 추가해 보기

참고: [Hugo](https://github.com/gohugoio/hugo) · [nginx 공식 이미지 문서](https://hub.docker.com/_/nginx)

## 1-2. 개발용 DB 모음 스택

로컬에 Postgres, MySQL, Redis를 직접 설치하지 않고 필요할 때만 띄우는 구성입니다. 실무에서 가장 자주 쓰게 되는 패턴이기도 합니다.

```
왜 Docker인가
- 프로젝트마다 다른 DB 버전을 충돌 없이 사용
- brew로 설치한 DB가 백그라운드에서 계속 도는 문제 없음
- down -v 한 번으로 완전 초기화
```

```yaml
name: devdb

services:
  postgres:
    image: postgres:18-alpine
    environment:
      POSTGRES_USER: dev
      POSTGRES_PASSWORD: dev
      POSTGRES_DB: dev
    ports:
      - "127.0.0.1:5432:5432"
    volumes:
      - pg:/var/lib/postgresql        # 18+ 경로 주의
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U dev"]
      interval: 5s
      retries: 10

  redis:
    image: redis:alpine
    ports:
      - "127.0.0.1:6379:6379"

  adminer:
    image: adminer:latest
    ports:
      - "127.0.0.1:8081:8080"
    profiles: ["tools"]

volumes:
  pg:
```

**연습 포인트**: 포트를 `127.0.0.1`로만 여는 습관, `profiles`로 관리 도구 분리, healthcheck 작성

# 2. 초급: 내 앱 컨테이너화하기

## 2-1. Node.js / Next.js 앱

```
왜 Docker인가
- Node 버전 차이로 생기는 "내 컴퓨터에선 되는데" 제거
- 빌드 산출물만 담은 작은 운영 이미지 생성
- CI에서 만든 이미지를 그대로 배포
```

```dockerfile
FROM node:24-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci

FROM node:24-alpine AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build

FROM node:24-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
RUN addgroup -S app && adduser -S -G app app
COPY --from=build --chown=app:app /app/.next/standalone ./
COPY --from=build --chown=app:app /app/.next/static ./.next/static
COPY --from=build --chown=app:app /app/public ./public
USER app
EXPOSE 3000
CMD ["node", "server.js"]
```

**연습 포인트**

```
□ .dockerignore 에 node_modules, .next, .git 넣기
□ Next.js는 output: "standalone" 설정으로 이미지 크기 줄이기
□ 빌드 타임 환경변수와 런타임 환경변수 구분하기
□ 최종 이미지 크기 측정: docker image ls
```

참고: [Next.js](https://github.com/vercel/next.js) (저장소의 `examples/with-docker`)

## 2-2. Python FastAPI + PostgreSQL

```
왜 Docker인가
- 파이썬 가상환경·시스템 라이브러리 문제를 이미지 안에서 해결
- DB까지 묶어 "clone 후 up 한 번"으로 실행 가능
```

```yaml
name: fastapi-app

services:
  api:
    build: .
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql://app:devpass@db:5432/appdb
      PYTHONUNBUFFERED: "1"      # 로그가 바로 나오도록
    depends_on:
      db:
        condition: service_healthy
    develop:
      watch:
        - action: sync
          path: ./app
          target: /code/app
        - action: rebuild
          path: ./requirements.txt

  db:
    image: postgres:18-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: devpass
      POSTGRES_DB: appdb
    volumes:
      - pg:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d appdb"]
      interval: 3s
      retries: 10

volumes:
  pg:
```

**연습 포인트**: `docker compose watch`로 핫 리로드, alembic 마이그레이션을 `service_completed_successfully`로 순서 보장

참고: [FastAPI](https://github.com/fastapi/fastapi)

# 3. 중급: 이미지와 운영을 다듬기

## 3-1. Go / Rust 바이너리로 초경량 이미지 만들기

컴파일 언어의 장점이 가장 극적으로 드러나는 연습입니다. 수백 MB짜리 이미지를 수 MB까지 줄여봅니다.

```
왜 Docker인가
- 정적 바이너리 + scratch/distroless = 극단적으로 작고 공격 표면이 적은 이미지
- 배포·기동 속도가 빨라짐
```

```dockerfile
# Go 예시
FROM golang:1.27-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /out/app ./cmd/server

FROM scratch
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=build /out/app /app
USER 65534:65534
ENTRYPOINT ["/app"]
```

```
측정해 보기
golang:1.27-alpine 에 그대로 담기   →  약 250MB
alpine 베이스 + 바이너리            →  약 15MB
scratch + 정적 바이너리             →  약 8MB
```

**주의할 점**

```
□ scratch에는 셸이 없어서 docker exec 디버깅 불가 → 필요하면 distroless:debug
□ TLS를 쓴다면 CA 인증서 복사 필수
□ 타임존이 필요하면 tzdata 복사
□ CGO를 쓰면 정적 링크가 아니므로 scratch에서 안 돌아감
```

참고: [distroless](https://github.com/GoogleContainerTools/distroless) · Rust는 `rust:alpine`으로 빌드 후 동일 패턴

## 3-2. 테스트에서 진짜 DB 쓰기 (Testcontainers)

목(mock) 대신 실제 DB를 컨테이너로 띄워 테스트하는 방식입니다. CI에서도 동일하게 동작합니다.

```
왜 Docker인가
- SQLite로 대충 테스트하고 운영에서 Postgres 특성 때문에 터지는 일을 방지
- 테스트가 끝나면 컨테이너가 자동으로 정리됨
```

```js
// testcontainers-node 예시
import { PostgreSqlContainer } from "@testcontainers/postgresql";

let container, url;

beforeAll(async () => {
  container = await new PostgreSqlContainer("postgres:18-alpine").start();
  url = container.getConnectionUri();   // 임의 포트로 격리 실행
}, 60_000);

afterAll(async () => {
  await container.stop();
});
```

**연습 포인트**: 테스트 병렬 실행 시 포트 충돌이 없는 이유 이해하기, CI 러너에서 Docker 사용 설정

참고: [Testcontainers](https://testcontainers.com/) · [testcontainers-node](https://github.com/testcontainers/testcontainers-node) · [testcontainers-go](https://github.com/testcontainers/testcontainers-go)

## 3-3. 리버스 프록시 + 자동 HTTPS로 셀프호스팅

도메인을 하나 사서 VPS에 올려보는 연습입니다. 실제 배포의 전 과정을 압축해서 경험할 수 있습니다.

```
왜 Docker인가
- 앱·프록시·인증서 갱신을 컨테이너 조합으로 구성
- 서버를 갈아엎어도 compose.yaml 하나로 복구
```

```yaml
name: selfhost

services:
  caddy:
    image: caddy:alpine
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy-data:/data          # 발급받은 인증서 보관 (꼭 볼륨으로!)
      - caddy-config:/config

  app:
    image: ghcr.io/myorg/myapp:1.0
    restart: unless-stopped
    expose:
      - "3000"                    # 외부 노출 없이 프록시만 접근

volumes:
  caddy-data:
  caddy-config:
```

```
# Caddyfile
example.com {
    reverse_proxy app:3000
}
```

Caddy는 이 세 줄로 Let's Encrypt 인증서를 자동 발급·갱신합니다.

**연습 포인트**: 인증서 볼륨을 안 만들면 재시작마다 재발급되어 rate limit에 걸린다는 것, 헬스체크 기반 무중단 갱신

참고: [Caddy 이미지](https://hub.docker.com/_/caddy) · [Traefik](https://github.com/traefik/traefik) · [acme-companion](https://github.com/nginx-proxy/acme-companion)

# 4. 고급: 여러 개를 엮기

## 4-1. 모니터링 스택 직접 구성하기

```
왜 Docker인가
- Prometheus, Grafana, Loki, cAdvisor를 각각 설치하려면 하루가 걸림
- compose.yaml 하나로 전체 스택을 재현 가능
```

```
구성
cAdvisor   컨테이너 지표 수집
Prometheus 시계열 저장·쿼리
Loki       로그 저장
Promtail   로그 수집
Grafana    대시보드
```

**연습 포인트**: 메트릭 보존 기간 설정, 대시보드 JSON을 git에 버전 관리, 알림 규칙 작성

참고: [Prometheus](https://github.com/prometheus/prometheus) · [Grafana](https://github.com/grafana/grafana) · [Loki](https://github.com/grafana/loki) · [cAdvisor](https://github.com/google/cadvisor)

## 4-2. 홈랩 / 미디어 서버

집에 남는 PC나 미니 PC, NAS가 있다면 가장 재미있는 연습입니다.

| 앱 | 용도 |
|---|---|
| [Immich](https://github.com/immich-app/immich) | 사진 백업 (구글 포토 대체) |
| [Jellyfin](https://github.com/jellyfin/jellyfin) | 미디어 서버 |
| [Gitea](https://hub.docker.com/r/gitea/gitea) | 자체 git 호스팅 |
| [Uptime Kuma](https://github.com/louislam/uptime-kuma) | 서비스 모니터링·알림 |
| [Vaultwarden](https://github.com/dani-garcia/vaultwarden) | 비밀번호 관리 서버 |
| [Dozzle](https://github.com/amir20/dozzle) | 브라우저에서 컨테이너 로그 보기 |
| [Portainer](https://github.com/portainer/portainer) | 컨테이너 관리 UI |

```
연습하며 배우는 것
- 볼륨 백업·복구 전략 (데이터가 진짜 중요해짐)
- 컨테이너 간 네트워크 분리
- 업데이트 전략 (태그 고정 vs 자동 업데이트)
- 외부 노출 시 보안 (VPN, 인증 프록시)
```

주의: Dozzle이나 Portainer처럼 `docker.sock`을 요구하는 도구는 사실상 호스트 권한을 갖습니다. 외부에 노출하지 말고 내부망이나 VPN 뒤에서만 쓰세요.

## 4-3. 로컬 LLM 실행 환경

```
왜 Docker인가
- 모델 런타임과 UI를 조합해서 띄우기 좋음
- 모델 파일은 볼륨에 두고 컨테이너만 교체 가능
```

```yaml
name: local-llm

services:
  ollama:
    image: ollama/ollama
    volumes:
      - ollama:/root/.ollama      # 모델 파일 보존 (수 GB)
    ports:
      - "127.0.0.1:11434:11434"

  webui:
    image: ghcr.io/open-webui/open-webui:main
    ports:
      - "127.0.0.1:3000:8080"
    environment:
      OLLAMA_BASE_URL: http://ollama:11434
    volumes:
      - webui:/app/backend/data
    depends_on:
      - ollama

volumes:
  ollama:
  webui:
```

**연습 포인트**: 큰 볼륨 관리, GPU 패스스루(리눅스 + NVIDIA Container Toolkit), 메모리 제한과 OOM

참고: [Ollama](https://github.com/ollama/ollama) · [Open WebUI](https://github.com/open-webui/open-webui)

## 4-4. 마이크로서비스 흉내내기

```
구성 예
gateway   (nginx/Traefik)
  ├── auth-service   (Node)
  ├── order-service  (Go)
  └── user-service   (Python)
        └── 각자 DB + 공용 메시지 브로커(RabbitMQ/Redis)
```

```
연습하며 배우는 것
- 서비스 간 통신 (HTTP, gRPC, 메시지 큐)
- 네트워크 분리와 서비스 디스커버리
- 분산 추적 (OpenTelemetry + Jaeger)
- 여기까지 오면 왜 오케스트레이터가 필요한지 체감됨
```

혼자 연습할 때는 서비스 3개 정도가 적당합니다. 그 이상은 관리 비용만 늘고 배우는 게 크게 늘지 않습니다.

# 5. 무엇을 만들든 챙길 것들

어떤 프로젝트를 하든 아래 항목을 체크하면 "돌아가는 것"에서 "쓸 만한 것"이 됩니다.

```
이미지
  □ .dockerignore 작성 (빌드 컨텍스트 크기 확인)
  □ 멀티스테이지로 빌드 도구 제외
  □ 레이어 순서: 의존성 먼저, 소스 나중
  □ 베이스 이미지 버전 고정
  □ USER 로 비root 실행

실행
  □ healthcheck 작성
  □ 메모리·CPU 제한
  □ 로그 로테이션 (max-size, max-file)
  □ 재시작 정책
  □ 데이터는 볼륨에, 비밀값은 secrets/환경변수 주입

운영
  □ compose.yaml 하나로 clone 후 실행 가능한가
  □ 볼륨 백업 방법이 있는가
  □ 이미지 크기와 빌드 시간을 측정해 봤는가
  □ 서버를 잃어도 30분 안에 복구 가능한가
```

## 정리

- 입문은 정적 사이트 배포와 개발용 DB 스택. 손에 익히는 데 가장 빠름
- 초급은 내 앱(Node/Python) 컨테이너화. 멀티스테이지와 `.dockerignore`가 핵심
- 중급은 초경량 이미지(scratch/distroless), Testcontainers, 리버스 프록시 + 자동 HTTPS
- 고급은 모니터링 스택, 홈랩, 로컬 LLM, 마이크로서비스 흉내내기
- 실제 오픈소스의 Dockerfile과 compose.yaml을 읽는 것이 가장 좋은 교재
- 무엇을 만들든 비root 실행, healthcheck, 자원 제한, 로그 로테이션, 볼륨 백업은 챙기기
