# 라이프타임 (Lifetime) - 참조가 얼마나 오래 유효한가

## 들어가며

[참조와 빌림](../2-기초개념/02-참조와-빌림.md)에서 "참조는 항상 유효해야 한다"는 규칙을 봤습니다. 컴파일러가 이 규칙을 검사하려면 **각 참조가 언제까지 유효한지** 알아야 하는데, 이것이 라이프타임입니다.

```
대부분의 경우   → 컴파일러가 알아서 추론 (생략 규칙)
애매한 경우     → 개발자가 'a 같은 라이프타임 매개변수로 "관계"를 알려줌
```

중요한 오해 하나를 먼저 정리합니다.

```
❌ 라이프타임 표기가 값의 수명을 늘리거나 바꾼다
✅ 라이프타임 표기는 여러 참조의 수명 사이의 "관계"를 컴파일러에게 설명할 뿐이다
```

# 1. 라이프타임이 왜 필요한가

## 댕글링 참조

```rust
// ❌ 컴파일 에러 예제
fn main() {
    let r;
    {
        let x = 5;
        r = &x;
    } // x 가 여기서 사라짐
    println!("r: {r}"); // r 은 사라진 x 를 가리킴
}
```

```
error[E0597]: `x` does not live long enough
```

빌림 검사기는 스코프를 비교합니다.

```
    let r;                // ---------+-- 'a (r 의 수명)
    {                     //          |
        let x = 5;        // -+-- 'b  |  (x 의 수명)
        r = &x;           //  |       |
    }                     // -+       |
    println!("r: {r}");   //          |  ← 'b 가 끝났는데 r 을 사용
                          // ---------+
```

참조 `r`(수명 `'a`)이 가리키는 대상 `x`(수명 `'b`)보다 오래 살아서 거부됩니다.

## 함수 시그니처에서 애매해지는 경우

```rust
// ❌ 컴파일 에러 예제
fn longest(x: &str, y: &str) -> &str {
    if x.len() > y.len() { x } else { y }
}

fn main() {
    println!("{}", longest("ab", "abc"));
}
```

```
error[E0106]: missing lifetime specifier
 --> src/main.rs:2:33
  |
2 | fn longest(x: &str, y: &str) -> &str {
  |               ----     ----     ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but the signature does not say whether it is borrowed from `x` or `y`
help: consider introducing a named lifetime parameter
  |
2 | fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
  |           ++++     ++          ++          ++
```

반환된 참조가 `x`에서 온 건지 `y`에서 온 건지 컴파일러가 시그니처만으로는 알 수 없습니다. 함수 본문은 보지 않습니다 (시그니처가 계약이기 때문).

# 2. 라이프타임 표기

## 문법

```rust
// &i32         참조
// &'a i32      명시적 라이프타임을 가진 참조
// &'a mut i32  명시적 라이프타임을 가진 가변 참조

// "반환값은 x 와 y 둘 다 살아있는 동안(둘 중 짧은 쪽)만큼 유효하다"
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

fn main() {
    let string1 = String::from("long string is long");
    {
        let string2 = String::from("xyz");
        let result = longest(string1.as_str(), string2.as_str());
        println!("가장 긴 문자열: {result}"); // OK: string2 가 살아있는 동안 사용
    }
}
```

`'a`는 제네릭 매개변수처럼 선언하며, 호출 시점에 **x와 y의 수명 중 겹치는 구간**으로 구체화됩니다.

## 계약을 어기면

```rust
// ❌ 컴파일 에러 예제
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

fn main() {
    let string1 = String::from("long string is long");
    let result;
    {
        let string2 = String::from("xyz");
        result = longest(string1.as_str(), string2.as_str());
    } // string2 drop
    println!("가장 긴 문자열: {result}"); // result 는 string2 만큼만 유효할 수 있음
}
```

```
error[E0597]: `string2` does not live long enough
```

실제로는 `string1`이 더 길어서 반환되겠지만, 컴파일러는 **시그니처의 계약**만 보고 판단합니다.

## 관계가 없는 매개변수

```rust
// 반환값이 x 에서만 오면 y 에는 라이프타임을 연결하지 않음
fn first<'a>(x: &'a str, _y: &str) -> &'a str {
    x
}

fn main() {
    let a = String::from("hello");
    let r;
    {
        let b = String::from("temp");
        r = first(&a, &b);
    }
    println!("{r}"); // OK: r 은 a 에만 묶여 있음
}
```

# 3. 라이프타임 생략 규칙 (Elision)

대부분의 함수에 라이프타임을 안 적어도 되는 이유는 컴파일러가 다음 규칙을 적용하기 때문입니다.

```
규칙 1: 참조인 매개변수마다 각자 다른 라이프타임을 부여한다
        fn foo(x: &str, y: &str)  →  fn foo<'a, 'b>(x: &'a str, y: &'b str)

규칙 2: 입력 라이프타임이 딱 하나면, 모든 출력 라이프타임에 그걸 쓴다
        fn foo(x: &str) -> &str  →  fn foo<'a>(x: &'a str) -> &'a str

규칙 3: 메서드에서 &self 나 &mut self 가 있으면, 출력 라이프타임은 self 의 것
        fn foo(&self, x: &str) -> &str  →  반환값은 self 에 묶임

세 규칙을 적용한 뒤에도 출력 라이프타임이 정해지지 않으면 → 직접 적어야 함
```

```rust
struct Parser {
    input: String,
}

impl Parser {
    // 규칙 3: 반환값은 &self 에 묶임 (표기 생략 가능)
    fn first_token(&self, _sep: &str) -> &str {
        self.input.split_whitespace().next().unwrap_or("")
    }
}

// 규칙 2
fn trim_prefix(s: &str) -> &str {
    s.trim_start_matches('#')
}

fn main() {
    let p = Parser { input: "let x = 5".into() };
    println!("{} {}", p.first_token(" "), trim_prefix("##title"));
}
```

# 4. 구조체의 라이프타임

구조체가 **참조를 필드로 가지면** 반드시 라이프타임을 명시해야 합니다. "이 구조체 인스턴스는 필드가 가리키는 데이터보다 오래 살 수 없다"는 뜻입니다.

```rust
#[derive(Debug)]
struct Highlight<'a> {
    part: &'a str,
}

impl<'a> Highlight<'a> {
    fn new(text: &'a str) -> Self {
        let part = text.split('.').next().unwrap_or(text);
        Highlight { part }
    }

    fn len(&self) -> usize {
        self.part.len()
    }

    // 반환값을 self 가 아니라 원본 데이터('a)에 묶기
    fn part(&self) -> &'a str {
        self.part
    }
}

fn main() {
    let novel = String::from("Call me Ishmael. Some years ago...");
    let h = Highlight::new(&novel);
    println!("{h:?} {}", h.len());

    let p = h.part();
    drop(h);          // Highlight 가 사라져도
    println!("{p}");  // p 는 novel 에 묶여 있으므로 사용 가능
}
```

## 참조를 가진 구조체 vs 소유하는 구조체

```
struct User<'a> { name: &'a str }   → 복사 없이 빠름. 원본보다 오래 못 삶. 사용이 번거로움
struct User { name: String }        → 복사 비용. 독립적. 다루기 쉬움
```

처음에는 **소유하는 구조체(String, Vec)**를 기본으로 쓰고, 성능이 중요한 파서나 뷰(view) 타입에서만 참조를 가진 구조체를 쓰는 것이 좋습니다.

# 5. 'static 라이프타임

`'static`은 **프로그램 전체 기간 동안 유효할 수 있는** 참조입니다.

```rust
fn get_message() -> &'static str {
    "문자열 리터럴은 바이너리에 저장되어 항상 'static"
}

static GREETING: &str = "안녕";

fn main() {
    println!("{} {GREETING}", get_message());

    // Box::leak 으로 런타임에 'static 참조 만들기 (의도적으로 메모리를 해제하지 않음)
    let config: &'static str = Box::leak(String::from("런타임 설정").into_boxed_str());
    println!("{config}");
}
```

## T: 'static 의 진짜 의미

```rust
use std::fmt::Debug;
use std::thread;

// T: 'static = "T 안에 'static 이 아닌 참조가 없다" (소유 타입은 모두 만족)
fn spawn_print<T: Debug + Send + 'static>(value: T) {
    thread::spawn(move || println!("{value:?}")).join().unwrap();
}

fn main() {
    spawn_print(String::from("소유한 String 은 'static 을 만족")); // OK
    spawn_print(vec![1, 2, 3]);                                    // OK
    spawn_print("리터럴");                                          // OK

    let local = String::from("local");
    // spawn_print(&local); // ❌ &local 은 'static 이 아님 (local 이 먼저 사라질 수 있음)
    spawn_print(local.clone());
}
```

```
&'static T   → 프로그램 끝까지 유효한 참조 (리터럴, static, leak)
T: 'static   → T 가 빌린 데이터를 포함하지 않는다 (String, Vec<i32> 등 소유 타입 전부 OK)
```

컴파일러가 "`'static`이 필요하다"고 할 때 무작정 `'static`을 붙이지 말고, **소유한 값을 넘기거나 `move` / `clone` / `Arc`**를 쓰는 것이 보통 올바른 해결입니다.

# 6. 조금 더 깊이

## 라이프타임 바운드

```rust
use std::fmt::Display;

// 'b 는 최소한 'a 만큼 산다 ('b: 'a)
fn pick<'a, 'b: 'a>(x: &'a str, y: &'b str, use_y: bool) -> &'a str {
    if use_y { y } else { x }
}

// 제네릭 T 가 'a 보다 오래 살아야 함
struct Ref<'a, T: 'a> {
    value: &'a T,
}

// 제네릭 + 라이프타임 + 트레이트 바운드 함께
fn longest_with_note<'a, T>(x: &'a str, y: &'a str, note: T) -> &'a str
where
    T: Display,
{
    println!("참고: {note}");
    if x.len() > y.len() { x } else { y }
}

fn main() {
    println!("{}", pick("a", "b", true));
    let n = 5;
    let r = Ref { value: &n };
    println!("{}", r.value);
    println!("{}", longest_with_note("hi", "hello", 42));
}
```

## 익명 라이프타임 '_

```rust
struct Wrapper<'a> {
    text: &'a str,
}

// impl 블록에서 라이프타임 이름이 필요 없으면 '_
impl Wrapper<'_> {
    fn show(&self) {
        println!("{}", self.text);
    }
}

// 반환 타입에 "빌린 것이 있다"는 사실을 드러내기
fn make(text: &str) -> Wrapper<'_> {
    Wrapper { text }
}

fn main() {
    make("hello").show();
}
```

## 고차 트레이트 바운드 (HRTB) 맛보기

```rust
// "어떤 라이프타임 'a 에 대해서든" &'a str 을 받는 클로저
fn apply_to_all<F>(items: &[String], f: F)
where
    F: for<'a> Fn(&'a str) -> &'a str,
{
    for s in items {
        println!("{}", f(s));
    }
}

fn main() {
    let items = vec!["  hi  ".to_string(), " rust ".to_string()];
    apply_to_all(&items, |s| s.trim());
}
```

`for<'a>`는 대부분 컴파일러가 자동으로 처리해서 직접 쓸 일은 드물지만, 라이브러리 코드나 에러 메시지에서 볼 수 있습니다.

## 라이프타임 에러를 만났을 때 체크리스트

```
1. 스코프가 끝나는 지역 변수의 참조를 반환하려는가?  → 소유 값(String, Vec)을 반환
2. 구조체에 참조를 저장하고 있는가?                → 소유 타입으로 바꿀 수 있는지 검토
3. 스레드/비동기 태스크로 참조를 넘기는가?           → move + 소유 값 / Arc
4. 반환값이 어느 인자에서 오는지 시그니처에 드러났는가? → 'a 로 관계 명시
5. 정말 성능 때문에 참조가 필요한가?                → 아니라면 clone 도 괜찮은 선택
```

## 정리

- 라이프타임은 참조가 유효한 범위이며, 컴파일러는 이를 비교해 댕글링 참조를 막는다
- `'a` 표기는 수명을 바꾸지 않고 **참조들 사이의 관계**만 설명한다
- 생략 규칙 3가지 덕분에 대부분은 표기가 필요 없다
- 참조를 필드로 가진 구조체는 라이프타임 매개변수가 필요하다
- `&'static T`는 프로그램 끝까지 유효한 참조, `T: 'static`은 빌린 데이터를 포함하지 않는 타입
- 라이프타임 에러는 대부분 "소유 값으로 바꾸기"로 해결된다
