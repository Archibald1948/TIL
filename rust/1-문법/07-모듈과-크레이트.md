# 모듈과 크레이트 - 코드를 나누고 공개 범위 정하기

## 들어가며

프로젝트가 커지면 코드를 여러 파일로 나눠야 합니다. Rust의 모듈 시스템은 JS의 `import/export`와 개념은 비슷하지만 **파일이 자동으로 모듈이 되지 않는다**는 점이 가장 크게 다릅니다.

```
JS/TS
- 파일 하나 = 모듈 하나 (자동)
- export 한 것만 공개
- import { x } from './a'

Rust
- mod a; 로 "선언"해야 모듈 트리에 포함됨
- 기본이 비공개(private), pub 붙인 것만 공개
- use crate::a::x;
```

# 1. 용어 정리

```
패키지(package)  → Cargo.toml 이 있는 단위. cargo new 로 만드는 것
크레이트(crate)  → 컴파일 단위. 바이너리 크레이트 또는 라이브러리 크레이트
                  - src/main.rs → 바이너리 크레이트 루트
                  - src/lib.rs  → 라이브러리 크레이트 루트
                  - 한 패키지에 라이브러리는 최대 1개, 바이너리는 여러 개
모듈(module)     → 크레이트 안에서 코드를 묶는 네임스페이스 + 공개 범위 단위
경로(path)       → 아이템을 가리키는 이름 (crate::net::client::connect)
```

crates.io에서 받는 `serde`, `tokio` 등이 모두 **라이브러리 크레이트**입니다.

# 2. 모듈 정의

## 인라인 모듈

```rust
mod front_of_house {
    pub mod hosting {
        pub fn add_to_waitlist() {
            println!("대기 명단 추가");
            seat_at_table(); // 같은 모듈 안이라 비공개 함수 호출 가능
        }

        fn seat_at_table() {
            println!("자리 안내");
        }
    }

    mod serving {
        #[allow(dead_code)]
        fn take_order() {}
    }
}

fn main() {
    // 절대 경로
    crate::front_of_house::hosting::add_to_waitlist();
    // 상대 경로
    front_of_house::hosting::add_to_waitlist();

    // front_of_house::serving::take_order(); // ❌ 컴파일 에러: module `serving` is private
}
```

모듈 트리:

```
crate
 └── front_of_house
     ├── hosting
     │   ├── add_to_waitlist (pub)
     │   └── seat_at_table
     └── serving
         └── take_order
```

## 공개 범위 규칙

- 모든 아이템(함수, 구조체, 모듈, 상수...)은 **기본 비공개**
- 자식 모듈은 부모의 비공개 아이템을 볼 수 있음
- 부모는 자식의 비공개 아이템을 볼 수 없음
- 형제 아이템끼리는 서로 볼 수 있음

## pub의 세부 단계

```rust
mod network {
    pub mod client {
        pub fn connect() {
            super::helper();          // super: 부모 모듈
            self::retry();            // self: 현재 모듈
        }
        fn retry() {}

        pub(crate) fn internal_api() {}  // 크레이트 안에서만 공개
        pub(super) fn parent_only() {}   // 부모 모듈까지만 공개
    }

    fn helper() {
        client::parent_only();
    }
}

fn main() {
    network::client::connect();
    network::client::internal_api();
}
```

| 표기 | 공개 범위 |
|---|---|
| (없음) | 현재 모듈과 그 자식 |
| `pub` | 어디서나 (외부 크레이트 포함, 경로상 모듈도 공개여야 함) |
| `pub(crate)` | 현재 크레이트 전체 |
| `pub(super)` | 부모 모듈 |
| `pub(in crate::a::b)` | 지정한 경로 |

## 구조체와 열거형의 공개

```rust
mod shop {
    pub struct Breakfast {
        pub toast: String,        // 필드마다 따로 pub 필요
        seasonal_fruit: String,   // 비공개
    }

    impl Breakfast {
        // 비공개 필드가 있으면 외부에서 직접 생성 불가 → 생성자 제공
        pub fn summer(toast: &str) -> Breakfast {
            Breakfast {
                toast: String::from(toast),
                seasonal_fruit: String::from("복숭아"),
            }
        }

        pub fn fruit(&self) -> &str {
            &self.seasonal_fruit
        }
    }

    // enum 은 pub 이면 모든 variant 가 공개
    pub enum Appetizer {
        Soup,
        Salad,
    }
}

fn main() {
    let mut meal = shop::Breakfast::summer("호밀빵");
    meal.toast = String::from("통밀빵");
    // meal.seasonal_fruit = String::from("딸기"); // ❌ field `seasonal_fruit` of struct `Breakfast` is private
    println!("{} / {}", meal.toast, meal.fruit());

    let _a = shop::Appetizer::Soup;
    let _b = shop::Appetizer::Salad;
}
```

비공개 필드 + 생성자 조합으로 **불변식(invariant)**을 지킬 수 있습니다. 예를 들어 `Email` 구조체를 검증된 값으로만 만들 수 있게 강제하는 식입니다.

# 3. use - 경로를 스코프로 가져오기

```rust
use std::collections::HashMap;
use std::fmt::Result;
use std::io::Result as IoResult;               // 이름 충돌 시 as 로 별칭
use std::io::{self, Read, Write};              // 중첩 경로 (self = std::io 자체)
use std::collections::{BTreeMap, HashSet};

fn main() {
    let mut map = HashMap::new();
    map.insert(1, 2);
    let _set: HashSet<i32> = HashSet::new();
    let _tree: BTreeMap<i32, i32> = BTreeMap::new();
    println!("{map:?}");

    fn _f() -> Result { Ok(()) }
    fn _g() -> IoResult<()> { Ok(()) }
    let _ = io::stdout().flush();
    let _: Option<&dyn Read> = None;
}
```

## 관례

```rust
// 함수는 부모 모듈까지만 가져와서 출처를 드러냄
use std::fs;
// fs::read_to_string("a.txt")

// 구조체, 열거형, 트레이트는 전체 경로로 가져옴
use std::collections::HashMap;
// HashMap::new()

// glob (*) 은 테스트 모듈이나 prelude 에서만 주로 사용
// use super::*;

fn main() {
    let _ = fs::metadata(".");
    let _m: HashMap<i32, i32> = HashMap::new();
}
```

## pub use - 다시 내보내기 (re-export)

내부 구조와 공개 API 구조를 분리할 때 씁니다. JS의 `export { x } from './x'`와 같습니다.

```rust
mod internal {
    pub mod deeply {
        pub mod nested {
            pub fn useful() -> &'static str {
                "유용한 함수"
            }
        }
    }
}

// 사용자는 crate::useful 로 바로 쓸 수 있음
pub use internal::deeply::nested::useful;

fn main() {
    println!("{}", useful());
}
```

# 4. 파일로 모듈 나누기

## 파일 구조

`mod network;`를 선언하면 컴파일러는 `src/network.rs` 또는 `src/network/mod.rs`를 찾습니다. 예전에는 `mod.rs` 방식을 썼지만, 에디터 탭에 `mod.rs`가 여러 개 떠서 헷갈리기 때문에 Rust 2018부터는 **디렉터리와 같은 이름의 파일**을 두는 방식을 권장합니다.

```
src/
├── main.rs
├── config.rs
├── network.rs         ← network 모듈 본문
└── network/
    ├── client.rs      ← network::client
    └── server.rs      ← network::server
```

```rust
// (컴파일 검증 제외) - 여러 파일에 걸친 예시

// src/main.rs
mod config;    // src/config.rs 를 찾아 모듈 트리에 포함
mod network;   // src/network.rs 를 찾음

use network::client::Client;

fn main() {
    let cfg = config::load();
    let c = Client::new(&cfg.host);
    c.send("ping");
}

// src/config.rs
pub struct Config {
    pub host: String,
}

pub fn load() -> Config {
    Config { host: "localhost".into() }
}

// src/network.rs
pub mod client;   // src/network/client.rs
pub mod server;   // src/network/server.rs

// src/network/client.rs
pub struct Client {
    host: String,
}

impl Client {
    pub fn new(host: &str) -> Self {
        Self { host: host.to_string() }
    }
    pub fn send(&self, msg: &str) {
        println!("{} <- {msg}", self.host);
    }
}
```

**핵심**: `mod xxx;`는 "파일을 import"하는 게 아니라 **"모듈 트리에 이 모듈을 등록"**하는 선언입니다. 크레이트 전체에서 한 번만 선언하고, 다른 곳에서는 `use`로 경로를 가져옵니다.

자주 하는 실수: `client.rs` 파일만 만들고 어디에도 `mod client;`를 선언하지 않으면 그 파일은 **아예 컴파일되지 않습니다.**

## lib.rs + main.rs 패턴

바이너리 프로젝트도 로직은 `lib.rs`에 두고 `main.rs`는 얇게 유지하는 것이 좋습니다. 통합 테스트(`tests/`)는 라이브러리 크레이트만 가져올 수 있기 때문입니다.

```rust
// (컴파일 검증 제외)

// src/lib.rs
pub mod parser;
pub fn run(input: &str) -> usize {
    parser::count_words(input)
}

// src/main.rs  (패키지 이름이 my_app 이라면)
fn main() {
    let n = my_app::run("hello world");
    println!("{n}");
}
```

# 5. 외부 크레이트 사용

```bash
cargo add rand
```

```rust
// 외부 크레이트 rand 필요
use rand::RngExt; // rand 0.10 기준 (0.9 이하는 rand::Rng)

fn main() {
    let n: u32 = rand::rng().random_range(1..=100);
    println!("{n}");
}
```

- `Cargo.toml`의 `[dependencies]`에 넣으면 크레이트 이름으로 바로 경로를 쓸 수 있습니다. (`extern crate`는 2018 에디션부터 불필요)
- 패키지 이름의 `-`는 코드에서 `_`로 바뀝니다. (`serde-json` → `serde_json`)
- `std`도 하나의 크레이트이며, 자주 쓰는 것들(`Vec`, `String`, `Option`, `Result`, `Box` 등)은 **prelude**로 자동 `use`되어 있습니다.

# 6. 자주 쓰는 속성

```rust
#![allow(unused)]              // 크레이트 전체 (파일 맨 위, ! 붙음)

#[cfg(target_os = "macos")]    // macOS에서만 컴파일
fn platform() -> &'static str { "mac" }

#[cfg(not(target_os = "macos"))]
fn platform() -> &'static str { "other" }

#[deprecated(note = "new_api 를 사용하세요")]
fn old_api() {}

#[cfg(test)]                   // cargo test 할 때만 컴파일
mod tests {
    use super::*;

    #[test]
    fn it_works() {
        assert!(!platform().is_empty());
    }
}

fn main() {
    println!("{}", platform());
}
```

## 정리

- 패키지 ⊃ 크레이트 ⊃ 모듈. 크레이트 루트는 `main.rs` 또는 `lib.rs`
- 모든 아이템은 기본 비공개, `pub` / `pub(crate)` / `pub(super)`로 범위 조정
- 구조체는 필드별로 `pub`, enum은 `pub`이면 variant 전체 공개
- `mod x;`는 모듈 등록 선언(한 번만), `use`는 경로를 가져오는 것
- 파일 분리 시 `src/a.rs` + `src/a/b.rs` 구조가 현재 권장
- `pub use`로 내부 구조와 공개 API를 분리
