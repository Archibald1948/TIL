# 에러 처리 - 예외 대신 Result

## 들어가며

Rust에는 `try/catch`와 예외(exception)가 없습니다. 대신 에러를 두 종류로 나눕니다.

```
복구 불가능한 에러 → panic!        (버그. 배열 범위 초과, 불변식 위반 등)
복구 가능한 에러   → Result<T, E>  (파일 없음, 네트워크 실패, 파싱 실패 등)
```

JS/TS와 비교하면:

```ts
// TS: 함수 시그니처만 보고는 에러를 던지는지 알 수 없음
function parse(s: string): number { ... throw new Error() ... }
```

```
// Rust: 실패할 수 있다는 사실이 타입에 드러남. 처리하지 않으면 경고/에러
fn parse(s: &str) -> Result<i32, ParseIntError>
```

# 1. panic!

```rust
fn main() {
    let v = vec![1, 2, 3];

    let idx = 99;
    if idx < v.len() {
        println!("{}", v[idx]);
    }

    // 아래 줄들은 모두 panic 을 일으킴
    // v[99];
    // panic!("직접 발생: {}", 42);
    // None::<i32>.unwrap();
    // unreachable!("여기 오면 버그");
    // todo!("아직 구현 안 함");
}
```

```bash
# 백트레이스 보기
RUST_BACKTRACE=1 cargo run
```

- panic이 발생하면 기본적으로 스택을 되감으며(unwind) 값들을 drop하고 해당 스레드가 종료됩니다.
- `Cargo.toml`에 `panic = "abort"`를 주면 되감기 없이 즉시 종료합니다.
- **라이브러리 코드에서 입력값 때문에 panic하는 것은 나쁜 습관**입니다. 호출자가 처리할 수 있게 `Result`를 반환하세요.

# 2. Result<T, E>

## 정의

```rust
// 표준 라이브러리 정의 (prelude 포함)
// enum Result<T, E> {
//     Ok(T),
//     Err(E),
// }

use std::fs::File;
use std::io::ErrorKind;

fn main() {
    let result = File::open("hello.txt");

    let _file = match result {
        Ok(file) => file,
        Err(e) => match e.kind() {
            ErrorKind::NotFound => {
                println!("파일이 없어서 생성합니다");
                match File::create("/tmp/hello_rust_til.txt") {
                    Ok(fc) => fc,
                    Err(e) => panic!("생성 실패: {e:?}"),
                }
            }
            other => panic!("열기 실패: {other:?}"),
        },
    };
}
```

match 중첩은 장황하므로 실무에서는 아래의 `?`와 조합 메서드를 씁니다.

## unwrap과 expect

```rust
fn main() {
    let n: i32 = "42".parse().unwrap();                  // Err 이면 panic
    let m: i32 = "7".parse().expect("숫자여야 합니다");   // panic 메시지 지정
    println!("{n} {m}");
}
```

```
unwrap / expect 를 써도 되는 곳
- 프로토타입, 예제 코드, 테스트
- 논리적으로 절대 실패하지 않는 경우 (expect 에 이유를 적기)
  예) "127.0.0.1".parse::<IpAddr>().expect("하드코딩된 IP는 항상 유효")

프로덕션 코드에서는 가급적 ? 로 전파하거나 명시적으로 처리
```

# 3. ? 연산자 - 에러 전파

`?`는 "`Ok`면 값을 꺼내고, `Err`면 즉시 함수에서 그 에러를 반환"합니다.

```rust
use std::fs;
use std::io;

// ? 없이
fn read_username_verbose(path: &str) -> Result<String, io::Error> {
    let content = match fs::read_to_string(path) {
        Ok(c) => c,
        Err(e) => return Err(e),
    };
    Ok(content.trim().to_string())
}

// ? 사용
fn read_username(path: &str) -> Result<String, io::Error> {
    let content = fs::read_to_string(path)?;
    Ok(content.trim().to_string())
}

fn main() {
    match read_username("/definitely/not/exists.txt") {
        Ok(name) => println!("이름: {name}"),
        Err(e) => println!("에러: {e}"),
    }
    let _ = read_username_verbose("x");
}
```

- `?`는 **반환 타입이 `Result`(또는 `Option`)인 함수 안에서만** 쓸 수 있습니다.
- `?`는 에러를 반환하기 전에 `From::from`을 호출해서 **에러 타입을 자동 변환**합니다. (아래 4장)

## Option에도 ? 사용

```rust
fn last_char_of_first_line(text: &str) -> Option<char> {
    text.lines().next()?.chars().last()
}

fn main() {
    println!("{:?}", last_char_of_first_line("Hello\nWorld")); // Some('o')
    println!("{:?}", last_char_of_first_line(""));             // None
}
```

## main에서 Result 반환

```rust
use std::error::Error;

fn main() -> Result<(), Box<dyn Error>> {
    let n: i32 = "123".parse()?;
    println!("{n}");
    Ok(())
    // Err 를 반환하면 에러를 Debug 형식으로 출력하고 종료 코드 1 로 끝남
}
```

# 4. 커스텀 에러 타입

## enum으로 에러 정의

```rust
use std::fmt;
use std::num::ParseIntError;

#[derive(Debug)]
enum ConfigError {
    Missing(String),
    InvalidPort(ParseIntError),
    OutOfRange(u32),
}

// 사람이 읽을 메시지
impl fmt::Display for ConfigError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            ConfigError::Missing(key) => write!(f, "설정 누락: {key}"),
            ConfigError::InvalidPort(e) => write!(f, "포트 파싱 실패: {e}"),
            ConfigError::OutOfRange(p) => write!(f, "포트 범위 초과: {p}"),
        }
    }
}

// 표준 에러 트레이트 구현 (source 로 원인 에러 연결)
impl std::error::Error for ConfigError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        match self {
            ConfigError::InvalidPort(e) => Some(e),
            _ => None,
        }
    }
}

// ? 가 ParseIntError 를 ConfigError 로 자동 변환하게 함
impl From<ParseIntError> for ConfigError {
    fn from(e: ParseIntError) -> Self {
        ConfigError::InvalidPort(e)
    }
}

fn parse_port(value: Option<&str>) -> Result<u16, ConfigError> {
    let raw = value.ok_or_else(|| ConfigError::Missing("PORT".into()))?;
    let n: u32 = raw.parse()?; // ParseIntError → ConfigError (From 덕분)
    if n > 65535 {
        return Err(ConfigError::OutOfRange(n));
    }
    Ok(n as u16)
}

fn main() {
    for input in [Some("8080"), None, Some("abc"), Some("70000")] {
        match parse_port(input) {
            Ok(p) => println!("포트: {p}"),
            Err(e) => println!("에러: {e}"),
        }
    }
}
```

## Box<dyn Error> - 여러 에러를 간단히 묶기

```rust
use std::error::Error;
use std::fs;

fn load_number(path: &str) -> Result<i64, Box<dyn Error>> {
    let text = fs::read_to_string(path)?; // io::Error
    let n = text.trim().parse::<i64>()?;  // ParseIntError
    if n < 0 {
        return Err("음수는 허용되지 않습니다".into()); // &str → Box<dyn Error>
    }
    Ok(n)
}

fn main() {
    if let Err(e) = load_number("/no/such/file") {
        println!("실패: {e}");
    }
}
```

어떤 에러인지 호출자가 구분할 필요가 없을 때 편리합니다. 구분이 필요하면 `e.downcast_ref::<io::Error>()`로 확인할 수 있지만, 그럴 땐 enum이 더 낫습니다.

# 5. thiserror와 anyhow

위의 `Display`, `Error`, `From` 구현은 반복적이라 실무에서는 두 크레이트를 주로 씁니다.

```
thiserror → 라이브러리용. 호출자가 에러 종류를 match 할 수 있는 구체적인 enum 을 derive 로 생성
anyhow    → 애플리케이션용. 어떤 에러든 anyhow::Error 하나로 받고 context 를 덧붙임
```

```bash
cargo add thiserror anyhow
```

```rust
// (컴파일 검증: 외부 크레이트) thiserror 2, anyhow 1
use thiserror::Error;

#[derive(Debug, Error)]
pub enum DbError {
    #[error("연결 실패: {0}")]
    Connection(String),

    #[error("레코드를 찾을 수 없음 (id={id})")]
    NotFound { id: u64 },

    #[error("I/O 에러")]
    Io(#[from] std::io::Error), // From 자동 구현 + source 연결
}

fn find(id: u64) -> Result<String, DbError> {
    if id == 0 {
        return Err(DbError::NotFound { id });
    }
    Ok(format!("user-{id}"))
}

// 애플리케이션 레이어: anyhow
use anyhow::{Context, Result, bail};

fn run() -> Result<()> {
    let user = find(0).context("사용자 조회 중 실패")?;
    if user.is_empty() {
        bail!("빈 사용자");
    }
    let _cfg = std::fs::read_to_string("config.toml")
        .with_context(|| "config.toml 을 읽을 수 없음")?;
    Ok(())
}

fn main() {
    if let Err(e) = run() {
        // {:#} 로 출력하면 context 체인이 한 줄로: "사용자 조회 중 실패: 레코드를 찾을 수 없음 (id=0)"
        eprintln!("{e:#}");
    }
}
```

# 6. Result/Option 조합 메서드

```rust
fn main() {
    let good: Result<i32, String> = Ok(2);
    let bad: Result<i32, String> = Err("실패".into());

    println!("{:?}", good.clone().map(|x| x * 10));              // Ok(20)
    println!("{:?}", bad.clone().map_err(|e| format!("[E] {e}"))); // Err("[E] 실패")
    println!("{}", bad.clone().unwrap_or(0));                    // 0
    println!("{}", bad.clone().unwrap_or_default());             // 0
    println!("{:?}", good.clone().and_then(|x| if x > 1 { Ok(x) } else { Err("작음".into()) }));
    println!("{:?}", good.clone().ok());                         // Some(2) - Result → Option
    println!("{}", good.is_ok());

    let name: Option<&str> = None;
    println!("{:?}", name.ok_or("이름 없음"));                   // Err("이름 없음") - Option → Result
    println!("{}", name.map_or(0, |n| n.len()));                 // 0
    println!("{:?}", Some(3).filter(|x| x % 2 == 0));            // None
    println!("{:?}", None.or(Some(9)));                          // Some(9)

    // 여러 Result 를 한 번에: 하나라도 Err 면 첫 Err
    let all: Result<Vec<i32>, _> = ["1", "2", "3"].iter().map(|s| s.parse::<i32>()).collect();
    let some_bad: Result<Vec<i32>, _> = ["1", "x"].iter().map(|s| s.parse::<i32>()).collect();
    println!("{all:?} {}", some_bad.is_err());
}
```

| 메서드 | 용도 |
|---|---|
| `map` | 성공 값 변환 |
| `map_err` | 에러 값 변환 |
| `and_then` | 실패할 수 있는 다음 작업 연결 (flatMap) |
| `unwrap_or` / `unwrap_or_else` / `unwrap_or_default` | 실패 시 기본값 |
| `ok()` / `ok_or()` | Result ↔ Option 변환 |
| `?` | 에러 전파 |

# 7. 언제 panic, 언제 Result?

```
panic 이 적절한 경우
- 코드의 버그를 의미하는 상황 (도달하면 안 되는 분기, 깨진 불변식)
- 테스트 코드
- 계속 실행하면 더 위험한 상황

Result 가 적절한 경우
- 실패가 예상 가능한 상황 (사용자 입력, 파일, 네트워크, 파싱)
- 라이브러리의 공개 API
```

## 정리

- 복구 불가능하면 `panic!`, 복구 가능하면 `Result<T, E>`
- `?`로 에러를 호출자에게 전파, `From` 구현이 있으면 에러 타입 자동 변환
- `unwrap`/`expect`는 예제·테스트·절대 실패하지 않는 곳에서만
- 라이브러리는 구체적인 에러 enum (`thiserror`), 애플리케이션은 `anyhow` + `context`
- `map`, `map_err`, `and_then`, `ok_or` 등 조합 메서드로 match를 줄인다
