# 메모리 관리와 GC - 스택, 힙, 탈출 분석, 그리고 pprof

## 들어가며

Go는 GC가 있는 언어라 `malloc`/`free`를 직접 하지 않습니다. 그래도 서버가 커지면 이런 문제를 만나게 됩니다.

```
- 응답 지연(p99 latency)이 가끔 튄다
- 컨테이너 메모리 제한에 걸려서 OOMKilled
- CPU 사용률의 상당 부분이 GC
- 메모리가 계속 조금씩 늘어난다 (누수?)
```

이 문서는 **"Go가 메모리를 어떻게 다루는지 이해하고, 측정하고, 개선하는 방법"** 을 다룹니다.

```
1. 스택과 힙, 탈출 분석 → 어디에 할당되는가
2. GC 동작과 튜닝 (GOGC, GOMEMLIMIT)
3. 프로파일링 (pprof, trace)
4. 할당 줄이기 실전 팁
5. PGO, weak 포인터 등 최신 기능
```

> 최적화의 제1원칙: **측정하지 않고 최적화하지 않는다.** 대부분의 코드는 이 문서의 내용을 신경 쓰지 않아도 충분히 빠릅니다.

# 1. 스택과 힙

```
스택 (Stack)
- 고루틴마다 하나 (2KB 에서 시작해 필요하면 자동으로 커짐/줄어듦)
- 함수가 끝나면 자동으로 해제 → GC 부담 없음
- 할당/해제가 매우 빠름 (포인터 이동만)

힙 (Heap)
- 모든 고루틴이 공유
- 수명이 함수보다 길 수 있는 값
- GC 가 추적하고 회수 → 할당이 많을수록 GC 비용 증가
```

C에서는 개발자가 스택/힙을 선택하지만, **Go는 컴파일러가 결정**합니다. 이 결정 과정이 탈출 분석입니다.

# 2. 탈출 분석 (Escape Analysis)

"이 값이 함수가 끝난 뒤에도 살아있어야 하는가?"를 컴파일 타임에 분석합니다.

```go
package main

import "fmt"

type Point struct{ X, Y int }

// 1) 값으로 반환: 스택에 머묾
func newPointValue() Point {
	p := Point{1, 2}
	return p
}

// 2) 포인터로 반환: 힙으로 탈출
func newPointPtr() *Point {
	p := Point{1, 2}
	return &p
}

// 3) 인터페이스(any) 파라미터
func printIt(v any) {
	_ = v
}

// 4) 크기를 컴파일 타임에 모르는 슬라이스
func makeSlice(n int) []int {
	return make([]int, n)
}

// 5) 크기가 작은 상수 크기 슬라이스
func sumSmall() int {
	s := make([]int, 8)
	total := 0
	for _, v := range s {
		total += v
	}
	return total
}

func main() {
	a := newPointValue()
	b := newPointPtr()
	printIt(a)
	_ = makeSlice(10)
	_ = sumSmall()
	fmt.Println(a, *b)
}
```

```bash
# -m: 탈출 분석 결과 출력, -l: 인라이닝 끄기(결과를 보기 쉽게)
go build -gcflags='-m -l' .
```

```
./main.go:15:2: moved to heap: p                      ← 2) 포인터 반환
./main.go:20:14: v does not escape                     ← 3) 저장하지 않으면 탈출 안 함
./main.go:26:13: make([]int, n) escapes to heap        ← 4) 크기 모름 + 반환
./main.go:31:11: make([]int, 8) does not escape        ← 5) 작고 크기 고정
./main.go:45:14: a escapes to heap                     ← fmt.Println(any...) 로 전달
./main.go:45:17: *b escapes to heap
```

## 힙으로 탈출하는 대표적인 경우

```
✅ 로컬 변수의 포인터를 반환하거나 전역/힙 객체에 저장
✅ 클로저가 캡처한 변수가 함수보다 오래 살 때 (고루틴에서 사용 등)
✅ 인터페이스에 담아서 저장하거나 fmt.Println 같은 함수에 전달
✅ 크기를 컴파일 타임에 알 수 없는 make, 또는 너무 큰 할당
✅ 채널로 포인터를 보낼 때
```

> 인라이닝(inlining)이 되면 호출한 쪽 기준으로 다시 분석되기 때문에, 실제 빌드(`-l` 없이)에서는 탈출하지 않는 경우도 많습니다. "포인터를 반환하면 무조건 느리다"고 단정하지 말고 벤치마크로 확인합니다.

# 3. 가비지 컬렉터

## Go GC의 특징

```
- 동시(concurrent) 마크 & 스윕: 애플리케이션과 함께 돌면서 대부분의 작업을 수행
- 삼색(tri-color) 마킹 + 쓰기 배리어(write barrier)
- 세대(generational) 구분 없음, 압축(compaction) 없음
- Stop-The-World 구간은 보통 1ms 미만 (마킹 시작/종료 시점에만 짧게)
- 목표: 낮은 지연 시간 (처리량보다 latency 우선)

Go 1.26+: Green Tea GC 가 기본값
  - 작은 객체를 페이지(span) 단위로 모아서 스캔 → 메모리 지역성 개선
  - GC 오버헤드 10~40% 감소 (최신 amd64 에서는 추가 개선)
  - 끄려면 빌드 시 GOEXPERIMENT=nogreenteagc
```

## 삼색 마킹 개념

```
흰색: 아직 방문 안 함 (마킹이 끝났을 때 흰색이면 → 쓰레기)
회색: 발견했지만 내부 포인터를 아직 안 봄
검은색: 내부까지 다 봄 (살아있음)

1. 루트(전역 변수, 고루틴 스택)에서 참조하는 객체를 회색으로
2. 회색 객체를 하나씩 꺼내서 참조하는 객체를 회색으로, 자신은 검은색으로
3. 회색이 없어질 때까지 반복
4. 남은 흰색 객체 회수

마킹 도중 애플리케이션이 포인터를 바꾸면? → 쓰기 배리어가 추적
```


```
8 P               → GOMAXPROCS
```

# 4. GC 튜닝: GOGC와 GOMEMLIMIT

## GOGC: 얼마나 자주 GC 할까

```
GOGC=100 (기본값)
→ 살아있는 힙이 10MB 면, 힙이 20MB(100% 증가)가 되었을 때 다음 GC

GOGC=200 → 30MB 에서 GC: 덜 자주 GC, CPU 절약, 메모리 더 사용
GOGC=50  → 15MB 에서 GC: 더 자주 GC, 메모리 절약, CPU 더 사용
GOGC=off → GC 끄기 (짧게 실행되는 CLI 등 특수한 경우)
```

```go
import "runtime/debug"

debug.SetGCPercent(200) // 코드에서 설정
```

## GOMEMLIMIT: 메모리 상한 (Go 1.19+)

컨테이너 환경에서 매우 중요합니다.

```
문제 상황:
- 컨테이너 메모리 제한 1GB
- 살아있는 힙 600MB, GOGC=100 → 1.2GB 에서 GC 하려고 기다리다가 OOMKilled

GOMEMLIMIT=900MiB 설정 시:
- 전체 메모리 사용량이 900MiB 에 가까워지면 GOGC 와 상관없이 GC 를 더 자주 실행
- 평소에는 GOGC 대로 동작해서 CPU 낭비 없음
```

```bash
# 컨테이너 메모리 제한의 약 90% 정도로 설정하는 것이 일반적
GOMEMLIMIT=900MiB ./app

# 메모리가 넉넉한 환경에서 GC 를 최소화하고 상한으로만 관리
GOGC=off GOMEMLIMIT=900MiB ./app
```

```go
debug.SetMemoryLimit(900 << 20) // 코드에서 설정 (바이트)
```

```yaml
# Kubernetes 에서 limit 값을 자동으로 주입하는 예
env:
  - name: GOMEMLIMIT
    valueFrom:
      resourceFieldRef:
        resource: limits.memory
```

> `GOGC=off`와 함께 쓸 때 실제 사용량이 한계를 넘으면 GC가 계속 돌면서 CPU를 소모할 수 있습니다(death spiral). 런타임이 GC CPU를 약 50%로 제한하는 안전장치가 있지만, 한계를 너무 빡빡하게 잡지 않도록 주의합니다.

## 메모리 통계 확인

```go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	fmt.Printf("HeapAlloc=%d KB NumGC=%d\n", m.HeapAlloc/1024, m.NumGC)

	data := make([][]byte, 0)
	for range 1000 {
		data = append(data, make([]byte, 10_000)) // 약 10MB 할당
	}

	runtime.ReadMemStats(&m)
	fmt.Printf("HeapAlloc=%d KB NumGC=%d\n", m.HeapAlloc/1024, m.NumGC)
	_ = data
	// 출력 (예시):
	// HeapAlloc=236 KB NumGC=0
	// HeapAlloc=10232 KB NumGC=2
}
```

> `ReadMemStats`는 STW를 일으키므로 자주 호출하지 않습니다. 운영 모니터링에는 `runtime/metrics` 패키지나 Prometheus `client_golang`의 기본 Go 메트릭을 씁니다.

# 5. 프로파일링: pprof

## 프로파일 종류

```
cpu          → 어떤 함수가 CPU 시간을 쓰는가
heap         → 현재 살아있는 메모리를 누가 할당했는가 (inuse_space)
allocs       → 지금까지 누가 얼마나 할당했는가 (alloc_space) → GC 부담 원인 찾기
goroutine    → 지금 고루틴들이 어디서 무엇을 하고 있는가 → 누수, 데드락
block        → 채널/락에서 얼마나 블록되었는가
mutex        → 락 경합
goroutineleak → 누수된 고루틴 (Go 1.27+ 정식 지원)
```

## 1) 서버에 pprof 엔드포인트 붙이기

```go
package main

import (
	"log"
	"net/http"
	_ "net/http/pprof" // /debug/pprof/ 핸들러가 DefaultServeMux 에 등록됨
)

func main() {
	// 운영 트래픽과 분리된 내부 포트로 (외부에 노출 금지!)
	go func() {
		log.Println(http.ListenAndServe("localhost:6060", nil))
	}()

	// ... 실제 애플리케이션
	select {}
}
```

## 실행 추적: trace

pprof가 "어디서 시간을 쓰나"라면, trace는 **"시간 순서대로 무슨 일이 있었나"** 를 봅니다. 고루틴 스케줄링 지연, GC 멈춤, 네트워크 블로킹을 타임라인으로 확인합니다.

```bash
go test -trace trace.out .
curl -o trace.out http://localhost:6060/debug/pprof/trace?seconds=5

go tool trace trace.out
```

> Go 1.25+ `runtime/trace.FlightRecorder`는 최근 몇 초의 트레이스를 메모리 링 버퍼에 계속 기록하다가, 문제가 생긴 순간에만 파일로 저장할 수 있습니다.

## 1) 슬라이스/맵 용량 미리 잡기

```go
var ids []int
for _, u := range users {
	ids = append(ids, u.ID)

// ✅ 한 번만 할당

```

```go
var sb strings.Builder
sb.Grow(estimatedSize) // 크기를 알면 미리 확보
```

## 3) []byte ↔ string 변환 줄이기

```go
// 변환마다 복사가 일어남
s := string(b)
b := []byte(s)

// 가능하면 bytes 패키지 함수를 직접 사용
bytes.Contains(b, []byte("x"))
// strings.Builder, bytes.Buffer 의 Write 계열 활용
```

## 4) 핫 경로에서 인터페이스/fmt 피하기

```go
// fmt.Sprintf 는 인자를 any 로 받아서 할당이 생김
key := fmt.Sprintf("user:%d", id)

// strconv 가 더 가벼움
key := "user:" + strconv.Itoa(id)
```

## 5) 포인터가 없는 구조체는 GC 가 스캔하지 않는다

```go
// GC 가 내부를 스캔해야 함 (string 은 내부에 포인터)
type EntryA struct {
	Name string
	Tags []string
}

// 포인터 없음 → 이런 원소로 된 큰 슬라이스는 GC 스캔 비용이 거의 없음
type EntryB struct {
	ID    int64
	Score float64
	Flags uint32
}
```

수백만 개의 객체를 메모리에 올리는 캐시라면, 포인터를 줄인 구조로 바꾸는 것만으로 GC 시간이 크게 줄 수 있습니다.

## 6) 큰 슬라이스의 일부만 들고 있지 않기

```go
// ❌ 100MB 파일에서 10바이트만 필요한데 전체 배열이 GC 되지 않음
func header(data []byte) []byte {
	return data[:10]
}

// ✅ 복사해서 원본을 놓아줌
func header(data []byte) []byte {
	return bytes.Clone(data[:10])
}
```

# 7. PGO (Profile-Guided Optimization, Go 1.21+)

운영 환경의 CPU 프로파일을 컴파일러에 주면, **자주 호출되는 경로를 더 적극적으로 인라이닝**하는 등 최적화를 해줍니다. 공식 문서 기준(Go 1.22+) 대표적인 프로그램에서 약 2~14% 성능이 개선됩니다.

```bash
# 1. 운영(또는 대표 부하)에서 CPU 프로파일 수집
curl -o cpu.pprof "http://localhost:6060/debug/pprof/profile?seconds=30"

# 2. main 패키지 폴더에 default.pgo 로 저장
mv cpu.pprof ./cmd/server/default.pgo

# 3. 그냥 빌드하면 자동 적용 (-pgo=auto 가 기본값)
go build ./cmd/server
```

# 8. 약한 포인터와 Cleanup (Go 1.24+)

캐시처럼 "누군가 쓰고 있으면 유지하고, 아무도 안 쓰면 GC가 가져가도 되는" 구조를 만들 때 씁니다.

```go
package main

import (
	"fmt"
	"runtime"
	"weak"
)

type Blob struct {
	data [1 << 20]byte // 1MB
}

func main() {
	b := &Blob{}
	wp := weak.Make(b) // 약한 참조: GC 를 막지 않음

	// 객체가 회수될 때 실행할 정리 함수 (SetFinalizer 의 개선판)
	runtime.AddCleanup(b, func(name string) {
		fmt.Println("정리됨:", name)
	}, "blob-1")

	fmt.Println("살아있음:", wp.Value() != nil)

	runtime.KeepAlive(b) // 여기까지는 b 를 사용 중
	b = nil
	runtime.GC()
	runtime.GC()

	fmt.Println("회수 후:", wp.Value() == nil)
	// 출력 (cleanup 은 별도 고루틴에서 실행되어 순서가 달라질 수 있음):
	// 살아있음: true
	// 정리됨: blob-1
	// 회수 후: true
}
```

```
weak.Pointer[T]
- Value() 가 nil 이면 이미 회수된 것
- unique 패키지(Go 1.23+) 의 인터닝 구현에도 사용

runtime.AddCleanup vs runtime.SetFinalizer
- 한 객체에 여러 개 등록 가능
- 순환 참조가 있어도 누수 없음
- 객체 부활(resurrection) 불가 → 더 예측 가능
```

일반 애플리케이션 코드에서 직접 쓸 일은 드물고, 라이브러리/캐시 구현용 저수준 도구입니다.

# 9. 메모리 문제 진단 체크리스트

```
메모리가 계속 증가한다
  → heap 프로파일을 시간 간격을 두고 두 번 뽑아서 비교
     go tool pprof -base heap1.pb.gz heap2.pb.gz
  → goroutine 프로파일로 고루틴 수 증가 확인 (고루틴 누수가 가장 흔한 원인)
  → 전역 맵/캐시에 삭제 로직이 있는지 확인

GC CPU 가 높다
  → allocs 프로파일로 할당이 많은 함수 찾기
  → GOGC 올리기 + GOMEMLIMIT 으로 상한 관리

OOMKilled
  → GOMEMLIMIT 을 컨테이너 limit 의 90% 정도로 설정
  → 한 번에 큰 데이터를 메모리에 올리지 말고 스트리밍(io.Reader) 처리

p99 지연이 튄다
  → go tool trace 로 GC STW, 스케줄링 지연 확인
  → 락 경합이면 mutex 프로파일
```

## 정리

- 스택/힙 할당은 컴파일러의 탈출 분석이 결정, `-gcflags='-m'`으로 확인
- Go GC는 동시 삼색 마크 & 스윕, 짧은 STW, Go 1.26+ Green Tea GC 기본
- `GOGC`로 GC 빈도, `GOMEMLIMIT`(1.19+)으로 메모리 상한, 컨테이너에서는 GOMEMLIMIT 필수급
- `net/http/pprof`와 `go tool pprof`로 CPU/heap/allocs/goroutine 프로파일 분석
- `go tool trace`로 시간 순서의 실행 흐름 분석
- 용량 미리 할당, strings.Builder, 포인터 적은 구조체, sync.Pool로 할당 줄이기
- `default.pgo`로 PGO 적용(1.21+), `weak`/`runtime.AddCleanup`(1.24+)
- 최적화는 항상 프로파일로 측정한 뒤에
