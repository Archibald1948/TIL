# 고루틴 - 수십만 개를 띄워도 가벼운 동시성 단위

## 들어가며

Go가 서버 개발에서 사랑받는 가장 큰 이유가 **고루틴(goroutine)** 입니다.

```
JavaScript (Node.js):
- 싱글 스레드 + 이벤트 루프
- async/await 로 "기다리는 동안 다른 일"을 함
- CPU를 많이 쓰는 작업은 메인 스레드를 막음 → Worker Threads 필요

Java (전통적 방식):
- OS 스레드 하나당 메모리 약 1MB
- 요청마다 스레드를 만들면 수천 개에서 한계

Go:
- 고루틴 하나당 시작 스택 약 2KB (필요하면 자동으로 늘어남)
- 수십만 ~ 수백만 개도 가능
- 코드는 동기(블로킹) 스타일로 작성, 런타임이 알아서 멀티코어에 분산
- async/await, 콜백, Promise 가 필요 없음
```

`net/http` 서버가 요청마다 고루틴을 하나씩 띄우는 단순한 구조로도 높은 성능을 내는 이유입니다.

# 1. 고루틴 시작하기

## go 키워드

```go
package main

import (
	"fmt"
	"time"
)

func say(msg string) {
	for i := range 3 {
		fmt.Println(msg, i)
		time.Sleep(10 * time.Millisecond)
	}
}

func main() {
	go say("고루틴") // 새 고루틴에서 실행, 즉시 다음 줄로 넘어감
	say("main")   // main 고루틴에서 실행

	// 실행할 때마다 순서가 섞여서 출력됨
}
```

함수 호출 앞에 `go`만 붙이면 됩니다. 익명 함수도 됩니다.

```go
go func() {
	fmt.Println("익명 함수 고루틴")
}()
```

## main이 끝나면 전부 끝난다

```go
package main

import "fmt"

func main() {
	go fmt.Println("출력될까?")
	// main 이 바로 끝나면 다른 고루틴은 기다려주지 않고 강제 종료됨
}
```

위 코드는 대부분 아무것도 출력하지 않습니다. **고루틴이 끝나기를 기다리는 장치**가 필요합니다.

# 2. 기다리기: sync.WaitGroup

## wg.Go (Go 1.25+)

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func fetch(url string) string {
	time.Sleep(50 * time.Millisecond) // 네트워크 요청이라고 가정
	return "응답:" + url
}

func main() {
	urls := []string{"a.com", "b.com", "c.com"}
	results := make([]string, len(urls))

	var wg sync.WaitGroup
	start := time.Now()

	for i, url := range urls {
		wg.Go(func() { // Add(1) + go + defer Done() 을 한 번에
			results[i] = fetch(url) // 각자 다른 인덱스에 쓰므로 안전
		})
	}

	wg.Wait() // 모두 끝날 때까지 대기

	fmt.Println(results)
	fmt.Println("걸린 시간 < 100ms:", time.Since(start) < 100*time.Millisecond)
	// 출력:
	// [응답:a.com 응답:b.com 응답:c.com]
	// 걸린 시간 < 100ms: true      ← 순차 실행이면 150ms
}
```

## Add / Done (Go 1.24 이하 방식)

기존 코드에서 매우 많이 보이는 형태입니다.

```go
var wg sync.WaitGroup
for _, url := range urls {
	wg.Add(1) // 고루틴 시작 "전에" 호출
	go func() {
		defer wg.Done()
		fetch(url)
	}()
}
wg.Wait()
```

```
주의:
❌ wg.Add(1) 을 고루틴 "안에서" 호출 → Wait 가 먼저 실행되어 기다리지 않을 수 있음
   (Go 1.25 go vet 의 waitgroup 검사가 잡아줌)
❌ WaitGroup 을 값으로 복사해서 함수에 넘기기 → 포인터로 넘겨야 함
```

# 3. 경쟁 상태 (Race Condition)

## 문제

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	count := 0
	var wg sync.WaitGroup
	for range 1000 {
		wg.Go(func() {
			count++ // 여러 고루틴이 동시에 읽고 씀 (데이터 레이스)
		})
	}
	wg.Wait()
	fmt.Println(count) // 1000 이 아닐 수 있음
}
```

```
실행 결과 (매번 다름):
979
977
980
```

`count++`는 사실 "읽기 → 1 더하기 → 쓰기" 세 단계라서, 두 고루틴이 같은 값을 읽고 둘 다 같은 값을 쓰면 하나가 사라집니다.

## 레이스 디텍터

```bash
go run -race .
go test -race ./...
```

```
==================
WARNING: DATA RACE
Read at 0x00c000094038 by goroutine 10:
  main.main.func1()
      .../main.go:13 +0x2c

Previous write at 0x00c000094038 by goroutine 7:
  main.main.func1()
      .../main.go:13 +0x3c

Goroutine 10 (running) created at:
  sync.(*WaitGroup).Go()
      .../sync/waitgroup.go:238 +0x6c
==================
```

어느 줄에서 누가 읽고 썼는지 알려줍니다. **실제로 실행된 경로만 탐지**하므로 테스트 커버리지가 중요하고, 성능 오버헤드(CPU 2~20배)가 있어서 운영 환경보다는 테스트/CI에서 켭니다.

## 해결 방법 3가지

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

func main() {
	var wg sync.WaitGroup

	// 1) Mutex: 임계 구역 보호
	var mu sync.Mutex
	count1 := 0
	for range 1000 {
		wg.Go(func() {
			mu.Lock()
			count1++
			mu.Unlock()
		})
	}

	// 2) atomic: 단순 카운터라면 가장 빠름
	var count2 atomic.Int64
	for range 1000 {
		wg.Go(func() {
			count2.Add(1)
		})
	}

	// 3) 채널: 값을 한 고루틴에게만 보내서 소유권 이동
	ch := make(chan int)
	done := make(chan int)
	go func() {
		total := 0
		for n := range ch {
			total += n
		}
		done <- total
	}()
	var wg2 sync.WaitGroup
	for range 1000 {
		wg2.Go(func() { ch <- 1 })
	}
	wg2.Wait()
	close(ch)

	wg.Wait()
	fmt.Println(count1, count2.Load(), <-done)
	// 출력: 1000 1000 1000
}
```

> Go 속담: **"Do not communicate by sharing memory; instead, share memory by communicating."** (메모리를 공유해서 통신하지 말고, 통신해서 메모리를 공유하라)
>
> 그렇다고 무조건 채널이 정답은 아닙니다. 단순한 상태 보호는 Mutex가 더 명확하고 빠릅니다.

# 4. 고루틴은 어떻게 동작하나: GMP 스케줄러

```
G (Goroutine)  → 실행할 코드 + 스택 (2KB에서 시작)
M (Machine)    → OS 스레드
P (Processor)  → 실행 권한 + 로컬 실행 큐. 개수 = GOMAXPROCS

      P0              P1              P2              P3
   [G G G]         [G G]           [G G G G]       [G]      ← 로컬 큐
      │               │               │               │
      M0              M1              M2              M3     ← OS 스레드
      │               │               │               │
    CPU0            CPU1            CPU2            CPU3

전역 큐: [G G G ...]
```

```
동작 방식:
- M:N 스케줄링: 수많은 G 를 적은 수의 M 에 올려서 실행
- 한 P 의 큐가 비면 다른 P 의 큐에서 절반을 훔쳐옴 (work stealing)
- G 가 네트워크 I/O 로 블록되면 → netpoller(epoll/kqueue)에 등록하고 M 은 다른 G 실행
- G 가 시스템 콜로 오래 블록되면 → P 를 다른 M 에게 넘김
- 오래 실행되는 G 는 비동기 선점(Go 1.14+)으로 강제로 양보
```

그래서 개발자는 `conn.Read()` 같은 **블로킹 코드를 그냥 작성**해도, 런타임이 내부적으로는 논블로킹 I/O처럼 처리합니다.

## GOMAXPROCS

```go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	fmt.Println("CPU 수:", runtime.NumCPU())
	fmt.Println("GOMAXPROCS:", runtime.GOMAXPROCS(0)) // 0 = 조회만
	fmt.Println("현재 고루틴 수:", runtime.NumGoroutine())
}
```

```
기본값: CPU 코어 수
Go 1.25+: Linux 컨테이너의 cgroup CPU 제한을 인식해서 자동 설정
          (예: 64코어 노드에서 CPU limit 2 인 파드 → GOMAXPROCS=2)
          예전에는 이 문제 때문에 uber-go/automaxprocs 를 쓰곤 했음
```

# 5. 고루틴 누수 (Goroutine Leak)

고루틴은 가볍지만 **끝나지 않으면 메모리를 계속 차지**합니다. GC는 블록된 고루틴을 회수하지 않습니다.

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

// ❌ 누수: 아무도 ch 를 읽지 않으면 이 고루틴은 영원히 블록
func leaky() {
	ch := make(chan int)
	go func() {
		ch <- 42 // 받는 쪽이 없어서 영원히 대기
	}()
	// ch 를 읽지 않고 반환
}

// ✅ 버퍼를 줘서 받는 쪽이 없어도 보내고 끝날 수 있게
func fixed() {
	ch := make(chan int, 1)
	go func() {
		ch <- 42
	}()
}

func main() {
	for range 1000 {
		leaky()
	}
	for range 1000 {
		fixed()
	}
	time.Sleep(100 * time.Millisecond)
	fmt.Println("남아있는 고루틴:", runtime.NumGoroutine())
	// 출력: 남아있는 고루틴: 1001   (main + 누수된 1000개)
}
```

```
누수가 생기는 대표적인 경우:
- 받는 쪽이 없는 채널에 보내기 / 보내는 쪽이 없는 채널에서 받기
- 닫히지 않는 채널을 range
- 타임아웃/취소 없이 외부 응답을 무한정 기다리기
- 끝나는 조건이 없는 for-select 루프

예방법:
✅ 고루틴을 시작할 때 "언제 어떻게 끝나는지" 먼저 정하기
✅ context 로 취소 신호 전달 (context 문서)
✅ 테스트에서 go.uber.org/goleak 으로 검사
✅ Go 1.27+: runtime/pprof 의 goroutineleak 프로파일로 탐지
```

# 6. 고루틴에서 에러와 결과 받기

고루틴은 반환값을 직접 받을 수 없습니다. 보통 이런 방법을 씁니다.

```go
package main

import (
	"errors"
	"fmt"
	"sync"
)

type result struct {
	id  int
	val string
	err error
}

func work(id int) (string, error) {
	if id == 2 {
		return "", errors.New("2번 작업 실패")
	}
	return fmt.Sprintf("작업%d 완료", id), nil
}

func main() {
	// 방법 1: 인덱스별 슬라이스에 저장 (순서 유지)
	ids := []int{1, 2, 3}
	results := make([]result, len(ids))
	var wg sync.WaitGroup
	for i, id := range ids {
		wg.Go(func() {
			v, err := work(id)
			results[i] = result{id, v, err}
		})
	}
	wg.Wait()
	for _, r := range results {
		fmt.Println(r.id, r.val, r.err)
	}
	// 출력:
	// 1 작업1 완료 <nil>
	// 2  2번 작업 실패
	// 3 작업3 완료 <nil>

	// 방법 2: 결과 채널 (완료 순서대로)
	ch := make(chan result, len(ids))
	for _, id := range ids {
		go func() {
			v, err := work(id)
			ch <- result{id, v, err}
		}()
	}
	for range ids {
		r := <-ch
		_ = r
	}

	// 방법 3: errgroup (첫 에러 반환 + 취소) → 동시성 패턴 문서
}
```

# 7. 고루틴과 클로저

Go 1.22부터 루프 변수가 반복마다 새로 생성되므로 아래 코드는 안전합니다.

```go
for _, url := range urls {
	go func() {
		fetch(url) // Go 1.22+: 각 고루틴이 자기 url 을 가짐
	}()
}
```

Go 1.21 이하(또는 go.mod 의 go 버전이 1.21 이하)에서는 모든 고루틴이 **마지막 url**을 보는 버그가 있어서 이렇게 썼습니다.

```go
for _, url := range urls {
	go func(u string) { // 인자로 복사해서 넘기기
		fetch(u)
	}(url)
}
```

# 8. 동시성 vs 병렬성

```
동시성 (Concurrency): 여러 작업을 "다루는" 구조
  → 한 명의 요리사가 파스타 물 끓이는 동안 소스를 만듦

병렬성 (Parallelism): 여러 작업을 "동시에 실행"
  → 요리사 네 명이 각자 요리를 만듦

Go 의 고루틴은 동시성을 표현하는 도구이고,
GOMAXPROCS > 1 이면 런타임이 병렬로도 실행해준다.
```

Rob Pike의 발표 "Concurrency is not Parallelism"이 이 개념을 잘 설명합니다.

# 9. 고루틴을 쓸 때 체크리스트

```
✅ 이 고루틴은 언제 끝나는가? (종료 조건)
✅ 누가 끝날 때까지 기다리는가? (WaitGroup, 채널, errgroup)
✅ 공유 데이터가 있는가? → Mutex / atomic / 채널
✅ 에러는 어떻게 전달하는가?
✅ panic 이 나면? → 해당 고루틴에서 recover 하지 않으면 프로그램 전체 종료
✅ 무한정 띄우지 않는가? → 동시 실행 개수 제한 (worker pool, semaphore)
✅ go test -race 로 확인했는가?
```

## 정리

- `go f()`로 고루틴 시작, main이 끝나면 모든 고루틴도 종료
- 기다리기는 `sync.WaitGroup`, Go 1.25+ `wg.Go(func(){...})`
- 공유 변수 동시 접근은 데이터 레이스 → Mutex, atomic, 채널로 해결
- `-race` 플래그로 레이스 탐지, CI에서 항상 켜기
- GMP 스케줄러가 고루틴을 OS 스레드에 분배, 블로킹 코드도 효율적으로 처리
- Go 1.25+ GOMAXPROCS가 컨테이너 CPU 제한을 자동 인식
- 끝나지 않는 고루틴은 누수, 시작할 때 종료 조건을 먼저 설계
